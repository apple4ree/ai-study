# 네트워크 요청은 여러 계층의 약속을 거친다

브라우저에서 문서 검색 버튼을 눌렀는데 답이 늦게 온다고 하자. 모델 계산이 느린 것일 수도 있지만 DNS 조회, 연결 수립, 서버 대기열, 데이터베이스, 응답 전송이 병목일 수도 있다. 클라이언트가 timeout을 보았는데 서버에서는 이미 작업이 끝났을 수도 있다. 네트워크는 함수 호출을 멀리 보낸 것처럼 보이지만 지연·유실·재전송·부분 실패가 끼어든다. 어떤 계층이 무엇을 보장하는지 구분하는 것이 출발점이다.

## 주소, 포트, 소켓과 계층

### 개념과 작동 원리

IP 주소는 네트워크에서 목적지를 지정하는 데 사용한다. 포트는 그 호스트 안에서 통신할 서비스·끝점을 구별한다. 소켓은 프로그램이 운영체제의 통신 기능을 사용하는 인터페이스다. 같은 호스트에 여러 서버가 있더라도 서로 다른 포트로 접근할 수 있고, 연결은 출발·도착 주소와 포트 등으로 구별된다. NAT나 프록시가 있으면 사용자가 보는 주소와 실제 서버 내부 주소가 같지 않을 수 있다.

계층을 나누면 각 부분이 다른 문제를 담당할 수 있다. 링크 계층은 한 구간에서 프레임을 전달하고, IP는 여러 네트워크 사이의 패킷 전달을 다룬다. 전송 계층은 프로세스 사이의 전달 의미를 제공하고 HTTP 같은 응용 프로토콜은 요청·응답의 뜻을 정한다. 인터넷을 지나는 모든 라우터가 애플리케이션의 JSON 의미를 이해해야 하는 것은 아니다. 반대로 애플리케이션이 라우팅의 모든 세부사항을 직접 구현할 필요도 없다.

DNS는 사람이 사용하는 이름을 주소 등의 레코드로 해석하는 분산된 이름 시스템이다. 매 요청마다 이름을 처음부터 전부 찾는 것은 아니며 캐시와 유효기간이 개입한다. 이름 조회 실패, 오래된 캐시, 주소는 맞지만 서버 포트가 닫힌 경우는 서로 다른 오류다. “사이트가 안 열린다”는 하나의 현상을 계층별로 나누면 무엇을 확인해야 할지 좁혀진다.

### 목적지와 연결을 식별하는 정보

클라이언트 10.0.0.2:50000이 서버 10.0.0.8:443에 연결하는 예를 생각하자. 같은 클라이언트가 50001 포트로 두 번째 연결을 만들면 서버 포트가 같아도 두 흐름을 구분할 수 있다.

| 정보 | 주된 역할 | 단독으로 알 수 없는 것 |
|---|---|---|
| 이름 | 사용자가 찾는 대상 표현 | 실제 연결 성공 여부 |
| IP 주소 | 네트워크 목적지 식별 | 해당 서비스가 정상 동작하는지 |
| 포트 | 전송 끝점 구분 | 사용자의 계정·업무 요청 |
| 소켓 | OS 통신 인터페이스·끝점 상태 | 애플리케이션 응답이 의미상 성공인지 |

일반적인 TCP 연결은 출발·목적 IP와 포트의 조합으로 구분한다. 주소 변환·프록시·로드밸런서가 있으면 각 구간에서 보이는 주소가 달라질 수 있다. **DNS 성공, TCP 연결 성공, HTTP 성공, 업무 성공은 서로 다른 단계**다.

## IP와 TCP가 보장하는 범위

### 개념과 작동 원리

IP 패킷은 목적지 쪽으로 전달되지만 도착·순서·중복 없음까지 모두 보장하지 않는다. 중간 경로에서 버려지거나 순서가 바뀔 수 있다. TCP는 이런 네트워크 위에 순서 있는 신뢰성 있는 바이트 스트림을 제공한다. 순서 번호와 확인응답, 재전송 등으로 누락을 복구하고 중복 바이트를 처리한다. 연결 안에서 데이터의 순서와 전달을 다루지만 응용 작업이 성공했다는 뜻까지 해석하지는 않는다.

TCP의 흐름 제어는 수신자가 받아들일 수 있는 양을 넘지 않도록 조절한다. 혼잡 제어는 네트워크가 감당할 수 있는 양에 맞추어 보내는 속도를 조정한다. 수신 버퍼가 부족한 문제와 경로가 혼잡한 문제는 다르다. 네트워크가 왕복으로 확인을 주고받는 시간인 RTT가 크면 충분한 데이터를 동시에 전송 중으로 두지 못할 때 처리량이 제한될 수 있다. 대역폭만 보고 실제 파일 전송 속도를 정확히 예측할 수 없는 이유다.

TCP 연결 수립에는 양쪽의 연결 상태와 순서 정보를 맞추는 과정이 필요하다. 연결이 끊겼거나 재전송을 기다리는 경우 응용 코드의 `read`는 대기하거나 timeout·오류를 볼 수 있다. 운영체제가 하는 재전송과 응용 코드가 요청 전체를 다시 보내는 retry는 다른 층의 동작이다. 둘을 구분하지 않으면 지연을 여러 겹으로 늘리거나 같은 업무를 중복 실행할 수 있다.

UDP는 TCP처럼 순서 있는 연결 바이트 스트림을 자동 제공하지 않는 데이터그램 전송이다. 응용 목적에 따라 지연과 제어를 더 직접 다루거나 상위 프로토콜이 신뢰성을 구현할 수 있다. UDP를 쓴다는 말이 곧 모든 응용이 신뢰성 없이 동작한다는 뜻은 아니다. HTTP/3가 사용하는 QUIC는 UDP 위에서 신뢰성·암호화·다중 스트림 등 별도 규칙을 제공한다.

### TCP ACK가 확인하는 범위

애플리케이션이 '주문 저장' 요청을 보내고 TCP ACK를 받았다고 하자. ACK는 전송 계층의 바이트 수신 상태와 관련되며, 서버 프로그램이 내용을 파싱하고 DB 저장을 완료했다는 업무 확인은 아니다.

| 상황 | TCP 계층의 역할 | 응용 계층의 역할 |
|---|---|---|
| 패킷 일부 손실 | 재전송·순서 복구 | 연결 실패·지연 시 정책 결정 |
| 바이트 도착 | 스트림으로 제공 | 메시지 경계·인코딩 해석 |
| 서버 처리 완료 | 그 의미를 알지 못함 | 결과 코드·식별자·상태로 표현 |

한 TCP 흐름에서 앞쪽 바이트가 손실되면 뒤쪽이 도착해도 순서 있는 스트림 제공이 기다릴 수 있다. 신뢰성 있는 전송이라는 말이 유한한 시간 안에 성공 응답을 반드시 받는다는 뜻은 아니다. 보장 범위는 [TCP 표준 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)의 byte-stream service와 구분해 읽는다.

## 바이트 스트림에는 JSON 경계가 없다

### 개념과 작동 원리

TCP에서 송신자가 `send`를 두 번 했다는 사실이 수신자의 `recv` 두 번과 일치하지 않는다. 수신 버퍼에 도착한 양에 따라 메시지 일부만 읽거나 여러 메시지를 함께 읽을 수 있다. 따라서 데이터의 끝을 찾는 framing 규칙이 필요하다. 고정 길이, 길이 prefix, 구분자, HTTP처럼 정해진 프로토콜을 사용할 수 있다.

```py
def recv_exact(sock, n):
    data = bytearray()
    while len(data) < n:
        chunk = sock.recv(n - len(data))
        if not chunk:
            raise EOFError('message ended early')
        data.extend(chunk)
    return bytes(data)
```

길이가 5인 본문을 읽는데 첫 recv가 `b'he'`, 다음이 `b'llo'`를 주었다고 하자. 첫 반복 뒤 길이는 2이므로 아직 3바이트를 더 요청한다.

둘째 반복 뒤 5가 되어 루프를 끝내고 `b'hello'`를 반환한다. 중간에 빈 bytes가 오면 상대가 연결을 닫은 상황을 처리한다.

실서비스에서는 n의 최대값, timeout, 취소, 악의적 길이값까지 제한해야 한다. 이 함수는 길이 n이 이미 프로토콜에 따라 알려졌다는 가정만을 다룬 예제다.


줄바꿈으로 나눈다고 정하면 본문에 줄바꿈이 들어가는 경우의 escaping 규칙도 필요하다. 메시지 길이를 앞에 붙인다면 길이값의 바이트 수·바이트 순서·상한을 정한다. 구조화된 데이터를 보내는 일은 JSON으로 직렬화하는 것과 네트워크에서 메시지 경계를 유지하는 두 문제를 모두 포함한다.

### 길이 헤더도 나뉘어 도착할 수 있다

본문 앞에 2바이트 big-endian 길이를 붙이는 학습용 프레임을 생각하자. 본문이 hello이면 길이 5를 먼저 보내지만 그 헤더 두 바이트도 한 recv로 온다는 보장은 없다.

```py
payload = b'hello'
wire = len(payload).to_bytes(2, 'big') + payload
chunks = [wire[:1], wire[1:4], wire[4:]]
buffer = bytearray()
for chunk in chunks:
    buffer.extend(chunk)
size = int.from_bytes(buffer[:2], 'big')
assert size == 5
assert bytes(buffer[2:2+size]) == b'hello'
```

1. 고정 크기 헤더를 필요한 길이까지 모은다.
2. 헤더를 해석하고 허용 최대 길이 안인지 검사한다.
3. 본문도 필요한 길이가 모일 때까지 읽는다.
4. 남은 바이트는 다음 프레임 입력으로 유지한다.

본문 n바이트를 한 번씩 모으는 이상적 누적은 O(n) 작업과 O(n) 저장이 필요하다. 매번 새 문자열로 전체 버퍼를 복사하면 더 비싸질 수 있다. 중간 EOF·음수/초과 길이·인코딩 오류의 처리도 계약에 넣는다. 이 예는 실제 네트워크를 호출하는 완성 수신기가 아니라 **분할 수신을 재현하는 입력 모형**이다.

## HTTP와 TLS: 전송 위에 의미와 보호를 더한다

### 개념과 작동 원리

HTTP 요청은 메서드, 대상, 헤더, 선택적 본문을 가진다. 응답은 상태코드, 헤더, 선택적 본문으로 구성된다. GET과 POST 같은 메서드에는 의미와 재시도·캐시 관련 기대가 있다. 상태코드 200은 HTTP 수준의 성공을 표현하지만 모델의 답이 사실인지, 생성한 데이터가 업무 요구를 만족하는지까지 증명하지 않는다. 응용 결과와 프로토콜 상태를 별도로 설계해야 한다.

HTTP/1.1·HTTP/2는 보통 TCP 연결을 이용하고 HTTP/3는 QUIC를 이용한다. 따라서 “HTTP는 항상 TCP”라고 외우면 최신 프로토콜을 잘못 설명하게 된다. 연결 재사용은 DNS·연결·협상 비용을 여러 요청에 나누게 한다. Connection pool은 재사용할 연결 수와 수명을 관리하지만 무조건 크게 하면 서버 연결 제한과 큐 대기를 악화시킬 수 있다.

HTTPS에서 TLS는 전송 구간의 기밀성·무결성과 서버 신원 확인 같은 보호를 제공한다. 인증서가 맞다는 사실이 서버가 생성하는 모든 내용이 참이라는 뜻은 아니다. 암호화가 끝나는 프록시와 그 뒤 내부 연결처럼 보호 경계가 나뉠 수 있다. 네트워크 보안과 응용의 권한 검증, AI 답변의 정확성은 다른 질문이다.

스트리밍 응답은 전체 결과가 준비되기 전에 일부를 보낼 수 있게 한다. LLM에서는 첫 토큰까지의 시간과 전체 생성 완료 시간을 구분할 수 있다. 서버가 부분 결과를 이미 보낸 뒤 오류가 나면 일반적인 완성 JSON 응답과 다른 오류 전달 규칙이 필요하다. HTTP chunk나 SSE 이벤트 경계, 클라이언트 버퍼링을 이해해야 화면이 왜 한꺼번에 갱신되는지도 분석할 수 있다.

### safe·idempotent·암호화의 의미 비교

| 개념 | 보장하려는 의미 | 보장하지 않는 것 |
|---|---|---|
| safe 메서드 | 요청 의미가 본질적으로 읽기 성격 | 로그 등 부수 동작이 전혀 없음 |
| idempotent 메서드 | 같은 요청 반복의 의도된 효과가 한 번과 같음 | 매번 응답 본문·상태코드까지 동일 |
| TLS | 전송 구간의 기밀성·무결성·인증 관련 보호 | 서버의 모든 업무 결과가 올바름 |

같은 대상을 지우는 DELETE를 반복했을 때 첫 응답이 성공이고 다음 응답이 '이미 없음'일 수 있다. 응답이 다르더라도 요청의 의도된 효과가 같다면 멱등 의미와 양립한다. POST는 이름만으로 중복 실행이 안전하다고 판단할 수 없다.

HTTP 메서드의 의미는 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2)에서 확인한다. TLS 종료가 프록시에서 이루어진다면 프록시 뒤 구간의 보호는 별도로 확인해야 한다. 암호화와 애플리케이션 입력 검증은 다른 문제다. TLS의 보호 범위는 [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)도 참고한다.

## 동기·비동기와 병렬성

### 개념과 작동 원리

Blocking 호출은 결과를 기다리는 동안 그 실행 흐름이 대기한다. Nonblocking I/O는 즉시 완료할 수 없는 경우를 반환하고 준비되었을 때 다시 처리할 수 있게 한다. 비동기 프로그래밍은 완료를 기다리는 동안 다른 작업을 진행하는 제어 구조다. 이벤트 루프는 준비된 작업을 이어 실행한다. 이것은 CPU가 하나의 계산을 여러 코어로 자동 분할하는 것과 다르다.

```py
import asyncio

async def one_job(name):
    await asyncio.sleep(1)  # 실제 네트워크 대신 I/O 대기를 모사
    return name

async def main():
    return await asyncio.gather(one_job('A'), one_job('B'))
```

첫 작업이 sleep으로 기다리면 이벤트 루프는 둘째 작업을 시작할 수 있다. 두 기다림이 겹치므로 순서대로 1초씩 기다리는 것과 다르다. 그러나 `await` 없이 오래 계산하는 Python 루프를 넣으면 이벤트 루프가 그 계산에 묶일 수 있다. 실제 네트워크를 사용할 때도 비동기 호환 클라이언트가 필요하며 동기 라이브러리를 async 함수 안에서 호출했다고 자동으로 비동기가 되지는 않는다.

동시성 수를 늘리면 대기를 겹쳐 처리량을 높일 수 있지만 서버·DB·외부 API의 용량은 한정되어 있다. 제한 없는 동시 호출은 연결·메모리를 소모하고 rate limit·timeout을 늘릴 수 있다. 세마포어, 제한된 큐, 연결 풀을 사용해 진행 중인 작업 수를 제어하는 이유다. 평균 속도뿐 아니라 완료 지연 분포와 실패율을 함께 측정해야 한다.

### await가 있어도 CPU 작업은 이벤트 루프를 막을 수 있다

단일 이벤트 루프에서 코루틴은 대기 가능한 작업에서 제어를 넘겨 다른 일을 진행하게 한다. 긴 Python 계산을 await 없이 실행하면 그 동안 같은 루프의 다른 코루틴이 실행될 기회를 잃을 수 있다.

| 동작 | 동시성 효과 | 주의점 |
|---|---|---|
| 비동기 I/O 대기 | 다른 요청의 I/O 진행 가능 | 호출하는 라이브러리도 비동기 계약 필요 |
| 동기 I/O를 직접 호출 | 루프가 대기할 수 있음 | async 함수 안이라는 사실만으로 안 바뀜 |
| CPU 계산 직접 실행 | 해당 실행 흐름 점유 | 작업 분리·병렬 실행 구조 검토 |
| 작업 취소 요청 | 대기·실행 흐름 중단 협의 | 원격 업무까지 자동 취소된 것은 아님 |

[asyncio 공식 문서](https://docs.python.org/3/library/asyncio-task.html)는 coroutine 호출과 스케줄링, thread로 I/O를 옮기는 경우를 구분한다. **동시 진행과 여러 CPU에서의 동시 실행은 다르다.** 처리량이 늘어도 외부 서비스·DB 연결 풀 같은 공유 자원이 새 병목이 될 수 있다.

## 대기열은 부하가 용량에 가까워질 때 급격히 늘 수 있다

### 개념과 작동 원리

서버 처리시간이 평균 10ms라고 해서 평균 응답시간도 항상 10ms인 것은 아니다. 이미 처리 중인 요청이 있으면 앞의 요청을 기다려야 한다. 학습용 M/M/1 모델은 요청이 Poisson 과정으로 도착하고, 처리시간이 지수분포이며, 서버 하나가 일정한 평균 처리율 μ로 처리한다고 가정한다. λ는 평균 도착률이고 안정 상태를 위해 λ\<μ가 필요하다.

이 가정 아래 시스템 안에 머무는 평균 시간은 W=1/(μ−λ)다. 처리율 μ=100회/초, 도착률 λ=50회/초이면 W=0.02초다. 여기에는 평균 처리시간 1/μ=0.01초와 평균 대기시간 0.01초가 포함된다. λ=90회/초로 늘면 W=0.1초가 되어 처리시간 자체는 같아도 대기를 포함한 시간이 커진다. 이용률 ρ=λ/μ가 1에 가까워질수록 여유가 줄어 변동을 흡수하기 어려워진다.

![이론적 대기행렬 모형입니다. 실제 HTTP 서버의 지연시간이나 p95를 측정한 값이 아닙니다.](/figures/C07.svg)

이론적 대기행렬 모형입니다. 실제 HTTP 서버의 지연시간이나 p95를 측정한 값이 아닙니다.

그림은 M/M/1 가정에서 부하와 평균 체류시간의 관계를 보여 준다. 가로축이 ρ라면 1에 다가갈 때 세로축이 급격히 커지는 부분을 읽으면 된다.

이 곡선은 실제 인터넷 전체나 다단계 AI 서비스의 정확한 지연 모델이 아니다. 실제 요청은 여러 서버·배치·캐시·비균등 처리시간을 거치며 독립·지수분포 가정도 깨질 수 있다.

평균 식으로 p95·p99를 그대로 예측할 수도 없다. 여기서 배울 원리는 “처리시간이 그대로여도 대기 때문에 응답이 느려질 수 있다”는 점이다.


### 이용률 95%와 99%의 차이를 계산하기

단일 서버 M/M/1 모형에서 μ=100회/초, 도착률 λ<μ라 하자. 도착 간격과 서비스 시간의 독립 지수분포, 안정 상태 등 모형 가정 아래 시스템 체류 평균은 $W=1/(\mu-\lambda)$다.

| λ | 이용률 λ/μ | 평균 체류 W | 평균 대기 W−1/μ |
|---|---|---|---|
| 50 | 50% | 20ms | 10ms |
| 95 | 95% | 200ms | 190ms |
| 99 | 99% | 1000ms | 990ms |

안정 상태의 평균 시스템 내 요청 수는 Little 관계 L=λW로 연결된다. λ=95이면 19개, λ=99이면 99개다. 평균 처리시간이 같아도 부하가 용량에 가까워지면 대기가 크게 늘 수 있다.

실제 서버는 다중 워커·유한 큐·취소·배치·비지수 처리시간을 가질 수 있다. 위 수치는 **서버 p95·p99 예측값이 아니며 측정 결과도 아니다.** [MIT 대기행렬 교재의 M/M/1 가정](https://web.mit.edu/urban_or_book/www/book/chapter4/4.6.1.html)을 참고한다.

## Timeout과 재시도가 뜻하는 것

### 개념과 작동 원리

Connect timeout은 연결 수립 대기를, read timeout은 데이터를 기다리는 구간을 제한하는 식으로 쓰인다. 라이브러리마다 read timeout이 전체 응답 시간인지 개별 읽기 대기인지 의미가 다를 수 있으므로 문서를 확인해야 한다.

요청 전체 deadline도 별도로 두지 않으면 여러 재시도와 부분 읽기가 합쳐져 생각보다 오래 걸릴 수 있다. 취소 신호가 서버까지 전달되는지와 서버가 실제 작업을 중단하는지도 분리한다.


서버가 DB에 저장을 마쳤지만 응답이 사라지면 클라이언트는 성공 여부를 모른다. Timeout은 “실행되지 않았다”가 아니라 “정해진 시간 안에 결과를 확인하지 못했다”다. 읽기 요청은 다시 보내도 업무 효과가 없을 수 있지만 주문 생성·메일 전송·결제 같은 쓰기는 중복 효과가 생길 수 있다. 멱등 키로 같은 논리 요청을 식별하고 처리 결과를 재사용하는 설계가 필요하다.

재시도에는 횟수·총시간 제한을 두고 backoff로 간격을 늘리며 jitter로 동시에 몰리는 시점을 흩뜨릴 수 있다. 그렇다고 모든 오류를 재시도하지는 않는다. 잘못된 입력·권한 오류는 같은 요청을 반복해도 해결되지 않는다. 서버가 과부하일 때 모든 클라이언트가 즉시 재시도하면 원래 장애를 증폭한다. 네트워크의 불확실성을 제거할 수는 없지만 실패 의미를 명확히 하고 부하를 통제할 수는 있다.

### 재시도 예산과 중복 실행을 따로 제한하기

한 시도 timeout이 2초, 최대 3회 시도, 사이 backoff가 0.5초·1초라면 최대 대기는 단순 합으로 7.5초까지 커질 수 있다. 전체 요청 예산이 3초라면 시도별 timeout만 설정해서는 그 예산을 보장하지 못한다.

| 상황 | 알 수 있는 것 | 다음 설계 질문 |
|---|---|---|
| 연결 수립 실패 | 연결을 완성하지 못함 | 요청 전송 여부·오류 종류 |
| 처리 후 응답 유실 | 클라이언트가 성공을 모름 | 중복 제출을 어떻게 식별하는가 |
| 전체 deadline 만료 | 호출자 대기 예산 소진 | 원격 처리 취소·결과 조회 정책 |
| 여러 계층의 독립 재시도 | 시도 횟수가 곱해질 수 있음 | 재시도 책임을 어디에 둘 것인가 |

같은 업무 키를 받은 요청을 원자적으로 중복 처리하지 않게 하는 서버 계약이 있다면 재시도의 의미를 제어할 수 있다. 키를 붙이기만 하고 저장·동시성 정책이 없다면 보장이 생기지 않는다. HTTP의 멱등성과도 구현 계약을 연결해야 한다. [AWS의 재시도·timeout 설계 문서](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)에서 총 예산·부하·backoff의 관계를 확인할 수 있다.

**복습 문제:** 클라이언트 timeout 뒤 서버 기록을 보니 저장이 성공했다. 같은 생성 요청을 즉시 반복해도 항상 안전한가?

<details><summary>풀이</summary>

아니다. 결과 확인과 중복 실행 방지 계약이 없으면 같은 업무를 두 번 만들 수 있다. timeout은 실패 확정이 아니라 결과 확인 실패일 수 있다. 남은 deadline, 오류 종류, 멱등성·상태 조회 규칙을 보고 재시도 여부를 정한다.

</details>

## 핵심 정리

IP·전송 프로토콜·HTTP는 서로 다른 계층의 문제를 다룬다. TCP는 순서 있는 바이트 전달을 제공하지만 메시지 경계나 업무 성공까지 보장하지 않는다.

HTTP 상태와 TLS 보호는 응용의 정확성과 별개다. 비동기는 대기를 겹치는 도구이며 CPU 병렬성이나 무제한 용량을 뜻하지 않는다.

대기열 때문에 처리시간이 같아도 응답시간은 부하에 따라 크게 달라질 수 있다. Timeout은 결과의 불확실성을 남기므로 재시도에는 멱등성·제한·부하 제어가 필요하다.

지연은 DNS·연결·대기·처리·전송으로 나누고 평균과 꼬리 지연을 함께 관측한다.
