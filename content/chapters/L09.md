## 모델 파일이 곧 서비스는 아니다

노트북에서 모델 정확도 90%를 얻었는데 서버에서는 엉뚱한 예측이 나온다고 하자. 가중치가 같더라도 특성 열 순서가 바뀌었거나, 훈련과 다른 평균으로 표준화했거나, tokenizer·범주 인코더가 달라졌을 수 있다. 서비스는 원본 입력을 읽고 변환해 모델에 넣고 출력을 해석하는 전체 과정이다. 따라서 배포 단위는 가중치 파일 하나가 아니라 필요한 전처리·후처리·설정·버전·입출력 규약을 포함하는 artifact다.

재현성도 한 종류가 아니다. 같은 환경에서 같은 수치를 얻는 것, 다른 환경에서 비슷한 결과를 얻는 것, 다른 사람이 원리를 따라 재구현해 결론을 확인하는 것은 강도가 다르다. seed 고정은 난수 사용의 일부를 통제하지만 데이터 변경·라이브러리 차이·장치별 커널·비결정적 병렬 연산까지 모두 고정하지는 않는다. 무엇을 동일하게 만들고 어떤 차이는 허용했는지 명시해야 재현의 의미가 분명해진다.

## 데이터·학습·평가를 버전으로 연결하기

하나의 실행을 `코드 revision + 데이터 snapshot + 분할 + 설정 + 환경 + 결과`로 생각해 보자. 코드만 보존하면 원본 DB가 바뀌었을 때 같은 데이터로 훈련할 수 없다. 데이터만 보존하면 어떤 전처리·특성 선택을 썼는지 알 수 없다. 모델 registry나 실험 추적 도구의 가치는 이 연결을 찾아갈 수 있게 하는 데 있다. 특정 도구를 설치했다는 사실보다 연결 정보가 실제로 남는지가 중요하다.

훈련 파이프라인은 보통 데이터 검증·전처리·학습·평가·등록 단계로 나눌 수 있다. 단계의 입력·출력을 명확히 하면 일부만 다시 실행하거나 실패 지점을 찾기 쉽다. 그러나 무조건 모든 단계를 복잡한 오케스트레이터에 올릴 필요는 없다. 작은 프로젝트는 재현 가능한 스크립트와 명세에서 시작할 수 있다. 자동화의 목적은 더 많은 도구가 아니라 같은 조건의 작업을 반복 가능하게 만드는 것이다.

데이터 계약은 열 이름·타입·단위·결측 허용·키의 유일성 같은 입력 가정을 명시한다. 값이 cm에서 m로 바뀌어도 float 타입은 맞으므로 타입 검사만으로 충분하지 않다. 범위·단위·분포·업무 규칙까지 구분해 확인한다. 학습과 서빙의 전처리가 다른 training-serving skew는 모델 코드가 맞아도 오류를 만들 수 있어 동일 변환 artifact를 재사용하거나 일관성을 검증한다.

## Batch 추론과 온라인 추론

매일 밤 전체 고객의 점수를 계산해 저장하면 batch inference다. 사용자 요청을 받아 즉시 계산하면 online inference다. Batch는 많은 자료를 묶어 효율적으로 처리하고 일정을 관리하기 쉬울 수 있으며, online은 최신 입력과 빠른 응답이 중요하다. 모든 업무가 실시간이어야 하는 것도, 모델이 작다고 운영 문제가 없는 것도 아니다.

온라인 요청에는 입력 parsing·schema 검증·전처리·모델 실행·후처리·직렬화·네트워크 전달이 포함된다. 모델 서버는 잘못된 입력을 성공 응답처럼 처리하지 않아야 하고, 오류가 나면 상태·원인을 구분해 반환해야 한다. Warm-up은 커널 준비·컴파일·메모리 확보 등의 최초 비용을 미리 발생시키는 방식이다. Cold-start 지연과 정상 운영 지연을 같은 표본으로 섞으면 어떤 현상을 개선해야 할지 흐려질 수 있다.

## 지연시간과 처리량을 구분하기

한 요청이 200ms 걸리는 상황에서 모델 실행이 20ms이고 나머지 대기·네트워크·전처리가 180ms라고 하자. 모델 실행을 두 배 빠르게 해 10ms로 줄여도 전체는 190ms다. 전체 개선률은 (200−190)/200=5%이고 속도 향상 비는 200/190≈1.053배다. 모델을 무한히 빠르게 만들어도 다른 비용 180ms가 남아 최대 속도 향상은 200/180≈1.111배다. 이는 Amdahl의 법칙이 주는 직관과 같다. 측정하지 않은 부분을 가정으로 제거해서는 안 된다.

Latency는 요청 하나가 걸린 시간이고 throughput은 단위 시간에 처리한 작업 수다. batch를 모으면 장치 활용률이 올라 throughput이 좋아질 수 있지만, 입력이 모일 때까지 기다리는 시간이 요청 지연에 추가될 수 있다. 동시 요청 수를 늘리면 처음에는 장치가 더 잘 활용되다가 자원이 포화되며 대기열이 늘어날 수 있다. 그러므로 한 샘플 실행 속도와 서비스 부하 상태의 사용자 지연은 다르다.

지연 표본이 \[10,10,10,10,100\]ms이면 평균은 28ms, 중앙값은 10ms다. 평균만 보면 대부분의 경험과 일부 매우 느린 경험을 동시에 놓친다. p95·p99는 꼬리 지연을 요약하지만 표본 수가 적으면 추정이 불안정하고 구현별 percentile 보간 규약도 다를 수 있다. 부하·입력 길이·성공/실패 포함 기준·warm-up 제외 여부와 함께 보고한다. GPU 연산은 비동기로 예약될 수 있으므로 CPU에서 함수 호출 시간만 재면 실제 완료 시간을 놓칠 수 있다. 장치 동기화나 적절한 장치 타이머가 필요하다.

## 가중치·활성값·학습 상태·KV cache는 다른 메모리다

추론에 필요한 메모리를 가중치 크기로만 계산하면 큰 오차가 날 수 있다. 가중치는 모델의 저장된 파라미터이고, 활성값은 입력을 처리하며 생긴 중간 텐서다. 학습에서는 역전파를 위해 일부 중간값을 보존하며 gradient·optimizer 상태도 필요하다. 자기회귀 생성에서는 과거 key·value의 KV cache가 별도로 증가한다. 임시 workspace·통신 buffer·allocator 예약 공간도 실제 장치 사용량에 영향을 준다.

70억 파라미터를 FP16, 즉 원소당 2byte로 저장하는 이상적인 가중치 크기는 7×10⁹×2=14×10⁹byte=14GB다. 1GiB=2³⁰byte로 나누면 약 13.04GiB다. 8bit 표현은 이상적으로 7GB≈6.52GiB, packed 4bit는 3.5GB≈3.26GiB지만 scale·그룹 metadata·일부 높은 정밀도 가중치 등 추가 공간이 있을 수 있다. ‘7B 4bit’라는 이름만으로 정확한 최대 메모리를 정할 수는 없다.

L07의 예시인 32층·KV head 8개·head 차원 128·FP16을 다시 쓰자. 토큰·시퀀스당 cache는 2×32×8×128×2=131,072byte다. 길이 8192이면 1GiB, batch 4이면 4GiB다. 같은 7B 모델의 FP16 가중치 약 13.04GiB에 이 cache를 더하면 단순 합만 약 17.04GiB가 된다. 아직 활성값·workspace·예약 공간은 더하지 않았다. 16GiB 장치에 가중치만 들어갈 것 같다는 계산으로 동시 요청까지 가능하다고 말할 수 없는 이유다.

실제 GPU 요구량은 활성값·workspace·통신·메모리 단편화 등을 더해 측정해야 합니다. 특정 7B 모델의 실행 가능성을 보장하지 않습니다.

그림에서 가중치 정밀도별 저장량과 오른쪽 KV cache 증가분을 구분해 읽자. 오른쪽 그림은 길이 4096을 고정한 계산으로, 직전 본문의 길이 8192 예제와 다르다. 길이 4096이면 시퀀스당 cache가 0.5GiB이므로 batch 4에서 2GiB이고, FP16 가중치 약 13.04GiB를 더한 값은 약 15.04GiB다. 본문의 8192·batch 4에서는 cache가 4GiB여서 단순 합이 약 17.04GiB가 된다. 가중치 정밀도를 낮추면 가중치 부분은 작아지지만, cache를 같은 FP16으로 유지한다면 cache 부분은 자동으로 4분의 1이 되지 않는다. 입력 길이·batch를 늘리면 cache가 커지고, 학습 모드에서는 그림에 없는 gradient·optimizer·역전파 저장 텐서가 추가된다. 이 막대는 7B 가중치와 특정 구조의 KV 식을 더한 이론적 예시이지 실제 모델의 peak GPU 메모리 측정 결과가 아니다.

Mixed precision은 모든 값을 무작정 낮은 정밀도로 바꾸는 것이 아니라, 적절한 연산·저장 형식을 섞어 속도·메모리·수치 안정성을 조절한다. 작은 gradient가 표현 범위 밖으로 사라지는 문제 등에 loss scaling을 활용할 수 있고, FP16·BF16의 지수 범위·유효숫자 차이도 영향을 준다. Activation checkpointing은 일부 중간값 저장을 줄이고 역전파 때 재계산하여 메모리와 연산을 교환한다. Gradient accumulation은 여러 작은 batch의 gradient를 모아 더 큰 유효 batch처럼 갱신하지만 손실 정규화·갱신 빈도·정규화 계층 동작까지 완전히 같은 것은 아닐 수 있다.

## 분산 학습: 계산을 나누면 통신이 생긴다

Data parallel에서는 각 장치가 모델 사본과 서로 다른 batch를 갖고 gradient를 계산한 뒤 합치거나 평균한다. 전체 batch가 같고 계산·평균 규칙을 맞춘다면 단일 장치의 큰 batch와 연결해 이해할 수 있다. 다만 난수·동기화·정규화·수치 연산 순서 차이는 남을 수 있다. 각 장치가 학습한 서로 다른 모델의 최종 가중치를 아무 때나 평균하는 것과는 다르다.

장치 네 개가 각각 gradient g₁,…,g₄를 계산하고 샘플 수가 같으면 평균 g=(g₁+g₂+g₃+g₄)/4로 갱신할 수 있다. 장치별 샘플 수가 다르면 단순 평균이 전체 표본 평균과 다를 수 있어 가중치를 확인한다. all-reduce 같은 통신은 각 장치에 필요한 합을 전달한다. 장치 수를 늘려 계산을 나눠도 통신·동기화·입력 공급·느린 worker가 병목이 될 수 있다.

Model parallel은 모델의 다른 부분을 장치에 나누고, tensor parallel은 큰 연산을 분할하며, pipeline parallel은 계층 묶음 사이로 입력을 흘린다. Optimizer·gradient·parameter를 분할 저장하는 방식도 있다. 어느 방법이 필요한지는 ‘모델이 한 장치에 들어가는가’, ‘통신 비용이 어떤가’, ‘어떤 부분이 병목인가’에 달려 있다. 분산은 단일 장치의 잘못된 학습 코드를 자동으로 고치지 않는다.

## 테스트·배포·모니터링은 서로 다른 실패를 찾는다

단위 테스트는 작은 전처리·연산이 기대대로 동작하는지 확인한다. 계약 테스트는 입력·출력 schema나 artifact 호환성을 확인하고, 통합 테스트는 실제 구성 요소를 연결한 흐름을 본다. 모델 품질 평가는 고정한 데이터·지표에서 성능을 확인한다. 프로그램이 예외 없이 실행된다는 테스트와 예측이 유용하다는 평가는 다른 것이다. CI에서 매번 대형 모델을 새로 학습하기보다 작은 결정적 검사를 두고, 비싼 품질 평가를 적절한 주기로 구분할 수 있다.

새 모델을 일부 트래픽에 적용하는 canary 배포는 전체 영향 전에 운영 신호를 확인하는 방법이다. Shadow 실행은 실제 응답을 바꾸지 않고 새 모델의 예측을 비교하는 데 쓸 수 있다. Rollback을 하려면 이전 모델뿐 아니라 전처리·schema·환경도 되돌릴 수 있어야 한다. 새 모델이 만든 DB 변화처럼 외부 부작용이 있다면 가중치만 되돌리는 것으로 모든 문제가 복구되지는 않는다.

운영에서는 입력 누락·오류율·지연·처리량·자원·비용과 모델 품질을 함께 본다. 입력 분포 변화인 data drift가 탐지됐다고 반드시 성능 저하가 확정되는 것은 아니다. 모델이 불변으로 처리하는 변화일 수도 있다. 반대로 입력 분포가 비슷해 보여도 x와 y의 관계가 달라질 수 있다. 정답이 늦게 들어오는 문제에서는 먼저 서비스·데이터 신호를 보고, 정답이 확보되면 품질을 확인한다. ‘변화 탐지 → 자동 재학습 → 즉시 배포’를 검증 없이 연결하지 않는다.

## 프레임워크 내부를 이해하면 최적화의 근거가 생긴다

PyTorch 같은 프레임워크는 텐서 저장·stride·연산 dispatch·자동미분·장치별 kernel을 연결한다. 텐서의 모양이 같아도 메모리 배치와 연속성이 다르면 연산 비용이 달라질 수 있다. transpose가 새로운 수치를 모두 복사하는지, 같은 저장소를 다른 stride로 보는지 확인하면 불필요한 복사·메모리 증가를 이해할 수 있다. GPU kernel의 tiling·메모리 접근 결합은 CS의 캐시·병렬 구조와 이어진다.

작은 autodiff·NDArray·CPU/CUDA backend를 직접 만드는 심화 과정은 ‘왜 이 연산이 느린가’를 원리로 추적하게 한다. 모든 AI 서비스 개발자가 처음부터 프레임워크 전체를 구현해야 하는 것은 아니지만, 측정한 병목을 이해하는 데 필요한 깊이까지 내려갈 수 있어야 한다. 최적화의 출발점은 유행하는 기술 목록이 아니라 올바른 결과를 보존하는 측정과 비교다.

## 핵심 정리

모델 서비스는 가중치와 전처리·환경·입출력 계약을 함께 실행하는 시스템이다. 재현성은 seed 하나가 아니라 코드·데이터·설정·환경의 연결을 필요로 한다. 지연과 처리량은 다른 지표이며 큰 병목을 측정해야 전체 개선을 해석할 수 있다. 가중치·활성값·gradient·optimizer·KV cache는 서로 다른 메모리 항목이다. 분산 학습은 계산을 나누는 대신 통신·동기화 비용을 만든다. 테스트·품질 평가·운영 감시는 다른 실패를 찾으므로 모두의 역할을 구분해야 한다.

## 복습 문제와 풀이

**1. 전체 지연 100ms 중 모델이 40ms다. 모델만 4배 빠르게 하면 전체 지연과 속도 향상은?**

<details>
<summary>풀이 보기</summary>

나머지 비용은 60ms다. 모델 비용은 40/4=10ms이므로 전체는 70ms다. 속도 향상은 100/70≈1.429배이며 지연 감소율은 30%다. 모델의 4배와 전체 시스템의 4배는 다르다.

</details>

**2. 7B 가중치를 이상적인 4bit로 저장하고, 본문 구조의 FP16 cache로 길이 8192·batch 2를 처리할 때 가중치+cache만의 대략 GiB는?**

<details>
<summary>풀이 보기</summary>

가중치는 7×10⁹×0.5byte=3.5GB≈3.26GiB다. cache는 시퀀스당 1GiB이므로 두 개가 2GiB다. 단순 합은 약 5.26GiB다. 양자화 metadata·활성값·workspace·예약 공간이 제외됐으므로 장치 요구량의 완전한 추정은 아니다.

</details>

**3. 입력 분포가 바뀌었다는 경고가 떴다. 성능 저하와 즉시 재배포를 결론 내려도 되는가?**

<details>
<summary>풀이 보기</summary>

아니다. 데이터 오류·수집 변경·실제 모집단 변화인지 확인하고 가능한 정답·하위 집단 성능과 연결해야 한다. 후보 모델은 별도 평가 후 배포하고 운영 영향과 복구 경로를 확인한다. 변화 신호와 조치의 타당성은 별도 판단이다.

</details>
