# 자료구조는 저장 방식과 연산의 약속이다

문서 100만 개의 ID를 보관한다고 하자. “ID가 있는지 확인한다”, “시간순으로 가장 오래된 ID를 뺀다”, “우선순위가 가장 높은 ID를 고른다”는 서로 다른 요청이다.

모두 같은 리스트로 구현할 수 있지만 필요한 연산 비용은 크게 달라진다. 자료구조를 선택한다는 것은 데이터를 어떻게 저장하고, 어떤 연산을 빠르게 하며, 그 대가로 무엇을 부담할지 정하는 일이다.

먼저 자주 하는 연산과 보장해야 할 순서를 적은 뒤 구조를 고르는 것이 출발점이다.


## 추상 자료형과 복잡도

### 먼저 구분할 세 가지

| 질문 | 개념 | 예 |
| --- | --- | --- |
| 무엇을 할 수 있어야 하나? | **추상 자료형** | 맵의 저장·조회·삭제 |
| 어떻게 저장하고 처리하나? | **자료구조** | 해시 테이블, 균형 탐색 트리 |
| 입력이 커지면 연산량이 어떻게 늘어나나? | **복잡도** | 평균 조회 O(1), 최악 조회 O(n) |

**같은 맵 인터페이스라도 구현이 다르면 성능과 순서 보장이 다르다.** 기능 이름만 보고 비용을 결정하면 안 된다.

### 평균·최악·분할상환을 읽는 순서

1. **연산 하나를 고른다.** 예: 배열 끝에 원소 추가하기.
2. **한 번의 최악 비용을 묻는다.** 용량이 꽉 찬 순간에는 n개를 옮기므로 O(n)이다.
3. **연산열 전체를 묻는다.** 용량을 일정 배수로 늘리면 n번 추가의 총비용은 O(n)이어서 한 번당 분할상환 O(1)이다.
4. **입력에 대한 확률 가정을 따로 확인한다.** 해시 키가 잘 분산된다는 가정 아래의 기대 비용과, 확률 가정 없이 연산열을 나누는 분할상환 분석은 다른 질문이다.

| 표현 | 무엇을 고정하고 무엇을 비교하나? | 흔한 오해 |
| --- | --- | --- |
| 최악 O(n) | 허용된 입력 중 가장 비싼 경우 | 매번 n번 걸린다는 뜻은 아니다. |
| 기대 O(1) | 명시한 확률 가정 아래 평균 비용 | 모든 입력에 대한 보장은 아니다. |
| 분할상환 O(1) | 여러 연산의 총비용을 연산 수로 나눔 | 모든 개별 연산의 지연이 일정하다는 뜻은 아니다. |

### 입력 크기를 먼저 정의하기

- 정수 키 n개라면 n이 항목 수일 수 있다.
- 문자열 키라면 **항목 수 n과 문자열 길이 L을 구분**해야 한다.
- 그래프라면 정점 수 V와 간선 수 E를 함께 쓴다.
- 실제 실행시간은 이 증가율에 상수·캐시·객체 크기 등의 영향이 더해진다.

### 원리와 배경 설명

스택·큐·집합·맵은 사용할 수 있는 연산과 의미를 정하는 추상 자료형이다. 예를 들어 맵은 키에 대응하는 값을 저장·조회·삭제하는 약속이다. 맵을 해시 테이블로 만들 수도, 균형 탐색 트리로 만들 수도 있다. 사용자는 같은 조회 연산을 호출해도 내부 저장 방식과 정렬 순서·최악 비용이 달라진다. 인터페이스의 의미와 구현의 성질을 분리해야 라이브러리 선택을 정확히 할 수 있다.

시간복잡도는 입력 크기 n이 커질 때 일이 어떻게 증가하는지 나타낸다. O(1)은 n에 비례해 늘지 않는다는 뜻이지 실제로 한 번의 CPU 명령만 실행한다는 뜻이 아니다.

O(n)은 원소 수에 비례하는 일을 하고, O(log n)은 후보를 일정 비율씩 줄이는 과정에서 자주 나타난다. 엄밀하게 O는 점근적 상한이고, 위아래가 같은 차수로 묶인다는 것을 명시할 때는 Θ를 쓴다.

예를 들어 항상 3n+2번의 기본 연산을 하면 Θ(n)이며 O(n²)라는 느슨한 상한도 논리적으로 참이다. 일반적인 설명에서 “O(n)”이라고 말할 때는 유용한 가장 타이트한 수준을 의도하는 경우가 많으므로 상한과 정확한 증가 수준을 구분한다.

실제 시간에는 상수, 원소 처리 비용, 메모리 접근, 언어·컴파일러가 영향을 준다.


![이론적 성장 함수를 그렸으며 실제 런타임 벤치마크가 아닙니다. 해시 테이블의 최악 시간은 구현과 가정에 따라 선형일 수 있습니다.](/figures/C03.svg)

이론적 성장 함수를 그렸으며 실제 런타임 벤치마크가 아닙니다. 해시 테이블의 최악 시간은 구현과 가정에 따라 선형일 수 있습니다.

위 곡선은 n, log₂n, n log₂n, n² 같은 **가정한 연산 수의 증가 형태**를 비교하는 그림이다. 세로축을 실제 초 단위로 읽으면 안 된다. 작은 입력에서 어떤 구현이 더 빠른지는 이 그림만으로 알 수 없지만 n이 커질 때 제곱 증가가 얼마나 빨리 부담이 되는지는 볼 수 있다. 같은 알고리즘도 평균·최악·분할상환 중 무엇을 표시했는지 확인해야 한다.

## 배열: 위치를 계산해서 접근한다

### 연산별 비용을 한눈에

| 연산 | 일반적인 동적 배열의 비용 | 이유 |
| --- | --- | --- |
| 인덱스로 접근 | O(1) | 주소를 계산한다. |
| 값이 있는지 검색 | O(n) | 정렬 등 추가 조건이 없으면 순회한다. |
| 끝에 추가 | 분할상환 O(1), 한 번의 최악 O(n) | 가끔 확장과 복사가 필요하다. |
| 가운데 삽입·삭제 | 최악 O(n) | 순서를 유지하려면 뒤 원소를 이동한다. |

### 직접 세어 보는 분할상환

용량이 1인 빈 배열에서 시작해, 꽉 찰 때마다 **용량을 두 배로 늘린다**고 가정하자.

| 추가할 원소 번호 | 추가 전 상태 | 추가 작업 |
| --- | --- | --- |
| 1 | 용량 1, 원소 0 | 새 원소 하나 저장 |
| 2 | 용량 1, 원소 1 | 기존 1개 복사 후 저장 |
| 3 | 용량 2, 원소 2 | 기존 2개 복사 후 저장 |
| 4 | 용량 4, 원소 3 | 새 원소 하나 저장 |
| 5 | 용량 4, 원소 4 | 기존 4개 복사 후 저장 |
| 6~8 | 용량 8에 여유 있음 | 매번 새 원소 하나 저장 |

8번 추가하면서 새 값을 쓴 횟수는 8번, 기존 값을 옮긴 횟수는 `1+2+4=7`번이다. 합은 15번이다. 이 예에서 한 번당 평균 작업량은 `15/8`이며, n이 커져도 일정한 상수 범위로 묶인다.

**매번 용량을 1만 늘리면 이 결론이 달라진다.** 복사량이 `1+2+…+(n−1)`이 되어 총 O(n²)이 될 수 있다. 분할상환 O(1)은 확장 정책까지 포함한 주장이다.

### 메모리에서 확인할 것

- **길이:** 실제 원소 수.
- **용량:** 재할당 없이 저장할 수 있는 원소 수.
- **저장 대상:** 값 자체인지, 다른 객체를 가리키는 참조인지.
- **지역성:** 이웃한 원소를 함께 읽는 작업은 연속 저장의 이점을 받을 수 있다.

### 원리와 배경 설명

고정 크기 원소가 연속해서 저장된 배열에서는 i번째 원소의 위치를 시작 주소+i×원소 크기로 계산할 수 있다. 그래서 유효 인덱스의 접근은 O(1)이다. 반면 중간에 원소를 끼워 넣으면서 순서를 보존하려면 뒤 원소를 밀어야 한다. `[10,20,30,40]`의 인덱스 1에 15를 넣는다면 40,30,20을 한 칸씩 옮긴 뒤 15를 저장한다. 필요한 이동량은 위치에 따라 달라지고 최악에는 O(n)이다.

동적 배열은 현재 원소 수와 확보한 용량을 구분한다. 공간이 남으면 끝에 쓰기만 하면 되지만 용량이 꽉 차면 더 큰 영역을 확보하고 기존 원소를 옮겨야 한다.

용량을 1,2,4,8처럼 두 배로 늘린다고 가정하면 비싼 복사 작업이 가끔 생긴다. n번 append 동안 옮기는 양의 합은 1+2+4+…로 총 O(n)이므로 한 연산당 분할상환 비용은 O(1)이다. 매 append가 상수 시간이라는 말이 아니라 **연산열 전체 비용을 나누었을 때** 그렇다는 뜻이다.


CPython의 일반적인 list는 객체 참조의 동적 배열이다. 리스트의 참조 슬롯이 연속하다고 해서 각 Python 정수 객체의 내용도 C 정수 배열처럼 연속이라는 뜻은 아니다. 숫자 대량 연산에 NumPy의 고정 dtype 배열을 쓰면 저장 밀도와 연속 연산 방식이 달라지는 이유가 여기에 있다. 두 컨테이너의 원소 수만 비교해서 실제 메모리 사용량이 같다고 생각하면 안 된다.

## 연결 리스트: 다음 주소를 따라간다

### O(1) 삽입이라는 말을 해체하기

`10 → 20 → 30`에서 20 뒤에 25를 넣는다고 하자.

1. **20의 노드를 찾는다.** 머리 노드만 주어졌다면 링크를 따라간다. 일반적으로 O(n)이다.
2. 새 노드의 다음 링크를 30의 노드로 연결한다.
3. 20의 다음 링크를 새 노드로 바꾼다.

2~3번의 **연결 수정만** O(1)이다. 1번을 포함한 전체 요청이 항상 O(1)인 것은 아니다.

| 요청에 이미 주어진 정보 | 추가로 해야 할 일 | 전체 비용 |
| --- | --- | --- |
| 삽입 위치의 앞 노드 | 링크 두 개 수정 | O(1) |
| 머리 노드와 인덱스 i | i번째 위치까지 이동 후 수정 | 최악 O(n) |
| 머리 노드와 찾을 값 | 값을 비교하며 탐색 후 수정 | 최악 O(n) |

### 단일 연결과 이중 연결

| 구조 | 노드에 저장하는 링크 | 삭제할 때 주의점 |
| --- | --- | --- |
| 단일 연결 리스트 | 다음 노드 | 일반적으로 앞 노드를 알아야 연결을 끊을 수 있다. |
| 이중 연결 리스트 | 앞 노드와 다음 노드 | 삭제할 노드를 알면 양쪽 링크를 수정할 수 있지만 링크 공간이 더 든다. |

끝에 추가하는 작업도 **꼬리 참조를 유지하는지**에 따라 비용이 달라진다. 머리 참조만 있으면 끝까지 걸어가야 한다.

### 원리와 배경 설명

연결 리스트의 각 노드는 값과 다음 노드를 가리키는 참조를 가진다. 노드들이 메모리에서 이웃할 필요는 없다.

첫 노드에서 출발해 next를 반복해서 따라가면 전체를 읽을 수 있다. i번째 노드를 바로 계산해 찾을 수 없으므로 일반적인 인덱스 접근은 O(n)이다. 대신 삽입 위치의 앞 노드 p를 이미 알고 있다면 새 노드의 next를 `p.next`로 연결하고 `p.next`를 새 노드로 바꾸는 상수 번의 수정으로 삽입한다.


```py
class Node:
    def __init__(self, value, next=None):
        self.value = value
        self.next = next

head = Node(10, Node(30))
new = Node(20, head.next)
head.next = new
```

처음에는 10 노드가 30 노드를 가리킨다. 새 노드는 30을 가리키게 만들고, 마지막 줄에서 10이 20을 가리키게 한다. 결과 순서는 10,20,30이다. 연결을 바꾸는 순서가 중요하다. 기존 다음 노드를 잃어버린 뒤 연결하려 하면 뒤쪽 목록에 도달하지 못할 수 있다. 노드 추가 자체의 O(1) 비용과 위치를 찾는 O(n) 비용을 합쳐 생각해야 한다.

이중 연결 리스트는 이전 노드 참조도 가져 양방향 이동과 주어진 노드 삭제에 유리하다. 대신 노드당 저장 공간과 연결 수정 수가 늘어난다. 연결 리스트는 “삽입이 많으면 항상 더 빠르다”는 도구가 아니다. 작은 노드를 따로 할당하는 비용, 캐시 지역성, 위치 탐색 방식에 따라 연속 배열이 더 빠를 수 있다. 빅오는 저장 구조의 물리적 차이를 모두 표현하지 않는다.

## 스택과 큐: 꺼내는 순서를 제한한다

### 같은 입력, 다른 출력 순서

| 순서 | 스택 | 큐 |
| --- | --- | --- |
| A, B, C를 차례로 넣기 | 아래 A, 위 C | 앞 A, 뒤 C |
| 첫 번째 꺼내기 | C | A |
| 두 번째 꺼내기 | B | B |
| 세 번째 꺼내기 | A | C |

- **스택:** 나중에 시작한 일을 먼저 마무리할 때 사용한다. 예: 중첩 괄호, 되돌리기, DFS.
- **큐:** 먼저 기다린 일을 먼저 처리할 때 사용한다. 예: 작업 대기열, BFS의 같은 거리 탐색.
- **Deque:** 양 끝에서 추가·삭제할 때 사용한다. 가운데 임의 위치를 빠르게 접근한다는 뜻은 아니다.

### BFS에서 큐 구현이 중요한 이유

1. 각 정점을 큐에 한 번 넣고 한 번 꺼내도록 방문 표시를 한다.
2. 인접 리스트를 쓰면 모든 정점과 간선을 확인하는 양은 O(V+E)다.
3. 그런데 큐의 맨 앞 삭제가 매번 뒤 원소를 이동시키면, 자료구조 조작 비용이 추가된다.
4. Python에서 양 끝 연산이 필요한 큐는 보통 `collections.deque`를 사용한다. `list.pop(0)`은 뒤 원소 이동이 필요하다.

**알고리즘의 복잡도는 사용한 컨테이너의 연산 비용까지 포함해야 한다.**

### 원리와 배경 설명

스택은 가장 나중에 넣은 원소를 먼저 꺼내는 LIFO 구조다. push로 넣고 pop으로 꺼낸다. 함수 호출 상태, 괄호 검사, DFS의 미완료 작업을 다룰 때 이런 순서가 맞는다.

동적 배열 끝을 사용하면 push는 분할상환 O(1), pop은 보통 O(1)로 구현할 수 있다. 재귀 호출도 실행 중인 함수가 끝나야 호출자로 돌아가는 중첩 구조를 가지므로 스택이라는 개념과 연결된다.

자료구조로 직접 만든 스택과 시스템의 호출 스택은 같은 원리를 공유하지만 같은 저장 대상은 아니다.


큐는 먼저 들어온 원소를 먼저 꺼내는 FIFO 구조다. 작업 대기열과 BFS에서 사용한다. 배열의 맨 앞을 매번 삭제하면서 나머지를 이동하면 dequeue가 O(n)이 된다. 앞 원소를 지우는 대신 읽을 시작 위치를 이동하는 방법을 쓰면 이동을 피할 수 있다. Python의 `list.pop(0)` 대신 `collections.deque.popleft()`를 쓰는 대표적인 이유다.

원형 버퍼는 고정 크기 배열의 끝에 도달하면 인덱스를 0으로 되돌려 남은 공간을 재사용한다. 용량 4에서 head=2, size=2라면 원소는 인덱스 2와 3에 있다고 하자.

다음 삽입 위치는 (head+size)%4=0이다. 그 위치에 원소를 하나 넣으면 size는 3이 된다.

이어서 앞 원소를 하나 꺼내면 head는 3이 되고 size는 다시 2가 된다. 배열의 실제 위치와 논리적 순서가 다르지만 head·size로 대응을 계산한다. empty와 full을 구분하려면 size를 저장하거나 슬롯 하나를 비우는 등 명확한 규칙이 필요하다.


Deque는 양쪽 끝에서 넣고 뺄 수 있는 구조다. 이중 연결 리스트나 원형 배열 등으로 구현할 수 있다. Python deque도 구체적인 블록 기반 구현을 가지며 단순한 한 줄 배열과 동일하지 않다. 중요한 것은 양끝 연산에 적합하다는 의미와 임의 인덱스 탐색이 배열처럼 항상 O(1)은 아니라는 성질이다.

## 해시 테이블: 키를 저장 위치의 후보로 바꾼다

### 조회는 세 단계를 거친다

**키 → 해시값 → 버킷 후보 → 실제 키 비교** 순서다. 해시값만 같다고 같은 키로 판정하지 않는다.

버킷이 4개이고 교육용 인덱스 함수를 `key % 4`로 정하면 다음과 같다.

| 키 | 계산 | 버킷 |
| --- | --- | --- |
| 10 | 10 % 4 | 2 |
| 14 | 14 % 4 | 2 |
| 18 | 18 % 4 | 2 |

14를 찾을 때는 먼저 2번 버킷을 고르고, 그 안에서 **실제 키가 14인지 비교**한다. 버킷 하나를 고르는 계산과 버킷 안의 검색은 구분해야 한다.

### 충돌 처리 두 방식

| 방식 | 충돌한 항목을 두는 곳 | 삭제할 때의 핵심 |
| --- | --- | --- |
| 체이닝 | 같은 버킷의 별도 목록 등 | 해당 목록에서 키를 찾아 제거 |
| 개방 주소법 | 같은 테이블의 다른 슬롯 | 탐사 경로가 끊어지지 않게 삭제 표식·재배치 등을 사용 |

**개방 주소법의 삭제 예제**

1. 10이 2번 슬롯을 사용한다.
2. 14가 충돌해 다음 슬롯인 3번에 저장된다.
3. 10을 삭제하며 2번 슬롯을 단순히 ‘한 번도 사용하지 않은 빈칸’으로 바꾼다.
4. 14 조회가 2번의 빈칸에서 종료되면, 실제로 3번에 있는 14를 놓친다.

따라서 **한 번도 사용하지 않은 빈칸과, 항목이 삭제된 칸은 같은 상태가 아니다.**

### 평균 O(1)에 붙는 조건

- **적재율 α:** 항목 수 n을 버킷 수 m으로 나눈 `n/m`.
- **분산 조건:** 한 버킷에 지나치게 몰리지 않아야 한다.
- **확장 조건:** 항목이 늘면 용량도 조절해 적재율을 관리해야 한다.
- **키 비용 조건:** 해시 계산과 동등성 비교를 상수 비용으로 볼 수 있는지 확인해야 한다.

체이닝에서는 적절한 균등 분산 가정 아래 기대 조회 비용을 O(1+α)로 해석할 수 있다. α를 상수 수준으로 관리하면 기대 O(1)이다. 그러나 모두 같은 버킷에 몰리는 최악에는 O(n)이 될 수 있다.

길이 L인 문자열의 해시를 처음 계산하려면 문자열을 읽는 비용이 추가될 수 있다. **n에 대한 O(1)과 L까지 포함한 O(1)은 같은 주장이 아니다.**

### 키를 바꾸면 왜 문제가 생기나?

키로 넣었을 때와 찾을 때의 해시·동등성 기준이 달라지면, 저장한 위치와 조회할 후보 위치가 달라질 수 있다. 해시 테이블의 키는 이 기준이 안정적이어야 한다.

### 원리와 배경 설명

맵에서 문자열 키를 조회하려면 모든 키를 순회할 수도 있지만 원소가 많아지면 비싸다. 해시 테이블은 키를 해시값으로 변환하고 이를 버킷 위치에 연결한다. 용량이 4인 간단한 예에서 `key % 4`를 쓴다면 10,14,18은 모두 위치 2로 간다. 이런 충돌은 해시 함수의 출력 범위가 제한되어 있으므로 피할 수 없는 가능성이다. 충돌한 키를 어떻게 구분하고 찾아갈지가 자료구조 설계의 일부다.

Chaining은 각 버킷에 여러 항목의 목록을 두고 실제 키를 비교한다. Open addressing은 테이블 안의 다른 슬롯을 탐사한다. 후자는 빈 슬롯과 삭제한 슬롯의 의미를 구별해야 탐색이 중간에 잘못 멈추지 않는다. 예를 들어 충돌 때문에 뒤 슬롯에 저장한 키를 찾는 도중 앞 슬롯이 삭제되었다고 곧바로 실패를 반환하면 그 키를 놓친다. 삭제 표식이나 적절한 재배치가 필요한 이유다.

적재율 α는 저장한 항목 수를 테이블 용량으로 나눈 값이다. 적재율이 높아지면 충돌과 탐사 비용이 커질 수 있어 용량을 늘리고 위치를 다시 계산한다.

좋은 분산과 적절한 적재율 등 조건 아래 평균 조회·삽입을 O(1)로 설명하지만 최악에는 많은 키를 확인할 수 있다. resize 한 번은 전체 항목을 옮기는 O(n) 작업일 수 있다. 긴 문자열의 해시 계산과 동등성 비교 비용까지 포함하면 “키가 아무리 길어도 언제나 완전히 일정한 시간”은 아니다.


키의 동등성과 해시 일관성도 중요하다. 같다고 판정되는 두 키는 같은 해시값을 가져야 해시 테이블에서 올바르게 찾을 수 있다. 키로 저장한 뒤 해시·동등성 기준이 바뀌는 가변 객체는 문제를 일으킬 수 있다. Python이 list를 기본적으로 dict 키로 허용하지 않는 이유를 이런 관점에서 이해할 수 있다.

## 트리와 이진 탐색 트리: 계층과 순서를 이용한다

### 이름이 비슷해도 보장은 다르다

| 구조 | 유지하는 규칙 | 탐색에 필요한 핵심 조건 |
| --- | --- | --- |
| 이진 트리 | 자식이 최대 두 개 | 키의 정렬 순서는 보장하지 않는다. |
| 이진 탐색 트리 | 왼쪽·오른쪽 키에 정렬 규칙 | 연산 비용은 높이 h에 비례한다. |
| 균형 탐색 트리 | 탐색 규칙과 높이 균형 | 높이를 O(log n)으로 제어한다. |
| 힙 | 부모·자식의 우선순위 규칙 | 루트의 최솟값/최댓값에 특화된다. |

### 정렬된 입력을 그대로 넣어 보기

1. 빈 BST에 1을 넣는다.
2. 2는 1보다 크므로 오른쪽 자식이 된다.
3. 3은 1보다 크고 2보다 크므로 다시 오른쪽으로 내려간다.
4. 이 과정을 계속하면 트리라기보다 길이 n의 사슬이 된다.

따라서 **BST라는 이름만으로 O(log n)을 보장할 수 없다.** 균형 유지 여부까지 봐야 한다.

### 문자열 접두사에는 Trie

`car`, `cat`을 저장하면 처음 두 글자 `c → a`의 경로를 공유하고 마지막 글자에서 갈라질 수 있다.

- 검색은 문자열의 글자를 한 글자씩 따라간다.
- 자식 선택을 상수 비용으로 처리한다는 가정 아래 길이 L인 문자열 검색은 O(L)이다.
- 중간 노드가 존재하는 것과 단어가 끝나는 것은 다르므로 **단어 종료 표시**가 필요하다.
- 빠른 접두사 탐색을 얻는 대신 노드·자식 링크의 공간 비용을 부담한다.

### 구간 질의에는 다른 트리가 필요하다

| 구조 | 대표 문제 | 대표 비용과 조건 |
| --- | --- | --- |
| 세그먼트 트리 | 점 갱신과 구간 합·최솟값 등 | 전형적인 구현에서 구축 O(n), 갱신·질의 O(log n). 구간을 합치는 연산은 결합법칙을 만족해야 한다. |
| Fenwick 트리 | 점 덧셈 갱신과 누적 합 | 갱신·누적 합 O(log n). 구간 합은 누적 합 두 개의 차로 계산한다. |

이 자료구조들은 **‘특정 키를 찾기’와 ‘구간의 정보를 합치기’가 다른 작업**이라는 점에서 출발한다.

### 원리와 배경 설명

트리는 루트에서 자식으로 내려가는 계층을 표현한다. 파일 디렉터리, 구문 구조, 분류 체계처럼 부모·자식 관계가 중요한 데이터에 맞는다. 각 노드의 자식 수, 트리 높이, 균형 여부에 따라 탐색 비용이 달라진다. 이진 트리는 각 노드에 최대 두 자식이 있는 구조일 뿐, 자동으로 탐색 순서가 정해지는 것은 아니다.

이진 탐색 트리, BST는 왼쪽 부분트리의 키가 현재 키보다 작고 오른쪽은 크다는 식의 정렬 불변식을 둔다. 중복 키를 어떻게 다룰지는 별도 계약이다. 키 8에서 3을 찾으면 3\<8이므로 왼쪽으로, 다음 노드가 5라면 다시 왼쪽으로 내려간다. 매 단계 비교 하나로 한쪽 부분트리를 제외한다. 연산 비용은 트리 높이 h에 비례해 O(h)다.

1,2,3,4를 그대로 삽입해 오른쪽으로만 뻗은 BST는 높이가 원소 수에 비례해 최악 O(n)이 된다. 반면 AVL·red-black tree 같은 균형 트리는 회전과 높이·색 규칙으로 높이를 O(log n) 수준으로 유지한다.

회전은 탐색 순서를 보존하면서 부모·자식 연결을 바꾸는 연산이다. 균형을 유지하는 추가 작업을 지불해 최악 탐색을 제어하는 설계다.

정렬 순회나 범위 검색이 필요하면 해시 테이블보다 이런 트리 계열이 적절할 수 있다.


## 힙: 전체 정렬 대신 가장 급한 원소만 보장한다

### 최소 힙의 연산 표

| 작업 | 전형적인 이진 최소 힙의 비용 | 설명 |
| --- | --- | --- |
| 최솟값 보기 | O(1) | 루트를 확인한다. |
| 원소 추가 | 최악 O(log n) | 필요하면 부모 방향으로 올린다. |
| 최솟값 꺼내기 | 최악 O(log n) | 마지막 원소를 루트로 옮긴 뒤 내린다. |
| 임의의 키가 있는지 찾기 | 일반적으로 O(n) | 힙 순서만으로 위치를 알 수 없다. |
| 배열 전체를 힙으로 만들기 | O(n) | 아래쪽 부분트리부터 정리한다. |

### 원소 1을 추가하는 과정을 추적하기

| 단계 | 배열 상태 | 확인한 규칙 |
| --- | --- | --- |
| 시작 | `[2,5,3,9,7]` | 이미 최소 힙 |
| 끝에 추가 | `[2,5,3,9,7,1]` | 새 원소의 부모는 3 |
| 3과 교환 | `[2,5,1,9,7,3]` | 새 부모는 2 |
| 2와 교환 | `[1,5,2,9,7,3]` | 루트까지 이동 완료 |

### heapify가 O(n)인 이유

모든 노드가 높이 log n만큼 내려가는 것은 아니다. **절반 가까운 노드는 잎이어서 내려갈 곳이 없고**, 그 위의 다수 노드도 한두 단계만 움직인다. 높이별 노드 수와 이동 거리를 함께 합하면 O(n)으로 묶인다. n개를 차례로 삽입하는 O(n log n) 상한과 구분한다.

**주의:** 힙 배열 전체가 정렬된 것은 아니다. 최솟값을 반복해서 꺼내야 정렬된 순서를 얻는다.

### 원리와 배경 설명

최소 힙은 부모의 우선순위가 자식보다 크지 않다는 불변식을 유지한다. 완전 이진 트리 형태를 배열로 저장하면 인덱스 i의 자식은 2i+1과 2i+2, 부모는 (i−1)//2로 계산할 수 있다. 루트는 전체 최솟값이므로 확인은 O(1)이다. 하지만 서로 다른 부분트리의 형제·사촌까지 정렬되지는 않으므로 힙 배열을 그대로 읽으면 오름차순 목록이 되지 않는다.

최소 힙 `[2,5,3,9,7]`에 1을 추가하면 먼저 끝에 넣어 `[2,5,3,9,7,1]`이 된다. 부모 3보다 작으므로 교환해 `[2,5,1,9,7,3]`, 다시 부모 2와 교환해 `[1,5,2,9,7,3]`이 된다. 추가 원소가 루트 방향으로 이동한 것이다. 트리 높이만큼만 올라가므로 O(log n)이다. 최솟값을 꺼낼 때는 마지막 원소를 루트로 옮기고 더 작은 자식과 교환하며 내려가 불변식을 복원한다.

우선순위 큐는 이처럼 매번 최우선 항목을 처리하는 작업에 적합하다. Dijkstra의 다음 후보, 이벤트 시뮬레이션, 제한된 상위 k개 유지에 사용한다. 임의의 특정 키를 빨리 찾는 목적이라면 힙만으로 충분하지 않을 수 있고 별도 위치 맵 등이 필요하다. 모든 문제에 힙을 쓰기보다 필요한 연산이 무엇인지 다시 확인한다.

## 그래프: 연결 자체가 데이터일 때

### 저장 방식부터 선택하기

| 항목 | 인접 행렬 | 인접 리스트 |
| --- | --- | --- |
| 저장 공간 | O(V²) | O(V+E) |
| 두 정점의 간선 여부 | O(1) | 기본 목록에서는 해당 정점의 이웃을 탐색 |
| 한 정점의 이웃 순회 | 행의 V칸 검사 | 실제 이웃 수만큼 순회 |
| 잘 맞는 경우 | 조밀한 그래프, 빈번한 간선 검사 | 희소 그래프, 이웃 순회 |

### BFS를 한 단계씩

방향 간선이 `A→B`, `A→C`, `B→D`, `C→D`일 때 A에서 시작하자.

1. 큐에 A를 넣고 **넣는 순간** 방문 표시를 한다.
2. A를 꺼내 B, C를 방문 표시하며 넣는다. 큐는 `[B,C]`다.
3. B를 꺼내 D를 방문 표시하며 넣는다. 큐는 `[C,D]`다.
4. C를 꺼낼 때 D는 이미 표시되어 있으므로 다시 넣지 않는다.
5. D를 꺼내면 끝난다. 간선 가중치가 모두 같은 경우 BFS의 탐색 층은 시작점에서의 최단 간선 수와 연결된다.

인접 리스트와 상수 비용의 큐 연산을 사용하면 전체 탐색은 O(V+E)이다. 방문 표시 없이 같은 정점을 반복해서 넣는 구현과 구분한다.

### 연결 여부만 계속 묻는다면 Union-Find

집합이 `{A}`, `{B}`, `{C}`일 때 `union(A,B)` 후에는 A와 B의 대표가 같아진다. `find(A)==find(C)`로 같은 연결 집합인지 물을 수 있다.

- **경로 압축:** 대표를 찾는 길을 짧게 만든다.
- **크기·랭크 기반 합치기:** 작은 트리를 큰 트리 쪽으로 붙여 높이 증가를 제한한다.
- 두 기법을 함께 쓴 전형적인 분석에서는 연산열의 비용을 연산당 분할상환 O(α(n))으로 표현한다. α는 역 아커만 함수이며 매우 느리게 증가하지만, 엄밀히 O(1)이라고 쓰는 것과는 구분한다.
- 일반적인 Union-Find는 **집합 합치기와 연결 여부**에 맞춰져 있다. 최단 경로를 구하거나, 간선 삭제 후의 분리를 자동 처리하는 자료구조는 아니다.

### 원리와 배경 설명

그래프는 대상인 정점과 관계인 간선으로 이루어진다. 추천 관계, 도로, 작업 의존성은 트리보다 일반적인 연결을 가진다. 방향·가중치·중복 간선·자기 간선을 허용할지 먼저 정해야 같은 저장 구조를 일관되게 해석할 수 있다. 그래프는 추상적 관계이고 인접 리스트·인접 행렬은 그 관계를 저장하는 방법이다.

인접 행렬은 V×V 칸에 간선 여부나 가중치를 저장한다. 두 정점의 연결 여부를 바로 확인할 수 있지만 메모리는 O(V²)다.

인접 리스트는 각 정점에 연결된 이웃을 저장해 전체 O(V+E) 공간으로 표현할 수 있다. 이웃 순회에는 적합하지만 두 특정 정점의 연결 검사는 해당 이웃 목록을 훑거나 추가 집합 구조를 써야 한다.

정점 1만 개에 간선이 2만 개 정도인 희소 그래프라면 모든 쌍을 저장하는 것과 실제 연결만 저장하는 것의 차이가 크다.


예를 들어 A가 B,C와 연결되고 B가 C와 연결되었다면 `{A:[B,C], B:[C], C:[]}`는 방향 그래프의 인접 리스트다. 무방향 관계라면 반대 방향도 저장해야 한다. BFS·DFS는 이 목록을 따라 이웃을 방문한다. 방문 표시를 하지 않으면 순환 그래프에서 같은 정점을 계속 처리할 수 있다. 저장 의미와 알고리즘의 가정이 맞아야 한다.

## 핵심 정리

### 요구하는 연산에서 구조를 고르기

| 주로 필요한 일 | 먼저 검토할 구조 | 반드시 확인할 조건 |
| --- | --- | --- |
| 인덱스로 접근·끝에 추가 | 동적 배열 | 중간 이동, 확장 시 최악 지연 |
| 양 끝에서 추가·삭제 | Deque | 가운데 접근 비용 |
| 키로 존재 여부·값 조회 | 해시 테이블 | 분산, 적재율, 키의 길이와 안정성 |
| 정렬 순회·범위 검색 | 균형 탐색 트리 | 균형 보장과 비교 연산 비용 |
| 최우선 항목 반복 처리 | 힙 | 임의 키 탐색에는 별도 구조가 필요할 수 있음 |
| 접두사 검색 | Trie | 자식 선택 비용과 메모리 |
| 구간 합·구간 최솟값 | Fenwick·세그먼트 트리 | 지원하는 갱신·집계 연산 |
| 연결 집합 합치기 | Union-Find | 일반적인 간선 삭제·경로 검색과 구분 |

**선택 순서:** 필요한 연산 → 지켜야 할 순서·불변식 → 평균·최악 비용 → 메모리와 실제 측정.

### 원리와 배경 설명

자료구조는 자주 필요한 연산과 불변식을 기준으로 선택한다. 배열의 인덱스 계산과 연결 리스트의 참조 추적은 서로 다른 비용 구조를 가진다.

스택·큐·Deque는 꺼내는 순서를 정의하며 실제 구현은 여러 방식이 가능하다. 해시 테이블의 빠른 평균 조회는 충돌 처리·분산·적재율이라는 조건에 기대고 있다.

BST는 높이, 힙은 부모·자식 불변식이 성능과 기능을 결정한다. 그래프에서는 연결의 의미와 저장 표현을 나누어 생각해야 한다.

복잡도·메모리·실측 시간은 관련되지만 같은 양은 아니다.


### 심화 학습 지도: 자료구조를 고르는 네 가지 질문

**무엇을 저장하는가 → 어떤 연산을 반복하는가 → 어떤 최악 비용을 허용하는가 → 메모리가 얼마나 드는가** 순서로 판단한다. 이름을 많이 외우는 것보다 같은 문제에 두 구조를 비교할 수 있는 것이 중요하다.

| 요구사항 | 우선 검토할 구조 | 포기하거나 추가로 확인할 것 |
| --- | --- | --- |
| 키 하나의 값 조회 | 해시 테이블 | 정렬·범위 조회, 충돌, 재해싱 비용 |
| 키 순서와 범위 조회 | 균형 탐색 트리 | 회전·노드 메모리, 캐시 지역성 |
| 계속 들어오는 점수의 상위 K개 | 크기 K의 최소 힙 | 전체 원소의 정렬 순서는 유지하지 않음 |
| 최근 사용한 K개 항목 캐시 | 해시 테이블 + 이중 연결 리스트 | 동시 접근, 만료 시간, 값의 크기 |
| 값 변경과 구간 집계 반복 | 세그먼트 트리·Fenwick 트리 | 집계 연산의 성질, 갱신 종류 |
| 저장 전에 존재 여부를 저렴하게 거르기 | Bloom Filter | 양성 결과는 정확한 저장소에서 재확인 |
| 디스크 페이지 단위로 정렬 검색 | B+트리 계열 | 페이지 분할·쓰기 비용, DB별 구현 |

면접에서는 **기본 구조의 내부 동작 → LRU·Top-K·인덱스 선택 → 특수 구조** 순서로 공부한다. 세그먼트 트리 구현 숙련도와 서비스 설계 능력은 같은 평가 항목이 아니다.

### 심화 예제: LRU 캐시는 왜 두 자료구조를 결합하는가

용량이 2인 캐시에 `put(A), put(B), get(A), put(C)`를 수행한다. 가장 최근 사용한 항목을 왼쪽에 둔다.

| 연산 | 최근 → 오래된 순서 | 변화 |
| --- | --- | --- |
| put(A) | A | 새 항목 추가 |
| put(B) | B, A | 새 항목을 맨 앞으로 |
| get(A) | A, B | A를 가장 최근 위치로 이동 |
| put(C) | C, A | 가장 오래된 B 제거 |

**LRU(Least Recently Used)는 가장 오래 사용하지 않은 항목을 제거하는 정책**이다. 해시 테이블은 키로 노드를 찾고, 이중 연결 리스트는 찾은 노드를 떼어 내 맨 앞으로 옮긴다. 단일 연결 리스트는 이전 노드를 별도로 알지 못하면 제거할 위치 앞을 다시 찾아야 한다.

아래 구현은 양 끝의 가짜 노드인 **센티널**로 빈 리스트·마지막 항목의 경계 처리를 통일한다. `left` 다음은 가장 최근, `right` 이전은 가장 오래된 항목이다.

```py
class Node:
    def __init__(self, key=None, value=None):
        self.key, self.value = key, value
        self.prev = self.next = None


class LRUCache:
    def __init__(self, capacity):
        if capacity < 0:
            raise ValueError('capacity must be nonnegative')
        self.capacity = capacity
        self.nodes = {}
        self.left, self.right = Node(), Node()
        self.left.next, self.right.prev = self.right, self.left

    def _remove(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _front(self, node):
        first = self.left.next
        node.prev, node.next = self.left, first
        self.left.next, first.prev = node, node

    def get(self, key, default=None):
        node = self.nodes.get(key)
        if node is None:
            return default
        self._remove(node)
        self._front(node)
        return node.value

    def put(self, key, value):
        if self.capacity == 0:
            return
        node = self.nodes.get(key)
        if node is not None:
            node.value = value
            self._remove(node)
        else:
            node = Node(key, value)
            self.nodes[key] = node
        self._front(node)
        if len(self.nodes) > self.capacity:
            oldest = self.right.prev
            self._remove(oldest)
            del self.nodes[oldest.key]
```

**불변식:** 해시 테이블의 모든 노드는 리스트에 정확히 한 번 있고, 실제 노드 수는 용량 이하이며, 리스트 순서는 마지막 접근 순서와 일치한다. 조회·갱신·제거는 해시 연산의 기대 상수 비용을 가정하면 **평균 O(1)**, 공간은 **O(K)**이다. Python `OrderedDict`의 `move_to_end`와 `popitem`으로도 이 정책을 구현할 수 있다.

**실무의 추가 조건:** 이 코드는 단일 스레드 학습용이다. 동시 호출에서는 맵과 리스트를 함께 보호해야 한다. 항목 개수 K와 메모리 바이트 제한은 다르고, TTL(유효 시간)은 LRU와 다른 정책이다. 사용자별 권한·모델 버전이 다른 응답을 같은 캐시 키에 섞으면 정보 노출이나 잘못된 재사용이 생길 수 있다.

### 심화 원리: 균형 트리의 회전은 무엇을 보존하는가

30, 20, 10을 일반 BST에 넣으면 30의 왼쪽이 20, 20의 왼쪽이 10인 사슬이 된다. 30에서 **우회전**하면 20이 루트, 10이 왼쪽, 30이 오른쪽이 된다. **중위 순회 결과 10, 20, 30은 그대로이고 높이만 줄어든다.** 일반 회전에서도 두 노드 사이의 부분트리를 옮겨 키의 순서 관계를 보존한다.

| 구조 | 균형 규칙의 핵심 | 보장과 대가 |
| --- | --- | --- |
| 일반 BST | 키의 좌우 순서 | 높이 h에 비례한 O(h), 최악 O(n) |
| AVL | 각 노드에서 두 부분트리 높이 차가 최대 1 | 탐색·삽입·삭제 최악 O(log n), 높이 갱신·회전 필요 |
| Red-Black Tree | 루트와 NIL은 검정, 빨강의 자식은 검정, 각 하향 경로의 검정 높이가 같음 | 높이 O(log n), 색 변경·회전으로 복구 |

**해시 테이블과의 선택:** 정확한 키 조회만 많다면 해시가 유리할 수 있고, 정렬 순회·최솟값·범위 질의가 필요하면 균형 트리가 자연스럽다. 트리의 O(log n)이 해시의 O(1)보다 표기상 크더라도, **어떤 연산을 지원하는지와 최악 보장**까지 비교해야 한다.

### 심화 예제: 세그먼트 트리와 Fenwick 트리

배열 `[2,1,3,4]`의 전체 합은 10이다. 세그먼트 트리는 전체 `[0,4)`를 `[0,2)`의 합 3과 `[2,4)`의 합 7로 나누어 저장한다.

1. `[1,4)`의 합을 물으면 `[1,2)`의 값 1과 `[2,4)`의 합 7을 합쳐 **8**을 얻는다.
2. 인덱스 2의 값을 3에서 8로 바꾸면 해당 잎과 그 조상만 갱신한다.
3. 오른쪽 절반의 합은 12, 전체 합은 15, `[1,4)`의 합은 **13**이 된다.

일반적인 이진 세그먼트 트리의 구축은 **O(n)**, 점 갱신·구간 질의는 **O(log n)**, 공간은 **O(n)**이다. 구간 결과를 합치는 연산에는 **결합법칙**이 필요하고, 빈 구간까지 통일하려면 항등원이 필요하다. 합은 0, 최솟값은 양의 무한대를 항등원으로 둘 수 있다. 구간 전체 갱신은 별도 설계가 필요하며 lazy propagation은 일부 갱신·집계 조합에서 갱신을 미루는 방법이다.

Fenwick 트리는 1부터 세는 인덱스에서 `lowbit(i) = i & -i` 길이의 구간 정보를 둔다. 위 배열의 `bit[1], bit[2], bit[3], bit[4]`는 각각 **2, 3, 3, 10**이다.

- 처음 3개 합: `bit[3] + bit[2] = 3 + 3 = 6`. 인덱스를 `i -= lowbit(i)`로 줄인다.
- 세 번째 값에 5 추가: 인덱스 3과 4를 `i += lowbit(i)`로 방문해 각각 5를 더한다.
- 구간 합: 두 누적 합의 차를 사용한다. 합처럼 역연산을 쓸 수 있는 집계에 적합하다.

Fenwick은 갱신·누적 합 **O(log n)**, 공간 **O(n)**이다. 세그먼트 트리보다 상수가 작고 구현이 간결한 경우가 많지만, 기본 합 구현을 임의의 구간 최솟값·갱신에 그대로 적용할 수는 없다.

### 심화 원리: Bloom Filter의 양성은 확정이 아니다

Bloom Filter는 **비트 배열과 여러 해시 함수로 집합 포함 여부를 근사**한다. 교육용으로 비트 8개와 해시 2개를 사용하자. A의 위치가 1·4, B의 위치가 3·4라면 삽입 후 1·3·4번 비트가 켜진다.

| 조회 | 확인할 비트 | 결과의 의미 |
| --- | --- | --- |
| C가 1·3에 대응 | 둘 다 1 | C를 넣지 않았어도 양성일 수 있음: 거짓 양성 |
| D가 2·4에 대응 | 2번이 0 | 동기화된 정상 필터에서 D는 삽입된 적 없음 |

표준 삽입 전용 필터는 정확히 반영된 집합에 대해 **거짓 음성은 없고 거짓 양성은 가능**하다. 삽입·조회는 해시 k개의 계산과 비트 접근인 **O(k)**, 비트 공간은 **O(m)**이다. 저장 원소가 늘어 비트가 포화되면 거짓 양성이 많아진다.

**주의:** B를 삭제한다고 4번 비트를 꺼 버리면 A를 놓칠 수 있으므로 일반 필터는 단순 비트 삭제를 지원하지 않는다. 필터 복제가 늦거나 재구축 중이라면 시스템 전체의 무거짓음성 보장도 따로 설계해야 한다. DB 조회 전의 부정 결과 필터로는 쓸 수 있지만, 문서 중복을 확정하거나 권한을 판정하는 최종 저장소로는 쓰지 않는다.

### 면접 질문 01: 해시 테이블 조회는 언제 O(1)인가

**답변:** 키 해시·비교 비용이 상수이고 해시가 잘 분산되며 적재율을 제어한다는 조건에서 기대 O(1)입니다. 충돌이 한곳에 몰리면 최악 O(n)이 될 수 있고, 재해싱 한 번도 O(n)입니다. 평균·기대 비용과 확장 연산의 분할상환 비용을 구분하겠습니다.

**꼬리질문:** 긴 문자열도 O(1)인가? **문자열 길이 L에 대한 첫 해시 계산 비용 등을 별도로 포함**해야 한다. Python 문자열은 계산한 해시를 캐시할 수 있지만 모든 키·언어에 일반화하지 않는다.

### 면접 질문 02: 연결 리스트 삽입은 항상 배열보다 빠른가

**답변:** 삽입할 위치의 노드와 필요한 이전 노드를 이미 알고 있다면 링크 변경은 O(1)입니다. 인덱스로 위치를 찾는 과정은 O(n)일 수 있습니다. 배열은 중간 삽입에 이동이 필요하지만 연속 접근의 지역성과 낮은 메모리 비용 때문에 실제 실행에서 유리할 수 있습니다.

**꼬리질문:** Python list는 객체 자체가 연속하는가? **일반 CPython list는 객체 참조를 담는 연속 배열**이다. 숫자 값을 촘촘히 저장하는 NumPy 배열과 구분한다.

### 면접 질문 03: append의 평균과 분할상환은 무엇이 다른가

**답변:** 평균 분석은 입력 분포 등의 가정을 사용합니다. 분할상환 분석은 일련의 연산 총비용을 연산 수로 나눕니다. 기하급수적으로 늘어나는 동적 배열은 복사량의 합이 O(n)이어서 n번 append의 비용이 O(n), 한 번당 분할상환 O(1)이지만 특정 확장 시점은 O(n)입니다.

**꼬리질문:** 용량을 매번 1씩 늘리면? 복사가 `1+2+…+(n−1)`번 필요해 **총 O(n²)**이 될 수 있다.

### 면접 질문 04: LRU 캐시의 get도 왜 쓰기 동작인가

**답변:** 값을 읽은 항목을 가장 최근 위치로 옮겨야 하므로 순서 상태가 바뀝니다. 해시 테이블과 이중 연결 리스트를 함께 유지해 평균 O(1)에 처리하며, 동시 호출에서는 get도 동기화 대상입니다.

**꼬리질문:** LRU만으로 최신 데이터인가? 아니다. **퇴출 정책과 데이터 유효성·무효화 정책은 별개**다.

### 면접 질문 05: 상위 K개를 왜 최소 힙으로 유지하는가

**답변:** 현재 상위 K개 중 가장 작은 값이 교체 기준이기 때문입니다. 힙 크기를 K로 제한하고 더 큰 값이 오면 루트와 교체합니다. 전체 정렬을 하지 않고 스트림을 한 번 순회할 수 있습니다.

```py
import heapq


def top_k(values, k):
    if k <= 0:
        return []
    heap = []
    for value in values:
        if len(heap) < k:
            heapq.heappush(heap, value)
        elif value > heap[0]:
            heapq.heapreplace(heap, value)
    return sorted(heap, reverse=True)
```

고정 비용 비교를 가정해 유지 비용은 **O(n log(K+1))**, 결과 정렬은 **O(K log(K+1))** 상한이고 추가 공간은 **O(K)**이다. 실제 K가 n보다 크면 저장 원소 수는 n이다. 중복 점수를 개별 원소로 유지하는 구현이며, 문서 ID로 중복 제거하려면 별도 상태가 필요하다.

### 면접 질문 06: 힙과 BST는 무엇이 다른가

**답변:** 힙은 부모와 자식 사이의 우선순위만 보장해 최솟값 접근에 적합합니다. BST는 좌우 부분트리의 키 순서를 유지해 키 탐색과 정렬 순회에 적합합니다. 힙에서 임의 키 조회는 일반적으로 O(n)이며 BST도 균형이 없으면 최악 O(n)입니다.

**꼬리질문:** heapify가 왜 O(n)인가? 높이가 큰 노드는 소수이고 잎은 이동하지 않아, **높이별 작업량의 합이 O(n)**이다.

### 면접 질문 07: AVL과 Red-Black Tree를 언제 고려하는가

**답변:** 정렬된 키의 조회·갱신을 최악 O(log n)에 유지해야 할 때 고려합니다. AVL은 높이 차를 엄격히 제한하고 Red-Black Tree는 색 규칙으로 높이를 제한합니다. 선택은 조회·갱신 패턴과 실제 구현 비용을 보고 결정합니다.

**꼬리질문:** Red-Black Tree가 항상 삽입이 더 빠른가? 회전 횟수만으로 단정할 수 없고 **구현·메모리·워크로드를 측정**해야 한다.

### 면접 질문 08: Trie가 해시 테이블보다 나은 경우는

**답변:** 접두사 자체를 따라가거나 접두사 아래 단어를 나열해야 할 때 구조가 자연스럽습니다. 문자별 자식 선택을 상수로 보면 길이 L의 키 탐색은 O(L)입니다. 자식 표현에 따라 시간·공간이 달라지고 결과 열거에는 출력량만큼 추가 비용이 듭니다.

**꼬리질문:** 단어 종료 표시가 왜 필요한가? `car`와 `cart`가 같은 경로를 공유하므로 **경로 존재와 완전한 단어 존재**를 구분해야 한다.

### 면접 질문 09: Union-Find로 최단 경로도 구할 수 있는가

**답변:** 일반 Union-Find는 같은 집합인지 확인하고 집합을 합치는 구조입니다. 경로 압축과 rank·size 기반 합치기를 함께 쓰면 연산당 분할상환 O(α(n)) 수준입니다. 최단 경로와 일반적인 간선 삭제 후 분리 문제는 직접 해결하지 못합니다.

**꼬리질문:** α(n)은 정확히 상수인가? **역 Ackermann 함수**로 매우 느리게 증가하지만 점근적으로 상수라고 동일시하지 않는다.

### 면접 질문 10: 세그먼트 트리와 누적 합은 언제 바꾸는가

**답변:** 값이 고정되면 누적 합을 O(n)에 만들고 구간 합을 O(1)에 구할 수 있습니다. 점 갱신이 반복되면 누적 합 갱신이 O(n)이 될 수 있어 Fenwick·세그먼트 트리의 O(log n) 갱신을 고려합니다.

**꼬리질문:** 합 대신 최솟값이면? 두 누적 최솟값의 차로 구간 최솟값을 얻을 수 없으므로 **집계 연산의 성질**부터 확인한다.

### 면접 질문 11: Bloom Filter를 중복 제거의 정답으로 써도 되는가

**답변:** 거짓 양성 때문에 실제로 새로운 항목을 중복이라고 버릴 수 있습니다. 손실을 허용하지 않는 파이프라인에서는 후보를 거르는 보조 구조로 쓰고 정확한 키 저장소로 확인합니다.

**꼬리질문:** 거짓 음성은 절대 없는가? 정상 삽입 전용 필터의 보장과 **복제 지연·유실·잘못된 삭제가 있는 운영 시스템**을 구분한다.

### 면접 질문 12: AI 서비스에는 어떤 자료구조를 쓰겠는가

**답변:** 요청 ID 중복 확인에는 해시, 대기 작업에는 큐, 점수 상위 후보에는 힙, 의존 관계에는 그래프를 먼저 검토합니다. 검색은 단어의 역색인이나 벡터 근사 최근접 탐색처럼 검색 조건에 맞는 별도 인덱스가 필요합니다.

**꼬리질문:** 임베딩을 해시 맵에 넣으면 유사도 검색이 되는가? **정확한 키 일치와 벡터 거리 기반 이웃 검색은 다른 연산**이다. 인덱스 선택은 검색 품질·지연·메모리의 제약까지 연결한다.
