# 컴퓨터 구조는 같은 계산이 다른 속도로 실행되는 이유를 설명한다

행렬의 모든 원소를 더하는 두 프로그램이 있다. 하나는 행을 따라 연속해서 읽고 다른 하나는 열을 따라 띄엄띄엄 읽는다. 덧셈 횟수와 결과는 같지만 실행시간은 달라질 수 있다. CPU는 소스코드의 한 줄을 추상적으로 실행하는 것이 아니라 명령어를 읽고, 레지스터에서 계산하고, 여러 단계의 메모리에서 데이터를 가져온다. 컴퓨터 구조를 배우면 알고리즘의 연산 수와 실제 프로그램의 지연시간 사이에 무엇이 있는지 보인다.

## 비트와 바이트는 값의 표현 규칙이다

### 개념과 작동 원리

컴퓨터는 비트의 조합으로 정수·문자·명령어를 표현한다. 같은 비트열도 어떤 규칙으로 해석하는지에 따라 의미가 다르다.

8비트 무부호 정수는 0부터 255까지 표현할 수 있다. 부호 있는 정수에 흔히 쓰는 2의 보수 표현에서는 최상위 비트가 음의 가중치를 가지므로 범위가 −128부터 127이다.

예를 들어 비트열 11111111은 무부호로 255, 8비트 2의 보수로 −1이다. 비트 자체에 “음수”라는 표식이 별도로 붙는 것이 아니라 타입과 표현 규칙이 해석을 결정한다.


제한된 비트 수에서는 연산 결과가 범위를 넘을 수 있다. C의 부호 있는 정수 오버플로를 단순한 순환값으로 기대하면 안 되며, 무부호의 모듈러 연산 규칙과 구별해야 한다. Python의 일반 정수는 고정 32·64비트에 제한되지 않지만 값이 커질수록 더 많은 저장과 계산이 필요하다. 언어 차원의 정수와 GPU·배열의 고정 dtype 정수가 같은 수명·범위 규칙을 가지는 것은 아니다.

여러 바이트를 사용하는 값은 바이트 순서도 정해야 한다. 16진수 값 0x12345678을 낮은 주소부터 78,56,34,12로 저장하면 little-endian, 12,34,56,78이면 big-endian이다.

숫자의 수학적 의미가 달라진 것이 아니라 저장 순서가 다르다. 바이너리 파일·네트워크 메시지를 주고받을 때 양쪽이 같은 순서와 길이·부호를 사용하지 않으면 값이 깨진다.

직렬화 형식이 이런 규칙을 명시해야 하는 이유다.


부동소수점은 넓은 범위의 실수를 유한한 비트로 근사한다. 부호·지수·유효숫자에 해당하는 비트를 나누므로 표현 가능한 수 사이의 간격이 크기에 따라 달라진다.

0.1 같은 십진수가 이진 유한 소수로 정확히 표현되지 않을 수 있어 `0.1+0.2`가 0.3과 정확히 같은 비트가 아닐 수 있다. 덧셈 순서를 바꿀 때 반올림 위치가 달라져 결과가 달라지는 것도 가능하다.

모델 학습의 정밀도·수치 안정성은 수학적 등식만으로 판단할 수 없다.


### 같은 비트열을 두 규칙으로 해석하기

8비트 b₇…b₀의 무부호 값은 $\sum_{i=0}^7b_i2^i$다. 2의 보수 부호 해석에서는 최상위 비트의 기여가 $-b_72^7$로 바뀐다. 따라서 11111111은 무부호 255이고, 부호 있는 해석은 -128+127=-1이다.

| 해석 규칙 | 8비트 범위 | 같은 비트가 달라지는 이유 |
|---|---|---|
| 무부호 | 0~255 | 모든 자리의 가중치가 양수 |
| 2의 보수 부호 | -128~127 | 맨 앞 자리의 가중치가 음수 |

```py
raw = bytes.fromhex('78 56 34 12')
assert int.from_bytes(raw, 'little') == 0x12345678
assert int.from_bytes(raw, 'big') == 0x78563412
```

바이트 순서는 **바이트 사이의 배치**를 정한다. 바이트 안의 비트를 거꾸로 읽는 것과 다르다. 8비트 예제의 순환 연산을 C의 signed overflow 동작으로 일반화하지 않는다. 표현 범위와 연산 규칙은 각각 확인해야 한다.

## CPU는 명령어와 레지스터로 계산한다

### 개념과 작동 원리

명령어 집합 구조, ISA는 기계가 이해하는 연산과 레지스터·주소 지정 등의 약속이다. x86-64와 ARM64는 서로 다른 ISA다. 컴파일러는 소스의 계산을 해당 ISA의 명령어로 바꾼다. 같은 C 소스를 다시 컴파일할 수 있다는 것과 특정 ISA의 바이너리를 그대로 실행할 수 있다는 것은 다른 이야기다. Mac ARM에서 x86-64 전용 시스템 실습을 실행하려면 환경을 따로 맞춰야 하는 이유다.

레지스터는 CPU가 연산에 직접 사용하는 작은 저장 공간이다. `a[i] + b[i]`를 단순화하면 메모리에서 두 값을 읽고, 레지스터에서 더하고, 결과를 저장하는 과정으로 생각할 수 있다. 실제 명령어 형태와 최적화는 ISA·컴파일러에 따라 다르다. 컴파일러는 같은 값을 다시 읽지 않고 레지스터에 보관하거나 필요 없는 계산을 제거할 수 있다. 소스의 변수 하나가 반드시 RAM의 고정된 칸 하나에 대응하는 것은 아니다.

함수 호출에는 인자 전달, 복귀 위치, 보존해야 할 레지스터 같은 규칙이 필요하다. 호출 규약은 호출자와 피호출자가 이 역할을 어떻게 나눌지 정한다.

일부 인자는 레지스터, 나머지는 스택으로 전달할 수 있다. 지역 값도 레지스터에 두거나 스택에 저장할 수 있다.

재귀가 깊어지면 아직 끝나지 않은 호출 상태가 쌓이기 때문에 호출 스택 사용량이 늘어난다. 단, 컴파일러 최적화가 호출 구조를 바꾸는 경우가 있어 실제 기계어와 언어의 의미를 구별한다.


분기는 어떤 명령을 다음에 실행할지 바꾼다. CPU가 명령을 여러 단계로 겹쳐 처리하려면 분기의 결과를 미리 추측하는 것이 유리할 수 있다. 예측이 틀리면 추측으로 진행한 일을 버리고 올바른 경로로 돌아가야 한다. 따라서 같은 비교 횟수라도 데이터 패턴과 분기 예측에 따라 시간이 달라질 수 있다. 이것이 알고리즘의 비교 수만으로 모든 성능을 설명할 수 없는 또 하나의 이유다.

### 배열 주소 계산에서 명령 실행까지

원소가 8바이트인 연속 배열의 시작 주소가 0x1000이면 a[3]의 주소는 0x1000+3×8=0x1018이다. 인덱스 3을 주소에 그대로 더하면 네 번째 원소를 찾을 수 없다.

| 개념적 단계 | 처리하는 내용 | 확인할 조건 |
|---|---|---|
| 주소 계산 | 시작 주소+인덱스×원소 크기 | 인덱스와 바이트 단위 구분 |
| load | 메모리 값을 레지스터로 읽음 | 유효한 주소·접근 권한 |
| 연산 | 레지스터의 값에 덧셈 등 수행 | 타입·표현 범위 |
| store | 결과를 메모리에 기록 | 저장 대상·가시성 조건 |

이 표는 설명용 분해다. 실제 컴파일러는 주소 계산을 명령 안에 합치거나, 값을 레지스터에 유지하거나, 필요 없는 계산을 제거할 수 있다. **소스 한 줄과 기계어 한 명령은 일대일이 아니다.** 함수 호출 때도 모든 지역 변수가 항상 메모리 스택에 저장된다고 단정하지 않는다. [CS:APP 저자 자료](https://csapp.cs.cmu.edu/)의 기계 수준 프로그램·컴파일 설명과 연결한다.

## 지연시간, 처리량, 실행시간을 구분한다

### 개념과 작동 원리

지연시간은 작업 하나를 끝내는 데 걸린 시간이고 처리량은 단위 시간에 끝내는 작업 수다. 파이프라인은 한 작업이 여러 단계를 지나는 동안 다른 작업을 앞 단계에서 진행하게 해 처리량을 높일 수 있다. 그러나 단일 작업의 단계 수가 사라지는 것은 아니다. 네트워크 요청을 여러 개 병렬로 받는 것과 한 요청의 응답이 빨라지는 것이 다른 것과 비슷하다.

단순한 CPU 성능 모델에서 실행시간은 명령어 수×명령어당 평균 사이클 수÷클럭 주파수로 표현할 수 있다. 클럭을 높여도 명령어 수나 메모리 대기 때문에 평균 사이클이 커지면 효과가 제한된다. 최적화로 명령어 수를 줄였지만 더 느린 메모리 접근을 만들 수도 있다. 성능을 비교할 때 코드·컴파일 옵션·데이터·측정 구간을 함께 기록해야 한다.

프로그램의 한 부분이 전체 시간의 20%이고 그 부분을 10배 빠르게 한다면 새 시간은 0.8T+0.2T/10=0.82T다. 전체 향상은 약 1.22배다. 부분 성능이 전체 성능을 대체하지 않는다는 Amdahl 법칙의 예다. GPU 커널이 매우 빨라도 입력 파일 읽기·전처리·전송이 대부분이라면 전체 학습은 크게 빨라지지 않는다. 개선할 부분의 비중부터 측정하는 이유다.

### 파이프라인의 첫 결과와 연속 결과를 구분하기

가상의 처리 단계 5개가 각각 1ms 걸리고 모든 단계가 완벽히 겹친다고 하자. 한 작업의 지연시간은 5ms지만, 파이프라인이 찬 뒤에는 1ms마다 한 작업이 완료된다.

| 작업 10개 처리 | 전체 시간 | 한 작업의 경로 |
|---|---|---|
| 겹침 없이 순서대로 | 10×5=50ms | 각각 5ms |
| 이상적 5단계 파이프라인 | (5+10−1)×1=14ms | 각각 5ms |

처리량 향상이 개별 작업의 지연시간 단축과 같은 뜻은 아니다. 단계 불균형·분기·의존성·메모리 대기는 이 이상적 계산에서 제외했다.

명령어 10⁹개, 평균 CPI=2, 주파수 2GHz라면 실행시간은 $10^9\times2/(2\times10^9)=1$초다. 클럭만 보고 성능을 비교하면 명령어 수와 CPI 변화를 놓친다. 성능 개선은 동일 작업·입력에서 전체 실행시간으로 확인한다.

## 메모리 계층과 지역성

### 개념과 작동 원리

레지스터·캐시·RAM·저장장치는 용량과 접근 비용의 교환관계를 가진다. CPU 가까이에 큰 데이터를 전부 빠르게 둘 수 없기 때문에 작은 빠른 층과 큰 느린 층을 결합한다. CPU 캐시는 최근 또는 가까운 주소의 데이터가 다시 쓰일 가능성을 이용한다. 시간 지역성은 같은 데이터를 곧 다시 쓰는 성질이고 공간 지역성은 이웃한 주소를 가까운 시간에 쓰는 성질이다.

데이터를 1바이트 요청해도 캐시는 보통 캐시라인 단위로 주변 데이터를 함께 가져온다. 학습용 가정으로 라인이 64바이트, 원소가 8바이트라면 인접 원소 8개가 한 라인에 들어간다. 연속 읽기는 가져온 이웃을 활용할 가능성이 높다. 반면 멀리 떨어진 원소만 하나씩 읽으면 가져온 라인의 일부만 쓰고 나머지를 낭비할 수 있다. 실제 라인 크기와 캐시 구조는 장비에서 확인해야 하며 예시 숫자를 모든 CPU에 적용하지 않는다.

캐시의 hit는 필요한 데이터가 해당 층에 있는 경우, miss는 더 아래 층에서 가져와야 하는 경우다. 태그는 어떤 메모리 블록인지 구별하고 인덱스는 어느 캐시 집합을 찾을지, offset은 라인 안의 위치를 정하는 데 쓰인다.

집합당 몇 라인을 둘 수 있는지인 연관도와 교체 정책도 충돌에 영향을 준다. 전체 데이터 양이 캐시보다 작아도 매핑 충돌이나 다른 작업의 간섭으로 miss가 날 수 있다.

쓰기 정책도 값을 다음 층에 언제 반영할지 정하므로 단순한 읽기 캐시와 다르다.


### 평균 접근시간과 캐시 충돌 계산

hit 시간이 1ns, miss율이 5%, miss 때 추가 지연이 100ns인 단순 1단계 모형이면 평균은 $1+0.05\times100=6$ns다. miss 비용을 이미 포함한 총시간인지 **추가 penalty**인지에 따라 식이 달라진다. 이 값들은 실제 장비 측정값이 아닌 학습용 가정이다.

캐시라인이 64바이트이고 direct-mapped 집합이 4개라면 바이트 주소의 하위 6비트가 offset, 다음 2비트가 집합 인덱스다.

| 주소 | 메모리 블록 번호 | 집합 인덱스 |
|---|---|---|
| 0 | 0 | 0 |
| 64 | 1 | 1 |
| 256 | 4 | 0 |

주소 0과 256은 서로 다른 블록이지만 같은 집합을 사용하므로 번갈아 접근하면 충돌 교체가 생길 수 있다. 데이터 총량이 캐시 용량보다 작다고 항상 hit하는 것은 아니다. 실제 성능에서는 연관도·교체 정책·prefetch·여러 계층도 함께 작동한다.

## 행 순회와 열 순회를 주소로 따라가기

### 개념과 작동 원리

행 우선으로 저장한 작은 행렬에서 A\[0\]\[0\] 다음 주소에는 같은 행의 A\[0\]\[1\]이 온다. 아래 코드는 같은 원소를 한 번씩 더하지만 방문 순서가 다르다.

```c
for (int r = 0; r < rows; r++)
    for (int c = 0; c < cols; c++)
        sum_row += a[r][c];

for (int c = 0; c < cols; c++)
    for (int r = 0; r < rows; r++)
        sum_col += a[r][c];
```

첫 부분은 첫 행을 연속해서 읽고 다음 행으로 간다. 둘째 부분은 같은 열의 다음 행으로 이동하므로 주소 간격이 한 행의 크기만큼 벌어진다. 행렬이 충분히 크고 캐시가 제한되어 있으면 열 순회에서 다시 쓸 라인이 그 전에 교체될 수 있다. 두 합은 정수 오버플로가 없다는 조건 등에서 같은 수학적 결과를 내지만 캐시 접근 기록은 다르다. 부동소수점이면 덧셈 순서 때문에 최하위 자릿수 결과도 달라질 수 있다.

![명시한 작은 캐시 모델의 시뮬레이션입니다. 실제 CPU의 캐시 크기·연관도·prefetch 동작과 성능은 다릅니다.](/figures/C05.svg)

명시한 작은 캐시 모델의 시뮬레이션입니다. 실제 CPU의 캐시 크기·연관도·prefetch 동작과 성능은 다릅니다.

위 그림은 고정 크기 캐시와 LRU 교체를 가정해 row·column 접근을 비교한 **시뮬레이션 예제**다. LRU는 가장 오래 사용하지 않은 라인을 먼저 내보낸다.

행 접근이 같은 라인의 이웃을 바로 쓰는지, 열 접근에서 라인이 다시 필요할 때까지 얼마나 많은 다른 라인을 거치는지 읽으면 된다. 그래프의 hit·miss는 그 모델의 주소 기록을 센 값이며 실제 CPU 시간이나 모든 CPU의 miss 비율이 아니다.

실제 하드웨어에는 prefetch, 여러 캐시 층, 연관도, 다른 프로세스, 컴파일러 변환 등이 추가된다.


이 모델에서는 행 우선으로 저장한 8×8 배열을 사용하고, 한 캐시라인에는 원소 4개가 들어간다. 캐시는 완전 연관 방식으로 4라인을 보관하며 초기에 비어 있다. offset을 4로 나눈 몫이 라인 번호다.

행 순회는 offset 0,1,2,3을 읽을 때 첫 접근만 miss이고 다음 세 번은 같은 라인의 hit다. 전체 64원소에 필요한 라인은 16개라서 miss가 16번이다.

열 순회는 0,8,16,…,56처럼 라인 번호가 0,2,4,…,14로 바뀌며 8개 라인을 거친다. 캐시에 4라인밖에 없으므로 다음 열에서 첫 라인을 다시 쓸 때는 이미 쫓겨났다.

같은 일이 반복되어 이 모델의 열 순회는 64번 모두 miss가 된다. 왼쪽의 첫 24개 offset 궤적과 오른쪽의 전체 miss 횟수를 함께 읽으면 주소 간격이 교체 결과로 이어지는 과정을 확인할 수 있다.


블로킹 또는 타일링은 한 번에 작은 부분행렬을 처리해 캐시에 올라온 데이터를 여러 번 쓰게 한다. 행렬 곱에서 작은 블록의 행·열을 반복 사용하면 아래 메모리에서 가져오는 양을 줄일 수 있다. 알고리즘의 수학적 덧셈·곱셈 수가 같아도 데이터 재사용이 늘어 속도가 달라진다. “메모리에 연속하게 둔다”는 말과 “현재 연산이 필요한 순서로 재사용한다”는 말도 구분해야 한다.

### 작은 LRU 캐시로 순회 차이를 재현하기

4×4 행렬, 원소 8바이트, 행 우선 저장을 가정하자. 행 내부의 인접 원소 주소 차이는 8바이트, 같은 열의 다음 행까지는 4×8=32바이트다. 아래는 라인 16바이트·용량 2라인인 **가상 완전연관 LRU 캐시**이며 실제 CPU 벤치마크가 아니다.

```py
def cache_misses(indices):
    cache, misses = [], 0
    for row, col in indices:
        line = ((row*4 + col)*8) // 16
        if line in cache:
            cache.remove(line)
        else:
            misses += 1
            if len(cache) == 2:
                cache.pop(0)
        cache.append(line)
    return misses

rows = [(r, c) for r in range(4) for c in range(4)]
cols = [(r, c) for c in range(4) for r in range(4)]
assert cache_misses(rows) == 8
assert cache_misses(cols) == 16
```

두 순회 모두 원소 수에 비례하는 O(RC) 작업이다. 차이는 점근적 연산 수가 아니라 **접근 순서가 메모리 계층과 만나는 방식**이다. 실제 배열의 저장 순서·stride를 바꾸면 유리한 순회도 달라질 수 있다.

## SIMD, 멀티코어, GPU의 병렬성

### 개념과 작동 원리

SIMD는 하나의 명령으로 여러 데이터 원소에 비슷한 연산을 적용한다. 배열 전체에 같은 덧셈을 하는 연산은 잘 맞지만 제어 흐름이 제각각이면 활용이 제한될 수 있다. 멀티코어는 여러 실행 흐름을 서로 다른 코어에서 처리한다. 단일 스레드 코드가 코어 수만큼 자동으로 빨라지는 것은 아니며 병렬 작업 분할과 동기화가 필요하다.

여러 코어가 같은 메모리를 사용하면 각 캐시의 값이 일관되도록 관리해야 한다. 서로 다른 변수를 고치는 두 스레드라도 변수가 같은 캐시라인에 있으면 false sharing이 생길 수 있다. 프로그램 의미상 데이터를 공유하지 않는데 하드웨어는 같은 라인의 소유·수정 상태를 오가며 비용을 지불하는 것이다. 쓰기하는 위치의 배치와 작업 분할이 성능에 영향을 주는 이유다. 이는 정답을 바꾸는 데이터 경쟁과는 구분되는 성능 문제다.

GPU는 대량의 비슷한 연산을 병렬로 처리하는 데 강하다. 그러나 CPU와 GPU 사이의 데이터 이동, 작은 작업을 실행하는 준비 비용, GPU 메모리 접근 패턴을 고려해야 한다. 연산량이 작으면 GPU 호출·전송 비용이 이득보다 클 수 있다. GPU 메모리도 레지스터·공유 메모리·전역 메모리 등 서로 다른 역할과 비용을 가진다. CUDA는 NVIDIA의 실행 생태계이며 Apple GPU의 MPS와 동일한 환경이 아니다.

처리 속도를 높이려면 연산 능력이 병목인지 데이터 이동이 병목인지 구분한다. 같은 데이터를 적게 읽어 많은 계산을 하면 연산 장치를 더 잘 활용할 수 있다. 반대로 원소마다 작은 연산 하나만 하고 큰 데이터를 읽으면 메모리 대역폭이 제한할 수 있다. 프로파일러로 CPU 시간, 캐시·메모리 행동, 전송과 커널 시간을 나누어 관측해야 “GPU 사용률이 낮다” 같은 현상을 올바르게 해석할 수 있다.

### 병렬 계산 이득에서 전송·동기화 비용 빼기

가상의 CPU 작업이 100ms이고 GPU 경로가 입력 전송 30ms+준비 5ms+계산 10ms+결과 전송 30ms라면 전체는 75ms다. 계산 부분이 크게 빨라도 전체 향상은 100/75≈1.33배다. 데이터를 GPU에 유지해 여러 연산에서 재사용하면 계산이 달라질 수 있다.

| 병렬화 수준 | 주된 활용 조건 | 남는 비용 |
|---|---|---|
| SIMD | 비슷한 연산을 여러 원소에 적용 | 분기·정렬·메모리 공급 |
| 멀티코어 | 독립 작업 또는 분할 가능한 데이터 | 동기화·공유 자원 경쟁 |
| GPU | 충분히 큰 병렬 작업 | 전송·실행 준비·접근 패턴 |

**복습 문제:** 전체 시간의 90%를 8배 빠르게 만들면 전체 속도 향상은?

<details><summary>풀이</summary>

새 시간은 $0.1T+0.9T/8=0.2125T$이므로 약 4.71배다. 나머지 10%와 추가 병렬화 오버헤드는 사라지지 않는다. 이 계산은 작업량이 고정된 단순 Amdahl 모형이다.

</details>

## 핵심 정리

비트열의 의미는 타입과 표현 규칙으로 정해진다. 명령어·레지스터·호출 규약은 소스코드를 실제 실행으로 연결한다.

클럭·지연시간·처리량은 서로 다른 성능 지표다. 캐시는 시간·공간 지역성을 이용하므로 같은 연산 수라도 접근 순서가 성능을 바꾼다.

행렬 순회와 타일링은 데이터 재사용의 효과를 보여 준다. SIMD·멀티코어·GPU는 각기 다른 병렬성을 제공하며 데이터 이동과 동기화 비용을 동반한다.

하드웨어 캐시와 운영체제의 가상 메모리, 응용 서비스의 캐시는 구분해서 설명해야 한다.
