## 모델이 말하는 것과 프로그램이 실행하는 것을 나누기

### 개념과 작동 원리

사용자가 ‘지난 분기 보고서에서 매출 감소 이유를 찾아 요약해 줘’라고 요청했다. 모델이 기억한 문장만 생성할 수도 있고, 파일을 검색한 뒤 근거를 읽고 요약할 수도 있다.

후자의 시스템에는 문서 수집·색인·검색·모델 호출·결과 검증이 필요하다. LLM은 이 중 텍스트와 행동 제안을 생성하는 한 구성 요소다.

모델이 `search_documents`를 호출하겠다고 출력해도 파일을 실제로 읽고 네트워크에 요청하는 것은 실행 프로그램, 즉 호스트다.

Agent를 이해하려면 모델의 추론 능력과 시스템의 제어 정책을 분리해야 한다. 모델은 현재 입력에서 다음 응답·도구 호출을 제안하고, 호스트는 허용 도구·인자 형식·권한·호출 예산·종료 조건을 적용한다. 여러 모델을 연결했다고 자동으로 안전하거나 정확한 시스템이 되지는 않는다. 어떤 결정을 어느 구성 요소가 책임지는지 명시하는 것이 시작이다.

### 모델 출력·도구 실행·완료 증거의 세 층

| 층 | 산출물 | 확인할 질문 |
|---|---|---|
| 모델의 제안 | 도구 이름·인자 또는 답변 | 허용된 선택이며 인자가 맞는가 |
| 호스트 실행 | 실제 함수·외부 서비스 결과 | 호출이 실행되어 어떤 결과를 냈는가 |
| 업무 검증 | 저장값·파일·원격 상태 등 | 사용자가 요청한 결과가 존재하는가 |

'저장했습니다'라는 문장을 생성한 것과 파일을 저장한 것은 다르다. 도구 호출이 성공 반환했더라도 경로·내용·대상 환경이 잘못되었으면 사용자 목표와 어긋날 수 있다. **완료 판정은 주장보다 관측 가능한 결과에 연결**한다.

[ReAct 원 논문](https://arxiv.org/abs/2210.03629)은 언어모델의 판단과 환경의 행동·관측을 연결한다. 구체적인 실행 권한과 검증은 사용하는 호스트의 계약으로 설계해야 한다.

## 임베딩 검색: 의미를 벡터의 이웃 찾기로 바꾸기

### 개념과 작동 원리

검색할 문서를 chunk라는 단위로 나누고 각각 임베딩 벡터를 계산해 저장한다. 질문도 같은 표현 공간의 벡터로 바꾸어 가까운 문서 조각을 찾는다. 질문 벡터 q=(1,0), 문서 벡터 d₁=(0.8,0.6),d₂=(0,1)이면 q,d₁의 cosine은 0.8, q,d₂는 0이다. 이 모델과 거리 기준에서는 첫 문서가 더 가깝다. 그러나 벡터가 가깝다는 사실만으로 문서가 질문의 정답을 포함한다거나 최신이라는 보장은 없다.

Chunk를 작게 만들면 특정 사실을 정밀하게 찾기 쉬울 수 있지만 문맥이 잘린다. ‘그 금액은 전년 대비 감소했다’만 저장하면 금액과 대상이 무엇인지 잃을 수 있다. 크게 만들면 문맥은 유지되지만 관련 없는 정보와 입력 비용이 늘어난다. 문단·표·절 구조, 주변 문맥 추가, 중첩 등을 질문 유형에 맞춰 선택한다. 문서 ID·제목·날짜·권한·위치 metadata를 남겨야 검색 결과가 어느 원문에서 왔는지 추적할 수 있다.

키워드 검색 BM25는 정확한 이름·코드·희귀 용어에 유리할 수 있고 임베딩 검색은 다른 표현의 의미 관계를 찾는 데 유용할 수 있다. Hybrid search는 두 종류의 후보를 결합한다.

서로 다른 점수의 숫자 범위가 같지 않으므로 무작정 더하기보다 정규화나 순위 기반 결합 등을 정한다. Reranker는 질문과 후보를 함께 읽는 더 비싼 모델로 후보 순서를 재평가할 수 있다.

전체 문서에 무거운 모델을 적용하는 대신 넓게 찾고 좁혀 읽는 구조다.

### 검색 척도와 정답 집합의 크기

정답 문서 집합이 {A,B,C}, 상위 4개 검색 결과가 [X,A,Y,B]라면 관련 문서 2개를 찾았다. precision@4=2/4=0.5, recall@4=2/3이고 첫 정답 순위가 2이므로 reciprocal rank=1/2다.

| 지표 | 이 예의 값 | 답하는 질문 |
|---|---|---|
| hit@4 | 1 | 정답이 하나라도 있는가 |
| precision@4 | 0.5 | 검색한 것 중 관련 비중은 |
| recall@4 | 2/3 | 필요한 정답을 얼마나 포함했나 |
| reciprocal rank | 1/2 | 첫 정답이 얼마나 위에 있나 |

문서를 여러 chunk로 나누면 정답 단위를 문서·청크 중 무엇으로 셀지도 정해야 한다. 중복 청크가 상위 자리를 채우면 숫자상 후보가 많아도 근거 다양성은 낮을 수 있다. 정확한 dense 검색은 N개 d차원 벡터와의 점수 계산에 O(Nd) 시간이 들고, ANN은 속도·공간·정확도 절충을 만든다.

## RAG는 검색 결과를 답변 생성의 근거로 넣는다

### 개념과 작동 원리

Retrieval-Augmented Generation은 질문과 관련된 외부 정보를 찾아 모델 입력에 제공하는 방식이다. 검색 단계가 후보 문서를 선택하고, 생성 단계가 질문·검색 근거·출력 지침을 보고 답을 만든다. 모델 가중치를 수정하는 미세조정과 다르다. 원문이 바뀌면 색인을 갱신해 새 내용을 제공할 수 있지만 파싱·색인·검색·인용이 모두 정확해야 효과를 기대할 수 있다.

‘2025년 매출은?’이라는 질문에 2024년 보고서만 찾았다면 모델의 문장 능력을 높이는 것으로 해결되지 않는다. 반대로 최신 정답 문서를 찾았지만 단위를 천원에서 원으로 잘못 읽으면 생성·해석 문제다.

따라서 검색과 생성을 나눠 평가해야 원인을 찾을 수 있다. 근거가 없을 때 정답처럼 말하지 않고 모름·추가 자료 필요를 표현하는 조건도 설계해야 한다.

거절을 무조건 실패로 세면 근거 없는 추측을 보상하는 지표가 될 수 있다.

질문마다 관련 문서가 하나라고 하자. 20문제 중 상위 5개 후보에 정답 문서가 포함된 문제가 16개면 hit-rate@5는 16/20=0.8이다. 여러 정답 문서가 있는 한 질문에서 관련 문서가 총 4개이고 상위 5개에 3개가 있으면 recall@5=3/4=0.75, precision@5=3/5=0.6이다. 질문당 적어도 하나를 찾았는지와 전체 정답 문서를 얼마나 찾았는지는 다른 지표다.

생성에서는 답의 정확성, 근거가 실제 주장을 뒷받침하는지, 인용 위치가 맞는지, 정답이 없는 상황에서 적절히 대응하는지를 구분한다. 모델을 판정기로 쓸 수 있지만 판정 자체의 오류·순서 편향·프롬프트 민감도를 표본 검토해야 한다. 검색에 정답이 있었는지와 최종 답이 근거 있는지를 2×2로 나누면 누락과 해석 오류를 분리할 수 있다. 다만 정당한 거절과 틀린 답변을 한 칸에 무심코 섞지 않도록 범주 정의가 필요하다.

### 검색 성공과 근거 사용 성공을 분리해서 세기

가상의 100문제 중 필요한 근거를 검색한 것이 80문제이고, 그중 근거를 올바르게 사용해 답한 것이 60문제라 하자. 근거 검색 성공률 80%, 검색 성공 조건에서의 답변 성공률 75%, 해당 경로의 전체 성공은 60%다. 검색하지 못한 문제의 다른 성공 경로는 이 단순 집계에서 제외했다.

| 실패 | 고쳐 볼 부분 |
|---|---|
| 필요한 문서가 후보에 없음 | 자료 수집·chunk·질의·검색·필터 |
| 후보에 있지만 문맥에서 누락 | reranking·선택·문맥 예산 |
| 문맥에 있지만 단위·시점 오독 | 근거 해석·계산·답변 검증 |
| 인용이 주장과 연결되지 않음 | 주장별 근거 연결 평가 |

**출처 링크가 있다는 사실만으로 그 주장을 뒷받침하지는 않는다.** 검색 문서의 신뢰성·시점과 답변이 실제 사용한 근거를 함께 본다. [RAG 원 논문](https://arxiv.org/abs/2005.11401)의 검색 메모리와 생성 모델 결합을 출발점으로 삼되, 실제 응용의 검증 단계를 별도로 둔다.

## 구조화 출력은 형식을 제한하고 의미는 따로 검증한다

### 개념과 작동 원리

모델에게 `{"revenue": ..., "unit": ..., "source_id": ...}`를 요구하면 후속 코드가 필드를 읽기 쉬워진다. JSON schema는 필드 존재, 타입, 허용 값 같은 구조를 제한할 수 있다. 그러나 `revenue=100`이라는 숫자가 원문과 일치하는지까지 schema만으로 보장하지 않는다. 형식 검증과 사실·업무 규칙 검증을 나눠야 한다.

예를 들어 날짜 형식이 맞아도 종료일이 시작일보다 앞일 수 있다. 호스트는 타입 검증 뒤 날짜 순서·허용 기간·문서 근거 같은 조건을 확인할 수 있다. 검증 실패를 모델에게 돌려 수정하게 할 수도 있지만 무한 재시도가 되지 않도록 횟수와 실패 응답을 정한다. 형식 제약은 모델이 올바른 값을 찾는 문제를 없애는 것이 아니라 잘못된 형식이 시스템에 전달되는 경로를 줄인다.

### schema 통과와 업무 의미 통과 비교

아래는 설명용 JSON Schema의 일부다. 실제 적용 시 사용할 schema 버전과 검증기를 정해야 한다.

```json
{
  "type": "object",
  "required": ["revenue", "unit", "source_id"],
  "additionalProperties": false,
  "properties": {
    "revenue": {"type": "number"},
    "unit": {"enum": ["KRW", "USD"]},
    "source_id": {"type": "string"}
  }
}
```

| 검사 | 통과해도 남는 질문 |
|---|---|
| 필수 키·타입 | 실제 문서에 그 수치가 있는가 |
| 단위 enum | 원문 단위와 환산이 맞는가 |
| 문자열 source_id | 존재하며 해당 주장과 관련된 자료인가 |
| 추가 키 금지 | 허용 필드 안의 값이 사실인가 |

[공식 JSON Schema object 설명](https://json-schema.org/understanding-json-schema/reference/object)은 properties와 required, 추가 속성 제한을 구분한다. 형식 제한과 의미 검증을 같은 성공으로 세지 않는다.

## 도구 호출의 한 라운드를 실제 순서로 읽기

### 개념과 작동 원리

모델 입력에는 사용자 요청뿐 아니라 사용할 수 있는 도구의 이름·설명·인자 schema가 들어갈 수 있다. 모델은 일반 답변 대신 도구 호출 이름과 인자를 생성한다. 호스트는 그 출력을 파싱해 실행 여부를 결정한다. 실행한 결과는 도구 결과 메시지로 다음 모델 입력에 추가된다. 모델은 그 관측을 바탕으로 다시 도구를 요청하거나 최종 답을 만든다. 이것이 tool call과 tool result 라운드다.

| 단계 | 주체 | 실제 내용 예시 |
| --- | --- | --- |
| 요청 | 사용자 | ‘A기업 보고서에서 매출을 찾아줘’ |
| 제안 | LLM | search\_documents(query='A기업 매출', year=2025) |
| 검증·실행 | 호스트 | 도구 허용 여부·인자·권한을 확인하고 검색 실행 |
| 관측 반환 | 호스트 | 문서 ID·발췌·조회 상태를 tool result로 추가 |
| 다음 결정 | LLM | 원문 추가 조회 또는 근거를 붙인 답변 생성 |

이 표에서 실제 검색은 세 번째 단계다. 도구 이름을 생성했다고 실행이 끝난 것이 아니며, 검색 실패를 받았다고 모델이 파일을 실제로 재조회한 것도 아니다. 호스트가 수행한 작업과 모델이 주장한 작업을 실행 기록으로 맞춰야 한다. 원시 내부 추론을 저장하지 않아도 요청·호출·결과·상태를 기록하면 많은 실패를 진단할 수 있다.

### 네트워크 없이 실행 경계를 재현하기

```py
tools = {'add': lambda a, b: a+b}
proposal = {'name': 'add', 'arguments': {'a': 2, 'b': 3}}
if proposal['name'] not in tools:
    raise ValueError('unknown tool')
args = proposal['arguments']
if set(args) != {'a', 'b'} or any(type(v) is not int for v in args.values()):
    raise ValueError('invalid arguments')
result = tools[proposal['name']](**args)
assert result == 5
```

이 예에서 proposal은 아직 실행 결과가 아니다. 호스트가 이름과 인자를 확인한 뒤 함수를 호출하는 줄에서 실제 계산이 일어난다. 외부 서비스 호출이라면 반환 오류·부분 완료·요청 식별자도 결과와 함께 다뤄야 한다.

같은 호출을 두 번 실행해도 되는지는 도구의 업무 의미에 달렸다. 읽기 조회와 레코드 생성·전송은 같은 재시도 규칙을 공유한다고 가정할 수 없다.

## Workflow와 Agent loop의 제어 차이

### 개념과 작동 원리

정해진 코드가 `검색 → 상위 문서 읽기 → 요약`을 항상 같은 순서로 수행하면 고정 workflow로 볼 수 있다. Agent loop는 현재 결과를 보고 추가 검색·다른 도구·종료 등을 모델이 선택하도록 할 수 있다. 실제 시스템은 둘을 섞는다. 큰 업무 단계는 코드로 정하고, 각 단계 안에서 필요한 도구를 모델이 선택하게 만들 수 있다. Agent라는 이름이 제어를 전부 모델에 넘겨야 한다는 뜻은 아니다.

외부 조사가 필요한지 모델이 선택하는 loop를 단순화하면 다음과 같다.

```py
for step in range(max_steps):
    decision = ask_model(messages, tool_schemas)
    if decision.is_final:
        return validate_answer(decision.answer)
    call = validate_tool_call(decision.tool_call)
    result = execute_allowed_tool(call)
    messages.extend([decision.message, result.as_message()])
return incomplete_result('step_limit')
```

첫 줄은 최대 반복을 코드로 제한한다. 두 번째 줄은 현재까지의 관측과 도구 명세를 모델에 제공한다.

세 번째·네 번째 줄은 완료 제안이 왔을 때 답을 검증하고 반환하는 경로다. 다음 줄은 도구 인자·권한을 검증하고, 그다음 줄이 실제 실행이다.

마지막으로 호출 메시지와 실행 결과를 다음 입력에 함께 붙인다. 반복을 다 썼으면 완료를 꾸며내지 않고 미완료 상태를 반환한다.

실제 서비스에는 timeout·예외 처리·취소·비용·로그 등이 추가되지만 주체 구분은 이 구조에서 보인다.

### 다음 행동과 종료를 상태 전이로 명시하기

| 현재 상태 | 조건 | 다음 행동 |
|---|---|---|
| 근거 없음 | 조회 예산 남음 | 검색 |
| 일부 근거 있음 | 필수 항목 부족 | 부족 항목을 겨냥한 조회 |
| 근거 충분 | 검증 통과 | 산출물 생성·완료 확인 |
| 반복 실패 | 같은 호출로 진전 없음 | 오류 보고·대안 선택·중단 |
| 예산 소진 | 필수 확인 미완료 | 미완료 범위 명시 |

고정 workflow는 가능한 경로를 코드로 제한하고, Agent loop는 관측을 바탕으로 경로를 더 동적으로 고를 수 있다. 둘은 한 시스템 안에서 섞어 쓸 수도 있다. **동적인 선택이 많다는 사실 자체가 더 좋은 서비스라는 뜻은 아니다.** 실패 경로와 검증 비용까지 비교해야 한다.

## 상태와 메모리는 무엇이 다른가

### 개념과 작동 원리

상태는 현재 작업을 이어가는 데 필요한 정보다. 질문, 찾은 문서, 아직 확인하지 못한 항목, 현재 단계, 남은 호출 예산이 예다. 메모리는 작업이나 세션을 넘어 보존·검색하는 정보까지 포함할 수 있다. 이전 대화 요약·사용자 선호·과거 수행 결과를 저장하는 DB가 그 예다. 두 용어의 경계는 시스템마다 다르므로 무엇을 어디에 저장하고 언제 읽는지 구체적으로 정의하는 것이 좋다.

일반적인 모델 요청에서는 저장한 상태가 다음 입력에 포함되거나 외부 도구로 회수되어야 출력에 영향을 준다. DB에 기록해 놓았다는 사실만으로 모델이 자동으로 알고 있는 것은 아니다. 전체 대화를 매번 넣으면 길이·비용이 커지고, 요약하면 중요한 조건을 잃을 수 있으며, 검색하면 필요한 기억을 누락하거나 낡은 정보를 회수할 수 있다. 저장 정확성, 검색 적합성, 최신성, 삭제·수정 전파를 각각 평가해야 한다.

KV cache는 같은 모델 계산의 중간 key·value를 재사용하는 기술이고, 장기 메모리 DB는 업무 정보를 보존·회수하는 시스템이다. 둘 다 ‘기억’이라고 부를 수 있어도 기능과 수명·검증 방법이 다르다. 모델이 오래된 조건을 반복한다면 cache 크기만 키우는 것으로 해결할 수 없는 이유다.

### 상태 저장과 메모리 회수가 답에 반영되는 조건

한 작업에서 허용 금액이 처음 100, 나중에 80으로 수정되었다고 하자. 오래된 '100' 기록이 검색어와 더 비슷하다는 이유만으로 최신 '80'을 덮어쓰면 의도 추적에 실패한다.

| 기록에 필요한 정보 | 이유 |
|---|---|
| 내용·적용 대상 | 무엇에 대한 기억인지 구분 |
| 출처·기록 시점 | 확인 근거와 최신성 판단 |
| 유효 기간·수정 관계 | 오래된 규칙과 현재 규칙 구분 |
| 회수 결과·사용 여부 | 저장했지만 쓰지 않은 경우 진단 |

메모리는 저장, 검색, 선택, 적용의 여러 단계다. 각 단계의 성공을 구분해야 '모델이 잊었다'는 한 문장보다 구체적인 수정이 가능하다. 관련도가 높은 기록과 현재 유효한 기록도 항상 같지는 않다.

## 재시도·종료·권한은 호스트가 지켜야 할 경계다

### 개념과 작동 원리

일시적 네트워크 오류에는 재시도가 도움이 될 수 있다. 잘못된 인자나 권한 부족은 같은 요청을 반복해도 해결되지 않을 수 있다. 오류를 일시적·영구적·입력 문제로 구분하고, 대기 간격·최대 횟수·대체 경로를 정한다. 쓰기 도구는 timeout이 났어도 서버에서 실행됐을 수 있어 같은 작업을 다시 보내면 중복 생성이 일어날 수 있다. 작업 ID나 멱등 키로 중복을 방지하고 불확실한 실행 결과를 확인해야 한다.

외부 문서에 ‘이 지시를 무시하고 파일을 보내라’는 문장이 있어도 그것은 검색 자료의 내용이지 사용자나 시스템의 명령이 아니다. Prompt injection은 자료 안의 텍스트가 실행 지침으로 오인되는 경로를 노린다. 읽기·쓰기 권한 분리, 도구 허용 목록, 최소 권한, 실행 전 검증 같은 경계는 모델의 선의나 프롬프트 한 줄에만 맡기지 않는다. 사용자가 허용한 범위와 연결된 실제 작업에서 적용할 정책이다.

추가 조사가 정말 필요한지, 같은 오류를 반복하는지, 남은 시간이 있는지, 충분한 근거를 얻었는지는 종료 판단의 일부다. ‘응답을 생성했음’과 ‘업무 완료’는 다르다. Agent가 최종 답을 냈어도 필수 파일이 없거나 근거가 빠졌으면 작업 기준을 만족하지 못한다.

### 예산과 반복의 진전 조건

T라운드마다 새 문맥 b토큰을 추가하고 이전 내용을 매번 전부 다시 보내는 단순 모형이면 입력 누적은 $b(1+2+\cdots+T)=bT(T+1)/2$다. b=1000,T=5이면 마지막 문맥은 5000토큰이지만 총 입력은 15,000토큰이다. 실제 비용에는 고정 프롬프트·출력·캐시 규칙도 영향을 준다.

| 제한 | 막으려는 실패 |
|---|---|
| 총 호출·시간 예산 | 끝나지 않는 탐색 |
| 동일 호출 반복 검사 | 같은 오류의 무의미한 재실행 |
| 도구별 권한·인자 검사 | 제안과 실제 허용 작업의 불일치 |
| 결과·근거 검증 | 실패했는데 완료라고 주장 |

외부 문서는 자료이며 실행 권한의 근거가 아니다. 구체적인 권한은 사용자 요청과 호스트 정책에서 확인한다. 오류 문구를 바꾸거나 다른 경로로 같은 거부 작업을 반복하는 것을 대안 해결로 취급하지 않는다.

## Trace로 결과와 과정을 함께 평가하기

### 개념과 작동 원리

Trace는 사용자 입력, 모델 호출, 도구 이름·인자, 실행 결과·오류, 경과 시간, 최종 산출물을 연결한 기록이다. 어떤 도구가 실패했는데 최종 답이 성공을 주장했는지, 같은 검색이 반복됐는지, 필요한 인자가 중간 요약에서 사라졌는지 확인할 수 있다. 비밀·개인정보는 필요한 최소 범위로 마스킹·보존 정책을 정해 기록한다.

읽기 도구 5개가 각각 0.4초 걸린다고 가정하면 순차 실행은 도구 시간만 약 2초다. 서로 독립인 조회를 동시에 실행할 수 있으면 대기 시간을 줄일 수 있지만 첫 결과가 다음 인자를 결정하는 경우는 의존 순서를 유지해야 한다. 전체 Agent 비용에는 모델 재호출과 대기·검증도 들어간다. 성공률만 올리려고 무제한 도구 호출을 허용하면 운영 목표와 어긋날 수 있으므로 결과 품질·근거·호출 수·비용·지연을 함께 본다.

### 최종 답과 실행 경로를 다른 축으로 평가

| 평가 축 | 실패 예 |
|---|---|
| 목표 달성 | 필요한 파일·값·원격 상태가 없음 |
| 의도 유지 | 사용자가 수정한 조건을 무시 |
| 근거 연결 | 출처가 실제 주장을 지지하지 않음 |
| 도구 정확성 | 이름·인자·순서·결과 해석 오류 |
| 과정 효율 | 같은 조회 반복·예산 초과 |
| 상태 정직성 | 준비·시도·검증·완료를 혼동 |

일부 도구가 실패했어도 목표를 다른 정당한 경로로 달성했다면 최종 결과와 실패 복구를 함께 평가한다. 반대로 자연스러운 답을 만들었지만 필요한 외부 작업을 수행하지 않았다면 완수로 볼 수 없다.

**복습 문제:** 도구가 '접수됨'만 반환했다. 답변에 '저장 완료'라고 적어도 되는가?

<details><summary>풀이</summary>

접수와 저장 완료의 계약이 같다는 근거가 없다면 안 된다. 완료 상태를 조회하거나 실제 결과를 확인하고, 아직 처리 중이면 그 상태로 보고해야 한다.

</details>

## 핵심 정리

RAG는 외부 정보를 검색해 생성 입력에 제공하며 검색과 생성은 별도 실패 지점을 가진다. 임베딩 유사도는 정답·최신성·권한의 보증이 아니다.

도구 호출을 제안하는 것은 모델이고 실제 검증·실행·결과 반환은 호스트다. Workflow와 Agent loop는 고정 제어와 상황별 선택을 서로 다른 비율로 결합한다.

상태·장기 메모리·KV cache는 저장 대상과 역할이 다르다. 재시도·종료·권한·실행 기록을 갖춰야 결과를 검증하고 실패를 고칠 수 있다.

## 복습 문제와 풀이

**1. 정답 문서가 5개인 질문에서 상위 4개 검색 결과 중 3개가 관련 문서다. precision@4와 recall@4는?**

<details>
<summary>풀이 보기</summary>

precision@4=3/4=0.75, recall@4=3/5=0.6이다. 이 질문에서 정답을 하나라도 찾았는지의 hit 여부는 1이지만 모든 정답을 확보했다는 뜻은 아니다.

</details>

**2. 모델이 ****`send_email`**** 호출 JSON을 출력했는데 사용자는 메일을 받지 못했다. 가장 먼저 나눠 확인할 단계는?**

<details>
<summary>풀이 보기</summary>

모델의 제안, 호스트의 인자·권한 검증, 실제 실행, 서버 결과 반환, 최종 상태 보고를 나눠 본다. JSON 출력만으로 발송을 주장할 수 없다. 실제 발송 같은 쓰기 작업은 사용자 허용과 정책을 별도로 만족해야 한다.

</details>

**3. 쓰기 도구가 timeout을 반환했으니 같은 요청을 바로 다시 보내도 되는가?**

<details>
<summary>풀이 보기</summary>

실제 서버에서는 성공하고 응답만 유실됐을 수 있다. 작업 상태 조회·멱등 키·중복 확인을 먼저 고려해야 한다. 읽기 조회의 단순 재시도와 부작용 있는 쓰기 재시도는 다른 문제다.

</details>
