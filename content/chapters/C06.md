# 운영체제는 실행과 메모리, 저장을 안전하게 나누어 준다

편집기에서 코드를 쓰면서 브라우저를 열고 학습 프로그램을 실행할 수 있다. 각 프로그램은 자신에게 CPU와 메모리, 파일이 있는 것처럼 동작하지만 실제 하드웨어는 공유한다.

운영체제는 이 자원들을 배분하고 서로의 데이터를 함부로 바꾸지 못하게 보호한다. 핵심 추상화는 **실행 중인 프로그램인 프로세스**, **독립된 주소 공간**, **지속적으로 남는 파일**이다.

이를 이해하면 서버가 느려진 이유가 CPU 경쟁인지, I/O 대기인지, 메모리 압박인지 나누어 볼 수 있다.


## 프로세스와 시스템 호출

### 개념과 작동 원리

프로그램은 저장된 코드와 데이터이고 프로세스는 그것을 실행하는 상태다. 같은 실행 파일을 두 번 켜면 보통 별개의 프로세스가 생긴다. 프로세스에는 다음에 실행할 명령 위치, 레지스터 상태, 주소 공간, 열린 파일, 권한 같은 정보가 있다. 운영체제는 이런 상태를 관리해 어느 프로세스를 멈췄다가 나중에 이어 실행할 수 있다.

프로그램이 디스크나 네트워크 장치를 원하는 대로 직접 제어하면 다른 프로그램의 데이터를 읽거나 장치를 독점할 수 있다. 그래서 하드웨어와 OS는 사용자 모드와 커널 모드 같은 권한 경계를 둔다. 파일 열기·프로세스 생성처럼 보호된 기능은 시스템 호출을 통해 요청한다. 일반 함수 호출과 비슷한 모양으로 사용해도 내부에서는 권한 경계와 커널의 검사를 거친다. 라이브러리 함수 한 번이 시스템 호출 한 번과 항상 일치하지는 않는다.

Unix 계열의 `fork`는 현재 프로세스를 바탕으로 자식 프로세스를 만들고 `exec`는 프로세스의 실행 내용을 다른 프로그램으로 바꾼다. `wait`는 부모가 자식의 종료 상태를 기다리고 수거하게 한다. 이 조합을 이해하면 셸이 명령을 실행한 뒤 프롬프트로 돌아오는 과정을 설명할 수 있다. 자식 프로세스의 종료를 수거하지 않으면 종료 정보가 남은 좀비 상태가 생길 수 있다.

```c
int x = 1;
pid_t pid = fork();
if (pid == 0) { x = 2; printf("child: %d\n", x); }
else if (pid > 0) { wait(NULL); printf("parent: %d\n", x); }
```

오류 처리와 헤더를 생략한 개념 예제다. fork 뒤 두 프로세스는 같은 이름 x를 갖지만 일반적인 프로세스 메모리는 분리되어 있다. 자식이 자기 x를 2로 바꾸어도 부모의 x는 1이다. `wait` 때문에 부모의 출력은 자식 종료 뒤에 나온다. 실제 구현은 copy-on-write 등으로 물리 페이지 복사를 미룰 수 있지만, 이 최적화가 일반 쓰기를 통해 부모와 자식의 메모리가 무조건 공유된다는 뜻은 아니다.

파일 디스크립터는 프로세스가 열린 파일·소켓 등에 접근하는 작은 정수 핸들이다. 셸의 리다이렉션과 파이프는 이런 입출력 연결을 바꾸어 구현할 수 있다. fork 이후 어떤 열린 상태가 어떻게 공유·상속되는지, exec에서 어떤 핸들이 유지되는지는 별도 규칙이 있으므로 메모리 복사와 같은 이야기로 뭉뚱그리지 않는다.

### 생성·실행 교체·회수를 다른 사건으로 읽기

| 동작 | 개념 | 혼동하기 쉬운 점 |
|---|---|---|
| fork | 기존 프로세스를 바탕으로 자식 생성 | 부모와 자식이 동일 프로세스인 것은 아님 |
| exec 계열 | 현재 프로세스의 실행 이미지를 교체 | 성공하면 원래 호출 지점으로 복귀하지 않음 |
| wait 계열 | 자식 종료 상태를 기다리거나 확인 | CPU 작업을 대신 수행하는 함수 아님 |
| 시스템 호출 | 커널 서비스를 요청 | 항상 디스크 I/O가 발생하는 것은 아님 |

copy-on-write를 사용하는 가상 모형에서 부모가 쓰는 페이지 100개를 자식과 공유하다가 자식이 3개 페이지를 변경하면, 해당 쓰기를 처리하며 일부 페이지를 복사할 수 있다. 처음부터 모든 데이터 100페이지를 즉시 복사하는 것과 다르다. 페이지 테이블·관리 정보·구현별 비용은 별도다.

프로세스 생성 비용을 소스코드 줄 수만으로 추정할 수 없다. 주소 공간, 자원 상태와 실제 구현을 함께 본다. [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/)의 Process API·Direct Execution 단원을 참고한다.

## 스레드와 스케줄링

### 개념과 작동 원리

스레드는 한 프로세스 안의 실행 흐름이다. 같은 프로세스의 스레드는 보통 주소 공간과 많은 자원을 공유하지만 각자 명령 위치·레지스터·호출 스택을 가진다. 따라서 한 스레드가 힙의 리스트를 바꾸면 다른 스레드도 볼 수 있는 반면 함수의 미완료 호출 상태는 스레드마다 구분된다. 프로세스를 나누면 격리와 별도 통신이 중요해지고 스레드를 나누면 공유 데이터 동기화가 중요해진다.

실행 가능한 스레드 수가 CPU 코어보다 많으면 운영체제는 일부를 실행하고 일부를 기다리게 한다. 문맥 전환은 현재 실행 상태를 저장하고 다른 상태를 복원하는 작업이다. I/O가 끝나길 기다리는 스레드는 runnable 상태로 CPU를 계속 쓰는 것과 다르다. CPU를 쓰고 싶은 작업이 많아서 기다리는지, 파일·네트워크 응답을 기다리는지 구분해야 지연 원인을 찾을 수 있다.

FCFS는 도착한 순서대로 처리한다. 단순하지만 긴 작업 하나가 앞을 막으면 뒤의 짧은 작업도 오래 기다릴 수 있다.

Round-robin은 시간 할당량을 주고 번갈아 실행한다. 할당량이 너무 길면 짧은 작업의 응답이 늦고 너무 짧으면 전환 부담이 커질 수 있다.

MLFQ는 여러 우선순위 큐를 사용해 작업의 행동에 따라 배치를 조정한다. 처음에는 빨리 반응하게 하면서 오래 CPU를 쓰는 작업과 짧은 대화형 작업을 구분하려는 설계다.

실제 OS의 정책은 더 복잡하므로 이들은 원리를 이해하는 모델이다.


응답시간은 첫 반응까지, 반환시간은 완료까지, 대기시간은 실행을 기다린 시간을 가리킨다. 한 정책이 모든 지표에서 항상 최선은 아니다. 공정성과 처리량, 우선순위와 굶주림 방지의 균형을 따져야 한다. 우선순위가 낮은 작업이 계속 밀리면 장기적으로 실행 기회를 보장하는 방법이 필요하다.

### Round Robin은 어떤 지연을 줄이는가

도착 시각이 모두 0이고 CPU 작업 A=6ms, B=4ms이며 I/O·전환 비용이 없는 모형을 생각하자. FCFS에서 A를 먼저 처리하면 A는 6ms, B는 10ms에 끝난다. 양자 2ms의 Round Robin은 다음과 같다.

| 시간 구간 | 실행 | 남은 CPU 작업 |
|---|---|---|
| 0~2 | A | A 4, B 4 |
| 2~4 | B | A 4, B 2 |
| 4~6 | A | A 2, B 2 |
| 6~8 | B | A 2, B 0 |
| 8~10 | A | A 0, B 0 |

B가 처음 실행되는 시간은 FCFS의 6ms에서 2ms로 줄지만, 평균 완료 시간은 FCFS 8ms, RR 9ms다. **첫 응답·완료 시간·처리량은 서로 다른 지표**다. 양자를 작게 하면 반응성이 좋아질 수 있지만 전환 횟수가 늘어 실제 비용이 추가된다.

## 주소 공간, 스택, 힙

### 개념과 작동 원리

프로세스가 사용하는 주소는 보통 가상 주소다. 전형적인 주소 공간에는 코드, 전역·정적 데이터, 동적 할당을 위한 힙, 스레드별 호출 스택, 공유 라이브러리·메모리 매핑 영역 등이 있다. “힙은 아래에서 위로, 스택은 위에서 아래로” 같은 그림은 특정 전형적 배치를 설명하는 모델이며 모든 언어·OS·실행에서 주소와 방향이 고정된다는 보장은 아니다.

스택은 함수 호출의 지역 상태와 복귀에 필요한 정보를 관리하는 데 쓰인다. 자동 저장 기간의 블록 지역 변수는 블록을 벗어나면 수명이 끝난다.

힙의 동적 영역은 함수 호출보다 오래 살 수 있고 해제 규칙을 따로 가진다. C의 `static` 지역 변수는 이름의 범위는 지역이지만 저장 기간은 프로그램 전체이므로 “지역 변수는 모두 함수 끝에 사라진다”라고 일반화하지 않는다.

Python 객체의 수명은 참조·런타임 규칙으로 결정되며 C 자동 지역 변수의 수명과 같지 않다.


이 주소 공간은 물리 RAM을 그대로 펼친 지도가 아니다. 서로 다른 프로세스에서 같은 가상 주소값을 사용해도 다른 물리 페이지에 대응할 수 있다. 반대로 명시적 공유 메모리나 읽기 전용 코드 페이지처럼 여러 프로세스가 같은 물리 페이지를 매핑할 수도 있다. 격리·공유·보호를 물리 메모리 배치와 독립적으로 설계할 수 있다는 것이 가상 메모리의 장점이다.

### 가상 주소의 같음과 물리적 공유를 구분하기

프로세스 P와 Q가 모두 가상 주소 0x1000을 사용해도 서로 다른 물리 프레임을 가리킬 수 있다. 반대로 공유 매핑을 설정하면 서로 다른 가상 주소가 같은 물리 저장 영역을 가리킬 수 있다.

| 저장 영역 | 전형적인 용도 | 중요한 구별 |
|---|---|---|
| 코드 | 실행할 명령 | 주소 공간의 일부 |
| 힙 | 동적으로 관리하는 객체 | 할당기와 OS의 관리 단위가 다름 |
| 스레드별 스택 | 호출·자동 저장 등의 실행 상태 | 스레드 간 독립 주소 공간이라는 뜻은 아님 |
| 공유 매핑 | 프로세스 간 공유·파일 매핑 | 공유 여부를 매핑과 권한으로 판단 |

같은 프로세스의 스레드는 주소 공간을 공유하므로 유효한 포인터를 전달하면 다른 스레드 스택의 객체에 접근할 수도 있다. '각자 스택이 있다'는 말은 하드웨어가 다른 스레드의 스택을 무조건 격리한다는 뜻이 아니다. 그 객체의 수명과 동기화 문제는 별도로 해결해야 한다.

## 페이징과 주소 변환

### 개념과 작동 원리

페이징은 가상 주소 공간과 물리 메모리를 고정 크기 조각인 페이지·프레임으로 나누어 대응시키는 방법이다. 가상 주소는 가상 페이지 번호와 페이지 내부 offset으로 나눌 수 있다. 페이지 테이블은 가상 페이지가 어떤 물리 프레임에 매핑되며 읽기·쓰기 같은 권한이 무엇인지 나타낸다. 프로세스가 큰 연속 가상 영역을 써도 실제 프레임은 RAM 여기저기에 있을 수 있다.

학습용으로 페이지 크기를 4,096바이트라고 하자. 가상 주소 0x1234는 페이지 번호 1, offset 0x234로 나뉜다. 페이지 1이 물리 프레임 9에 대응하면 물리 주소는 0x9000+0x234=0x9234다. offset은 그대로이고 페이지 번호 부분의 매핑이 바뀐 것이다. 실제 시스템의 페이지 크기와 다단계 테이블·큰 페이지 사용 여부는 별도지만 이 분해 원리는 같다.

주소를 읽을 때마다 RAM의 페이지 테이블을 여러 번 확인하면 비용이 커질 수 있다. TLB는 최근 주소 변환 결과를 보관하는 하드웨어 캐시다. CPU 데이터 캐시는 데이터 내용을, TLB는 주소 변환 정보를 보관한다. TLB miss가 나면 매핑 정보를 찾는 과정이 필요하지만 그것만으로 데이터가 디스크에 있다는 뜻은 아니다. 데이터 캐시 miss·TLB miss·page fault는 서로 다른 사건이다.

Page fault는 해당 접근을 현재 매핑·상태로 바로 완료할 수 없을 때 OS가 처리하는 예외다. 아직 실제 메모리를 배정하지 않은 페이지에 처음 쓰는 경우, copy-on-write 사본이 필요한 경우, 저장장치에서 페이지를 가져와야 하는 경우 등이 있다.

따라서 모든 page fault가 느린 디스크 읽기는 아니다. 접근 자체가 허용되지 않으면 오류가 될 수 있다.

실행 중 swap이 많아지면 저장장치 대기로 성능이 크게 떨어질 수 있지만 가상 메모리 전체를 swap과 동일시해서는 안 된다.


페이지 테이블을 두는 데도 메모리가 든다. 주소 공간이 크고 실제로 일부만 쓰면 다단계 구조로 사용하지 않는 범위의 테이블을 생략하는 것이 유리하다. 페이지를 크게 하면 변환 항목 수를 줄일 수 있지만 작은 데이터에 낭비가 늘거나 배치 제약이 생길 수 있다. 어떤 단위로 관리하든 관리 비용과 내부 낭비 사이의 교환관계가 있다.

### 페이지 번호와 offset을 계산해 변환하기

페이지 크기 4096바이트, 가상 주소 0x12345라면 가상 페이지 번호는 0x12, offset은 0x345다. 가상 페이지 0x12가 물리 프레임 0xAB에 대응하면 물리 주소는 0xAB345다.

```py
page_size = 4096
virtual_address = 0x12345
vpn, offset = divmod(virtual_address, page_size)
frame = {0x12: 0xAB}[vpn]
physical_address = frame*page_size + offset
assert vpn == 0x12 and offset == 0x345
assert physical_address == 0xAB345
```

| 사건 | 의미 | 디스크 읽기가 항상 필요한가 |
|---|---|---|
| TLB hit | 주소 변환 캐시에 대응이 있음 | 아님 |
| TLB miss | 해당 캐시에 변환이 없음 | 아님; 페이지 테이블 탐색으로 해결 가능 |
| page fault | 접근을 그대로 완료할 수 없어 OS 처리 필요 | 아님; zero-fill·copy-on-write 등도 가능 |

페이지 테이블이 어떻게 구성되는지에 따라 탐색 단계와 저장 비용이 달라진다. 모든 주소 변환을 무조건 해시 O(1)이라고 설명하지 않는다. [OSTEP 페이징 장](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-paging.pdf)의 페이지·프레임 대응을 참고한다.

## 동적 할당과 단편화

### 개념과 작동 원리

`malloc`은 요청한 바이트를 사용할 영역으로 돌려주고 `free`는 재사용할 수 있게 반환한다. 보통 매 호출마다 OS에서 새 페이지를 받는 것이 아니라 할당기가 큰 영역을 받아 잘게 나누고 빈 블록을 관리한다. 블록 크기·사용 여부를 기록하는 metadata, 정렬 조건, 빈 블록 탐색·병합 전략이 성능과 낭비를 좌우한다. Python 같은 런타임의 객체 할당도 그 위나 옆에서 별도 관리 정책을 가질 수 있다.

내부 단편화는 할당 단위나 정렬 때문에 요청보다 큰 블록 안에 남는 낭비다. 외부 단편화는 빈 공간 총합은 충분해도 떨어진 작은 조각으로 나뉘어 필요한 연속 블록을 만들지 못하는 상황이다. 둘은 “RAM이 남는다”라는 한 수치로 구별되지 않는다.

![24B 연속 할당은 왼쪽 배치에서는 실패하고 오른쪽에서는 가능합니다. 물리 메모리·가상 메모리 전체 구조를 나타내는 그림은 아닙니다.](/figures/C06.svg)

24B 연속 할당은 왼쪽 배치에서는 실패하고 오른쪽에서는 가능합니다. 물리 메모리·가상 메모리 전체 구조를 나타내는 그림은 아닙니다.

그림의 왼쪽은 64바이트 힙을 사용16·빈16·사용16·빈16으로 나눈 학습용 예다. 빈 공간 합계는 32바이트지만 가장 큰 연속 빈 블록은 16바이트라서 24바이트 요청을 넣지 못한다.

오른쪽은 사용32·빈32이므로 같은 총 여유 32바이트에서 24바이트 요청이 가능하다. 이 그림은 정렬과 metadata를 생략했다.

또한 이미 사용 중인 블록을 실제 할당기가 임의로 옮겨 오른쪽 배치로 만들 수 있다는 뜻은 아니다. C 포인터가 기존 주소를 보관하는 상황에서는 이동에 제약이 있고, 인접한 빈 블록의 병합과 사용 중 블록의 이동은 다른 작업이다.


해제 뒤 메모리 수치도 층별로 읽어야 한다. 프로그램에 참조가 남은 객체는 사용 중이다. 참조가 없어 객체를 회수해도 런타임이나 할당기는 재사용하려고 영역을 보유할 수 있다. RSS는 OS 관점의 상주 메모리이며 Python 객체 바이트 수나 GPU 예약 메모리와 같지 않다. OOM은 메모리 요구와 자원 정책의 문제지만 관측한 큰 수치가 모두 누수라는 결론은 성급하다. 어느 층에서 무엇이 늘고 있는지 시간에 따라 비교한다.

### 내부 낭비와 연속 공간 부족을 따로 계산하기

최소 할당 단위가 16바이트인 가상 할당기에서 17바이트를 요청해 32바이트를 받으면 내부 낭비는 15바이트다. 이는 객체 내부가 아니라 **할당 블록 안의 미사용 공간**을 뜻한다.

빈 연속 영역이 각각 8,8,16바이트이고 사이에 사용 중인 블록이 있다면 총 빈 공간은 32바이트다. 그래도 24바이트 연속 블록을 바로 제공하지 못할 수 있다. 인접한 빈 블록이 아니라면 단순 병합으로 해결할 수 없다.

| 문제 | 관찰해야 할 양 | 흔한 오해 |
|---|---|---|
| 내부 단편화 | 실제 요청 대비 할당량 | 여유 바이트를 언제나 다른 객체에 사용 가능 |
| 외부 단편화 | 빈 영역의 크기와 배치 | 총 여유량만 충분하면 연속 할당도 가능 |
| 메모리 누수 | 해제·회수되지 않는 불필요 객체 | 단편화와 동일한 현상 |

위 숫자는 정렬·메타데이터 비용을 생략한 모형이다. paging은 가상 연속 영역을 물리적으로 떨어진 프레임에 연결할 수 있지만, 사용자 공간 할당기의 모든 단편화까지 자동으로 없애지는 않는다.

## 동기화와 경쟁 상태

### 개념과 작동 원리

공유 카운터에 1을 더하는 작업을 “읽기→계산→쓰기”로 나누어 보자. 두 스레드가 모두 0을 읽은 뒤 각각 1을 저장하면 두 번 증가시켰는데 1이 된다. 실행 순서에 따라 결과가 달라지는 경쟁 상태다. 언어의 한 줄이 하드웨어·런타임에서 하나의 분리 불가능한 연산이라는 뜻은 아니다. CPython의 GIL이나 특정 버전에서 관찰한 우연한 실행 순서에 공유 데이터의 정확성을 맡기지 않는다.

```py
from threading import Barrier, Thread
counter = 0
barrier = Barrier(2)

def add_once():
    global counter
    old = counter
    barrier.wait()  # 둘 다 읽은 뒤에만 저장하도록 맞춘다
    counter = old + 1

threads = [Thread(target=add_once) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)  # 두 스레드가 old=0을 읽어 최종 1
```

Barrier는 여기서 오류를 재현하기 위한 도구다. 두 스레드가 기존 값을 읽은 후에만 다음 단계로 가게 해 잃어버린 갱신을 드러낸다. 올바르게 만들려면 읽기와 계산·쓰기 전체를 하나의 임계 구역으로 보호하거나 해당 자원에 맞는 원자 연산을 사용한다. lock으로 쓰기 한 줄만 감싸고 오래된 값을 미리 읽으면 문제가 남는다.

Mutex는 한 번에 하나의 실행 흐름만 임계 구역에 들어가게 한다. 조건변수는 “큐에 데이터가 들어왔다” 같은 조건이 바뀔 때까지 효율적으로 기다리게 한다. 기다림에서 깨어나도 조건이 여전히 맞는지 반복문으로 다시 확인해야 한다. 세마포어는 사용 가능한 자원 수를 카운터로 표현할 수 있어 연결 수·버퍼 슬롯 제한에 쓰인다. 모두 같은 도구가 아니라 보호할 상태와 기다릴 조건이 무엇인지에 따라 고른다.

### 경쟁 상태의 순서를 고정해서 이해하기

두 스레드가 공유값 0을 각각 읽고 1을 쓰면 결과가 1이 된다. 잠금은 읽기·변경·쓰기를 같은 임계구역에 묶고 **모든 관련 접근이 같은 규약을 따를 때** 이를 보호할 수 있다.

| 순서 | 잠금 없는 A | 잠금 없는 B |
|---|---|---|
| 1 | 0 읽음 | |
| 2 | | 0 읽음 |
| 3 | 1 저장 | |
| 4 | | 1 저장 |

정수 한 번 쓰기가 원자적이라는 가정을 하더라도 전체 읽기-수정-쓰기까지 원자적이라는 결론은 따라오지 않는다. 단일 코어에서도 실행 흐름이 중간에 바뀌면 논리적 경쟁이 생길 수 있다.

락을 오래 보유하면 다른 작업이 기다린다. 같은 임계구역을 모든 작업이 통과해야 하면 그 부분의 처리량은 직렬 구간이 제한한다. 락을 추가했다는 사실만이 아니라 보호할 불변식·접근 경로·락 획득 순서를 설명해야 한다. [OSTEP Locks 장](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-locks.pdf)을 참고한다.

## 교착상태와 파일의 지속성

### 개념과 작동 원리

스레드 A가 lock1을 잡고 lock2를 기다리며 B가 lock2를 잡고 lock1을 기다리면 둘 다 진행하지 못한다. 교착상태에는 상호배제, 자원을 잡은 채 다른 자원을 기다림, 강제 회수 불가, 순환 대기라는 조건이 함께 관여한다. 여러 lock을 항상 같은 순서로 얻도록 하면 순환을 막는 데 도움이 된다. timeout으로 기다림을 끊을 수는 있지만 실패 시 이미 잡은 자원을 어떻게 풀고 재시도할지도 정해야 한다.

파일은 프로세스가 종료되어도 남는 바이트열을 이름과 메타데이터로 관리하는 추상화다. 디렉터리는 이름과 파일을 연결하고 파일 시스템은 데이터 블록·메타데이터·빈 공간을 관리한다. 파일을 읽고 쓰는 API와 실제 저장장치 갱신 사이에는 사용자 버퍼와 OS 페이지 캐시가 있을 수 있다. `write`가 반환했다는 사실, 언어 버퍼가 flush되었다는 사실, 데이터가 전원 장애 뒤에도 남도록 동기화되었다는 사실을 구분한다.

전원 장애가 파일 데이터와 메타데이터 갱신 중간에 발생하면 구조가 일관되지 않을 수 있다. 저널링은 변경 기록을 이용해 복구 시 어떤 갱신을 반영할지 결정하는 방법이다.

그러나 파일 시스템의 구조적 복구가 애플리케이션의 모든 업무 트랜잭션을 자동 보장하지는 않는다. 임시 파일 작성 뒤 rename 같은 패턴을 쓰더라도 원하는 원자성·내구성의 범위와 OS·파일 시스템의 보장을 확인해야 한다.

운영체제의 추상화를 이해한다는 것은 API 이름뿐 아니라 성공·실패가 의미하는 경계를 이해하는 일이다.


### 진행 보장과 저장 보장을 다른 축으로 확인하기

lock1과 lock2를 동시에 써야 한다면 모든 스레드가 lock1→lock2 순서로 획득하도록 하는 방식은 순환 대기를 막는 한 방법이다. 타임아웃으로 일부 대기를 끊을 수도 있지만, 부분 작업을 어떻게 되돌릴지는 별도로 설계해야 한다.

| 파일 작업 단계 | 확인한 것 | 아직 별도로 필요한 것 |
|---|---|---|
| 사용자 버퍼 flush | 런타임 버퍼를 아래 층으로 전달 | 영구 저장 완료 여부 |
| write 성공 | 커널의 쓰기 요청 처리 결과 | 장애 후 지속성 |
| fsync 성공 | 해당 파일의 저장 동기화 결과 | 새 디렉터리 항목 등 관련 메타데이터의 별도 조건 |

Linux에서는 파일 자체에 fsync를 했다고 그 파일을 가리키는 디렉터리 항목까지 반드시 동기화된 것은 아니다. [fsync 공식 매뉴얼](https://man7.org/linux/man-pages/man2/fsync.2.html)의 파일·디렉터리 구분을 확인한다. 저널링의 구조적 일관성과 애플리케이션의 업무 트랜잭션 원자성도 같은 보장이 아니다.

**복습 문제:** 파일 저장 함수가 반환되었지만 전원 장애 뒤 기록이 없다. 항상 프로그래밍 언어의 파일 객체 버그인가?

<details><summary>풀이</summary>

아니다. 사용자 버퍼, 커널 캐시, 파일 시스템, 장치의 지속성 계약을 구분해야 한다. 어느 함수가 어떤 완료를 보장하는지, 반환 오류를 확인했는지, 파일과 이름 변경의 순서를 어떻게 처리했는지 조사한다.

</details>

## 핵심 정리

프로세스는 실행 상태와 자원을 가진 프로그램 인스턴스이고 스레드는 공유 주소 공간 안의 실행 흐름이다. 스케줄러는 실행 기회를 나누며 CPU 경쟁과 I/O 대기는 다르다.

스택·힙은 수명·할당을 이해하는 개념이고 가상 주소는 물리 RAM 주소와 동일하지 않다. 페이징과 TLB는 주소 변환을 제공하며 page fault가 항상 디스크 읽기는 아니다.

할당기 단편화와 객체 참조, OS RSS를 구분해야 메모리 문제를 진단할 수 있다. 동기화는 공유 상태의 전체 갱신 규칙을 보호해야 한다.

파일의 API 성공과 저장장치 내구성, 애플리케이션 트랜잭션은 서로 다른 보장이다.
