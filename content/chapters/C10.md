# 분산 시스템은 여러 컴퓨터 사이의 불확실성을 다룬다

작업이 많아져 서버를 두 대로 늘렸다고 하자. 요청을 나누어 처리할 수 있지만 이제 한 서버만 죽거나, 두 서버 사이의 메시지가 늦거나, 같은 요청이 두 번 전달될 수 있다. 한 서버의 메모리에서 함께 바꾸던 상태를 서로 다른 컴퓨터에서 맞추어야 한다. 분산 시스템은 단순히 서버 수가 많은 시스템이 아니라 **통신과 부분 실패 때문에 상태를 한눈에 확정할 수 없는 시스템**을 다룬다.

## 부분 실패와 시간의 한계

단일 프로세스에서는 함수가 정상 반환했는지 예외를 던졌는지로 많은 상황을 구분할 수 있다. 원격 요청은 다르다. 서버가 요청을 받기 전에 메시지가 사라졌을 수도 있고, 처리 중 죽었을 수도 있으며, 처리 완료 뒤 응답만 사라졌을 수도 있다. 클라이언트가 본 timeout 하나로 이 경우들을 구별할 수 없다. 네트워크 대기만 길어진 정상 서버와 실제 죽은 서버를 항상 즉시 구별할 수 없는 이유다.

전체 시스템이 모두 멈추는 대신 일부만 실패할 수 있다는 점도 중요하다. API 서버는 살아 있는데 DB 연결이 끊기거나 worker 한 대만 재시작할 수 있다. 모든 구성요소가 함께 성공·실패한다고 가정하면 복구 경로를 놓친다. 각 경계에서 작업이 완료됐는지, 다시 실행해도 되는지, 불확실한 상태를 어떻게 확인할지 정해야 한다.

컴퓨터들의 시계도 완전히 같지 않다. 설정·동기화·시계 보정 때문에 timestamp 순서와 실제 사건의 인과 순서가 다를 수 있다. A가 메시지를 보낸 뒤 B가 받았다면 송신이 수신보다 인과적으로 앞서지만 기록된 벽시계 숫자가 항상 그 순서를 보여 준다고 가정하지 않는다. 논리 시계는 이런 선후 관계를 표현하는 데 도움을 주지만 모든 동시 사건의 절대적인 실제 시간을 복원하는 것은 아니다.

프로세스 안에서 경과시간을 재려면 벽시계보다 단조 증가 시계를 쓰는 편이 적절하다. 분산 요청에는 전체 deadline을 전달해 각 구간이 남은 예산을 이해하게 할 수 있다. 그러나 시계가 다른 서버 사이에서 숫자 하나를 보내면 해석을 맞춰야 한다. 시간은 편리한 도구지만 정확한 전역 순서와 실패 판정의 만능 기준은 아니다.

## 복제는 사본 수만큼 자동으로 안전해지지 않는다

복제는 데이터를 여러 노드에 보관해 장애 대응과 읽기 확장을 돕는다. 한 노드가 leader로 쓰기를 받고 follower가 변경을 따라가는 구조를 생각해보자. 비동기 복제에서는 leader가 먼저 성공을 응답하고 follower 반영은 나중일 수 있다. 그 사이 follower에서 읽으면 이전 값이 보인다. 동기적으로 충분한 사본 반영을 기다리면 더 강한 조건을 얻을 수 있지만 응답 지연과 장애 시 처리 가능성이 달라진다.

예를 들어 x=0인 leader·follower가 있다. 사용자가 leader에서 x=1 쓰기를 완료한 뒤 즉시 follower에서 읽었는데 0이 돌아올 수 있다. 이것은 저장이 아예 안 됐다는 뜻일 수도 있지만 복제 지연일 수도 있다. 사용자가 방금 쓴 값을 다시 읽을 때 보게 하는 read-your-writes 요구와, 모든 클라이언트가 하나의 최신 순서를 공유하는 요구는 서로 다른 보장이다.

| 시점 | leader | follower | 사용자에게 보일 수 있는 것 |
| --- | --- | --- | --- |
| 시작 | 0 | 0 | 어느 쪽도 0 |
| 쓰기 응답 직후, 복제 지연 중 | 1 | 0 | follower 읽기는 이전 값 0 |
| 복제 완료 뒤 | 1 | 1 | 두 사본 모두 1 |

복제본이 있다고 백업이 되는 것도 아니다. 실수한 삭제나 잘못된 업데이트가 모든 사본으로 빠르게 전파될 수 있다. 특정 시점으로 돌아가는 백업·로그 보관과 장애 시 계속 서비스하는 복제는 다른 목적이다. 내구성도 “사본이 몇 개인가”만이 아니라 어느 장애 범위와 어떤 저장 완료 조건을 약속하는지로 설명해야 한다.

## 일관성 모델이 읽기·쓰기의 의미를 정한다

Eventual consistency는 적절한 조건 아래 더 이상 갱신이 없으면 사본들이 같은 상태로 수렴하는 성질을 가리킨다. 수렴 전의 읽기에서 무엇을 볼 수 있는지, 충돌 갱신을 어떻게 합치는지까지 알아야 실제 동작을 예측할 수 있다. “언젠가 맞는다”라는 문장만으로 사용자에게 어떤 결과를 허용할지 정해지지는 않는다.

Linearizability는 각 연산이 호출과 응답 사이의 한 순간에 원자적으로 일어난 것처럼 보이고 실제 비중첩 연산의 선후를 존중하는 보장이다. 쓰기가 완료된 뒤 시작한 읽기는 그 쓰기 이전으로 되돌아간 상태를 아무 이유 없이 읽어서는 안 된다. 여러 연산이 겹치면 그중 어떤 순서로 일어난 것으로 설명할 수 있는지 따진다.

Serializable은 여러 트랜잭션의 결과가 어떤 직렬 실행과 동등하게 보이는 성질이다. 트랜잭션 격리의 개념이고 실제 시간 순서까지 같은 방식으로 규정하는 linearizability와 동일하지 않다. 개별 키 연산, 여러 키 트랜잭션, 전체 서비스 작업 중 어느 범위의 보장인지도 명시해야 한다. “강한 일관성”이라는 표현만으로 이 차이가 사라지지 않는다.

네트워크 분할로 노드 그룹끼리 통신할 수 없을 때 양쪽에서 항상 요청을 완료시키면서 하나의 선형화 가능한 상태를 유지할 수는 없는 상황이 생긴다. CAP을 “세 가지 중 평소에 아무 둘을 고르는 제품 분류”로만 외우기보다, 분할이 발생한 동안 어떤 요청을 기다리게 하거나 거부하고 어떤 보장을 유지할지의 문제로 이해한다. 실제 시스템은 연산 종류와 장애 상태에 따라 다른 정책을 선택할 수 있다.

## 합의와 리더 선출

복제된 로그를 여러 노드가 같은 순서로 적용하려면 어떤 명령을 확정할지 동의해야 한다. 합의 프로토콜은 노드 고장과 메시지 지연 속에서도 이 결정을 맞추는 규칙을 제공한다. Raft는 leader 선출, 로그 복제, 안전성 규칙을 나누어 설명한다. 단순히 “과반수가 좋다고 하면 된다”는 것보다 term·로그의 최신성·확정 조건을 함께 유지해야 한다.

5개 노드의 과반수는 3개다. 서로 다른 두 과반수 집합은 최소 한 노드를 공유하므로 완전히 분리된 두 집합이 독립적으로 상충하는 결정을 내리는 것을 막는 데 사용할 수 있다. 하지만 집합이 겹친다는 사실만으로 프로토콜이 완성되지 않는다. 각 노드가 어느 term에 누구에게 투표했고 어떤 로그를 보유했는지에 대한 규칙이 필요하다.

Raft에서 follower가 일정 시간 leader 소식을 못 들으면 선거를 시도할 수 있다. 더 높은 term과 로그 최신성 규칙이 새 leader를 선택하는 데 관여한다. leader는 로그 항목을 복제하고 현재 term을 포함한 안전한 commit 규칙에 따라 확정한다. “어떤 항목이든 사본 수 3개면 언제나 확정”처럼 문맥을 빼면 이전 term 로그 처리에서 잘못된 설명이 될 수 있다. 구현은 공식 프로토콜의 상태 전이와 실패 시나리오를 따라 검증해야 한다.

노드가 둘씩 분리되거나 과반수를 사용할 수 없으면 안전하게 새 결정을 내리지 못할 수 있다. 이는 시스템이 전혀 아무 일도 못한다는 말과 같지는 않다. 읽기 캐시·상태 조회 등 별도 정책이 가능하지만 어떤 보장을 포기하거나 유지하는지 명확해야 한다. 합의는 모든 환경에서 즉시 진행을 보장하는 마법이 아니라 안전성과 진행 조건을 규정하는 방법이다.

## 샤딩과 부하 분산

복제가 같은 데이터를 여러 곳에 두는 것이라면 샤딩은 데이터의 서로 다른 부분을 나누어 둔다. user\_id를 기준으로 나누면 한 사용자의 데이터를 같은 shard에 모아 읽기·쓰기를 단순하게 만들 수 있다. 하지만 사용자별 데이터 크기나 요청이 균등하지 않으면 특정 shard가 뜨거워질 수 있다. 키 개수가 비슷하다는 사실과 실제 부하가 비슷하다는 사실은 다르다.

키를 노드 수로 나눈 나머지로 배치하는 단순 방법은 노드 수가 바뀔 때 많은 키의 위치가 달라질 수 있다. Consistent hashing 같은 방법은 재배치 범위를 줄이는 데 사용되지만 hot key와 거래의 분산 문제를 자동 해결하지 않는다. 큰 고객 하나가 대부분 요청을 만드는 경우에는 같은 키 안을 더 나누거나 읽기 사본·캐시·별도 제한을 고려해야 한다.

여러 shard에 걸친 조회·트랜잭션은 한 노드 안의 작업보다 복잡하다. 전역 정렬이나 집계는 결과를 모으는 단계가 필요하고, 둘 이상의 저장소 변경을 모두 성공시키려면 조정 비용과 실패 처리가 추가된다. 단일 노드 DB의 계약을 서버 수만 늘려 그대로 얻는 것은 아니다. 먼저 필요한 확장 규모와 일관성 범위를 확인한 뒤 분산 복잡성을 받아들이는 것이 합리적이다.

Load balancer는 들어오는 요청을 여러 서버에 분배한다. 라운드로빈처럼 단순 분배를 할 수도 있고 진행 중 요청 수·상태를 고려할 수도 있다. 하지만 요청의 비용이 크게 다르거나 세션 상태가 특정 서버에 묶여 있으면 단순히 개수를 나누는 것으로 균형이 맞지 않는다. 데이터 위치·캐시·worker 상태와 트래픽 분배를 연결해서 생각해야 한다.

## 작업 큐와 전달 의미

작업 큐는 요청 접수와 실제 처리를 분리한다. API 서버는 작업을 등록하고 worker가 나중에 가져가 처리할 수 있다. 긴 작업을 HTTP 연결 하나에 계속 묶어 두지 않아도 되지만 사용자에게 접수와 완료의 차이를 알려야 한다. 작업 ID로 상태를 조회하거나 결과를 가져오는 별도 계약이 필요하다.

Ack는 consumer가 작업을 처리했다는 신호다. 처리 전에 ack하고 죽으면 작업을 잃을 수 있다. 처리 후 ack하면 결과를 저장한 뒤 ack 전에 죽었을 때 재전달되어 중복 처리가 생길 수 있다. At-most-once와 at-least-once는 이런 전달·처리 정책의 범위를 표현하며, 실제 제품이 어느 경계에서 어떤 보장을 하는지 확인해야 한다.

중복 전달과 중복 효과는 다르다. 같은 작업이 두 번 도착해도 DB에 결과를 한 번만 반영하면 원하는 업무 효과를 한 번으로 만들 수 있다. job\_id를 고유하게 두고 저장 시 중복을 거부하는 예를 보자.

```sql
CREATE TABLE results (
  job_id TEXT PRIMARY KEY,
  value INTEGER NOT NULL
);
INSERT INTO results(job_id, value)
VALUES ('job-42', 7)
ON CONFLICT(job_id) DO NOTHING;
```

처음에는 job-42의 결과가 저장된다. 같은 문장을 다시 실행하면 고유키 충돌로 새 행을 넣지 않는다. 이 예제는 “같은 작업의 첫 결과를 남긴다”는 저장 계약이다. 결과값이 다른 재시도를 어떻게 처리할지, 결과 저장과 다른 DB 변경을 같은 트랜잭션에 넣을지 추가로 정해야 한다. 단순히 요청 ID를 기록한 뒤 실제 효과를 따로 실행하면 그 사이 장애로 누락·중복이 남을 수 있다.

## 멱등성과 외부 효과의 경계

멱등 연산은 같은 요청을 반복해도 정한 상태 효과가 한 번 한 것과 같게 유지되는 연산이다. “x를 1로 설정”은 같은 상태 모델에서 멱등일 수 있지만 “x에 1 추가”는 그렇지 않다. 결제 생성 같은 비멱등 업무도 요청 키와 결과 저장을 결합해 멱등 처리 인터페이스를 만들 수 있다. 다만 키 유효기간·동시 중복·실패 상태·입력 불일치까지 정책이 필요하다.

DB 안의 결과와 완료 표시를 한 트랜잭션으로 묶어도 이메일 전송처럼 바깥 효과까지 자동으로 묶이지 않는다. DB commit 뒤 이메일 전송 전에 죽거나, 전송 후 기록 전에 죽는 문제가 생긴다. Outbox는 업무 변경과 “보낼 사건”을 같은 DB 트랜잭션에 저장하고 별도 전달자가 사건을 보내는 방법이다. 전달자는 중복 전송할 수 있으므로 수신자의 중복 제거가 여전히 필요할 수 있다. 정확히 한 번이라는 표현은 저장소·전달·외부 효과 중 어느 범위의 주장인지 제한해야 한다.

재시도는 일시적 실패를 넘기는 도구지만 실패 작업 모두를 동시에 다시 넣으면 부하를 폭증시킬 수 있다. Backoff·jitter·시도 횟수·전체 deadline을 함께 정한다. 재시도할 수 없는 잘못된 입력은 별도로 처리하고 계속 실패하는 작업이 큐를 막지 않게 격리·관측할 수 있다. 작업을 버릴지 보관할지는 업무 계약이지 모든 서비스의 고정 정답은 아니다.

## 처리율, Backpressure, 병렬화의 한계

초당 120개가 들어오고 worker 전체가 초당 100개를 처리한다고 단순화하면 대기 작업은 초당 20개씩 늘어난다. 입력이 이 상태로 30초 지속되면 추가 backlog는 600개다. 개별 작업을 빠르게 처리하더라도 총 처리율보다 입력이 높으면 큐는 계속 늘어난다. 메모리를 더 주는 것은 붕괴 시점을 늦출 뿐 지속적인 불균형을 해결하지 않는다.

Bounded queue는 대기 작업 수를 제한한다. 가득 찼을 때 생산자를 기다리게 하거나 요청을 거부하는 식으로 상류에 압력을 전달하는 것이 backpressure다. 이것은 무조건 요청을 성공시키는 장치가 아니라 시스템이 감당할 수 있는 부하를 명시적으로 드러내는 방법이다. 외부 모델 API rate limit이 병목이면 worker를 늘려도 처리율이 늘지 않고 재시도만 늘 수 있다.

![Amdahl 법칙의 수학적 예제입니다. 분산 시스템에서는 네트워크·동기화·부분 실패 비용도 추가됩니다.](/figures/C10.svg)

Amdahl 법칙의 수학적 예제입니다. 분산 시스템에서는 네트워크·동기화·부분 실패 비용도 추가됩니다.

그림의 Amdahl 곡선은 **전체 작업 중 병렬화할 수 없는 비율**에 따라 worker를 늘렸을 때 향상이 어디서 제한되는지 보여 준다. 직렬 비율을 s, 병렬 처리 수를 p라 두면 이상화한 speedup은 1/\[s+(1−s)/p\]다. 예를 들어 s=0.2, p=4이면 1/(0.2+0.8/4)=2.5배이며, p가 무한히 커져도 상한은 1/0.2=5배다. 그래프는 통신·동기화·부하 불균형을 생략하므로 실제 분산 작업의 성능 예측이나 실측 결과가 아니다. 실제로는 이런 추가 비용 때문에 더 일찍 포화하거나 느려질 수도 있다.

병렬 계산과 분산 서비스는 관련되지만 같지는 않다. 한 요청을 여러 조각으로 나누는 경우와 독립 요청을 여러 worker에 나누는 경우는 지연·처리량·데이터 공유의 의미가 다르다. 장애를 넣어 작업이 중복·누락·대기하는 지점을 확인하고, 논리 요청 ID와 시도 ID를 나누어 관측하면 재시도 횟수와 실제 업무 완료 수를 혼동하지 않게 된다.

## 핵심 정리

분산 시스템에서는 지연과 부분 실패 때문에 작업 결과가 불확실할 수 있다. 복제는 읽기·장애 대응을 돕지만 일관성·백업·내구성의 모든 요구를 자동 충족하지 않는다. 일관성 모델과 합의는 어떤 순서와 상태를 안전하게 확정할지 규정한다. 샤딩은 데이터·부하를 나누는 대신 교차 작업과 재배치 비용을 만든다. 큐의 재전달과 업무 효과의 중복은 다른 문제이며 멱등성은 경계를 정해 설계한다. Backpressure는 감당할 수 없는 입력을 상류에 전달하는 수단이다. worker 수만 늘려도 직렬 부분과 통신·저장 병목은 남는다.
