# 데이터베이스는 저장된 값 사이의 약속을 관리한다

문서와 검색 결과를 JSON 파일에 저장하는 것으로 시작할 수 있다. 하지만 두 요청이 동시에 파일을 고치거나, 일부만 저장한 뒤 프로그램이 종료되거나, 특정 사용자의 최근 결과만 빨리 찾으려 하면 문제가 복잡해진다. 데이터베이스는 데이터를 오래 보관하는 것뿐 아니라 구조·제약·조회·동시 변경·복구를 관리한다. 어떤 데이터를 어떤 관계로 표현하고, 어느 작업을 하나의 논리적 변경으로 볼지 정하는 것이 먼저다.

## 테이블, 키, 제약으로 데이터의 의미를 표현한다

### 개념과 작동 원리

관계형 모델에서 테이블은 행과 열로 데이터를 표현한다. 열은 속성, 행은 하나의 기록에 대응한다. 하지만 단순한 표 그림과 달리 키·타입·제약이 허용되는 상태를 제한한다. 기본키는 행을 식별하고 외래키는 다른 테이블의 행과 연결한다. NOT NULL은 값이 반드시 있어야 함을, UNIQUE는 같은 값의 중복을 제한한다. 데이터가 틀린 뒤 매번 수정하는 대신 저장 경계에서 잘못된 상태를 막는 것이다.

문서와 청크를 저장하는 예를 보자. 문서 테이블은 문서 ID와 원본 URL을, 청크 테이블은 문서 ID·순번·본문을 가진다. 원본 URL은 문서에 한 번만 저장하고 각 청크는 그 문서를 참조한다. 이렇게 하면 URL을 바꿀 때 수백 청크를 모두 수정할 필요가 없다.

```sql
CREATE TABLE documents (
  id INTEGER PRIMARY KEY,
  source_url TEXT NOT NULL
);
CREATE TABLE chunks (
  document_id INTEGER NOT NULL,
  chunk_no INTEGER NOT NULL,
  body TEXT NOT NULL,
  PRIMARY KEY (document_id, chunk_no),
  FOREIGN KEY (document_id) REFERENCES documents(id)
);
```

복합 기본키는 문서 하나 안에서 청크 순번이 겹치지 않게 한다. 외래키는 존재하지 않는 문서 ID에 청크를 연결하지 않도록 한다. 실제 DB에서 외래키 검사 활성화 등 설정을 확인해야 한다. 예를 들어 SQLite에서는 연결별 외래키 설정을 고려한다. 스키마에 글자로 선언했다는 것과 원하는 환경에서 제약이 실제로 검사된다는 것은 확인해야 할 별개의 단계다.

NULL은 0이나 빈 문자열과 같지 않고 값의 부재·미상 등을 표현하는 특별한 상태다. SQL에서는 NULL과의 비교가 일반적인 참·거짓 논리만으로 움직이지 않으므로 `= NULL` 대신 `IS NULL`을 사용한다. 누락을 허용할지, 기본값으로 대체할지, 별도 상태를 둘지는 업무 의미에 따라 정한다. 의미가 다른 “모름”과 “실제로 0”을 같은 숫자로 저장하면 이후 분석에서 구별할 수 없다.

### 키와 제약으로 금지할 상태를 직접 적기

문서에는 고유 ID가 있고, 청크는 문서 안에서 순번이 중복되지 않아야 한다고 하자. 이 규칙은 애플리케이션의 if문뿐 아니라 DB 제약으로도 표현할 수 있다.

```sql
CREATE TABLE documents (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL
);
CREATE TABLE chunks (
  id INTEGER PRIMARY KEY,
  document_id INTEGER NOT NULL REFERENCES documents(id),
  seq INTEGER NOT NULL CHECK (seq >= 0),
  body TEXT NOT NULL,
  UNIQUE (document_id, seq)
);
INSERT INTO documents VALUES (1, 'Alpha'), (2, 'Beta');
INSERT INTO chunks VALUES (101, 1, 0, 'first'), (102, 1, 1, 'second');
```

| 제약 | 이 예에서 막는 상태 |
|---|---|
| PRIMARY KEY | 같은 ID의 중복 기록 |
| FOREIGN KEY | 존재하지 않는 문서에 속한 청크 |
| NOT NULL | 필수 값의 누락 |
| UNIQUE(document_id,seq) | 같은 문서·순번의 중복 |
| CHECK(seq>=0) | 음수 순번 |

**NOT NULL과 CHECK는 다른 제약**이다. NULL의 SQL 논리 때문에 CHECK만으로 모든 누락을 막는다고 가정하면 안 된다. [PostgreSQL 공식 제약 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)에서 각 제약의 의미를 확인한다.

## SQL은 원하는 결과를 선언한다

### 개념과 작동 원리

SQL에서 SELECT는 어떤 결과를 원하는지 표현하고 DB는 실제 읽기·결합 순서를 계획한다. FROM·JOIN은 행의 연결을, WHERE는 조건을, GROUP BY는 집계를, ORDER BY는 결과 순서를 정한다. 테이블에 저장된 물리 순서나 지난번 출력 순서에 기대어 결과가 항상 같은 순서라고 가정하지 않는다. 정렬이 필요하면 명시적으로 요청한다.

```sql
SELECT d.id, COUNT(*) AS chunk_count
FROM documents AS d
JOIN chunks AS c ON c.document_id = d.id
GROUP BY d.id
ORDER BY chunk_count DESC, d.id;
```

먼저 문서와 그 문서의 청크를 연결한다. 문서 하나에 청크 3개가 있으면 결합 결과에는 그 문서 ID가 세 행 나타난다.

GROUP BY는 문서 ID별로 모으고 COUNT는 연결된 청크 행을 센다. 마지막 동점 정렬 조건까지 주어 같은 청크 수의 문서가 어떤 순서로 나올지 정한다.

청크가 없는 문서도 보고 싶다면 INNER JOIN 대신 LEFT JOIN과 적절한 COUNT 대상이 필요하다. LEFT JOIN 뒤 `COUNT(*)`와 `COUNT(c.chunk_no)`는 청크가 없는 행에서 결과가 달라질 수 있다.


윈도 함수는 그룹을 하나의 행으로 접지 않고 원래 행을 유지하며 순위·누적값 등을 계산한다. 사용자별 최신 실행 한 개를 고를 때 `ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY ts DESC, id DESC)`처럼 쓸 수 있다.

동점 처리 기준을 주지 않으면 “최신 한 개”의 결과가 애매할 수 있다. SQL은 짧아 보여도 행이 늘어나는 지점, NULL, 중복, 정렬의 의미를 단계별로 따라가야 한다.


### LEFT JOIN에서 0개인 문서도 세기

앞의 자료에서 Alpha는 청크 2개, Beta는 0개다. 모든 문서를 남기려면 LEFT JOIN을 사용하고 청크 ID를 세면 된다.

```sql
SELECT d.id, COUNT(c.id) AS chunk_count
FROM documents AS d
LEFT JOIN chunks AS c ON c.document_id = d.id
GROUP BY d.id
ORDER BY d.id;
```

| 문서 ID | COUNT(c.id) | COUNT(*)를 쓰면 |
|---|---|---|
| 1 | 2 | 2 |
| 2 | 0 | 1 |

매칭이 없는 Beta도 LEFT JOIN 결과에서는 청크 쪽이 NULL인 행 하나를 만든다. COUNT(*)는 그 행을 세고 COUNT(c.id)는 NULL을 제외한다. **결합 전 행 수와 결합 후 행 수는 다르다.** 일대다 관계를 두 번 결합하면 행이 곱해질 수 있으므로 집계 전에 행 하나의 의미를 확인한다.

ORDER BY 없이 결과가 우연히 정렬되어 보였다고 순서 계약이 생기지는 않는다. 필터·집계·정렬의 논리적 의미와 실제 실행 계획의 처리 순서는 구분한다.

## 정규화와 중복의 대가

### 개념과 작동 원리

사용자 이름을 모든 실행 로그 행에 그대로 복사하면 한 번 조회하기는 편하다. 하지만 이름을 수정할 때 일부 행만 바뀌거나 새 사용자를 로그 없이 저장하기 어려운 문제가 생길 수 있다. 이런 갱신·삽입·삭제 이상은 같은 사실을 여러 곳에 중복 저장하는 데서 나온다. 정규화는 함수 종속 등을 바탕으로 사실을 적절한 관계로 나누어 일관성을 다루는 방법이다.

함수 종속 X→Y는 X값이 정해지면 Y값이 하나로 결정된다는 뜻이다. user\_id가 현재 사용자 이름을 결정하는 설계라면 이름을 사용자 테이블에 두고 로그는 user\_id로 참조하게 할 수 있다. 다만 “실행 당시 이름을 영구 기록한다”는 요구라면 현재 이름과 과거 snapshot은 다른 사실이다. 중복처럼 보이는 열을 기계적으로 제거하기보다 데이터가 어느 시점의 무엇을 뜻하는지 먼저 정해야 한다.

조회가 매우 많고 여러 테이블 결합이 부담되면 일부 중복 저장이나 사전 집계를 선택할 수 있다. 이것은 무조건 잘못된 정규화가 아니라 읽기 비용을 줄이는 대신 갱신·재계산·불일치 관리 부담을 받는 선택이다. 검색용 인덱스와 원본 DB를 분리할 때도 원본이 바뀌면 어느 시점에 검색 사본을 갱신하고 실패 시 어떻게 다시 맞출지 정해야 한다.

### 현재 속성과 과거 스냅샷의 중복은 다르다

현재 사용자 이름을 user_id마다 한 곳에서 관리하면 이름 변경 시 여러 로그를 수정할 필요가 없다. 반대로 청구서에 **발행 당시 이름**을 남기려는 목적이라면 현재 이름을 조회하는 것만으로 과거 사실을 재현할 수 없다.

| 저장할 사실 | 적절한 의미 | 변경할 때의 질문 |
|---|---|---|
| 현재 사용자 이름 | user_id에 대응하는 현재 속성 | 한 곳에서 갱신할 것인가 |
| 발행 당시 표시 이름 | 특정 이벤트 시점의 스냅샷 | 나중에 바꾸어도 되는가 |
| 중복 캐시 | 원본에서 다시 만들 수 있는 파생값 | 누가 언제 무효화하는가 |

정규화는 **어떤 함수 종속과 사실을 저장하는지**를 기준으로 판단한다. 문자열이 반복된다는 이유만으로 모두 잘못된 설계는 아니다. 읽기 성능을 위해 비정규화할 때에는 원본·갱신 책임·재구축 방법을 함께 정해야 한다.

## 페이지, 버퍼 풀, 인덱스

### 개념과 작동 원리

DB는 저장장치를 페이지 같은 단위로 읽고 쓴다. 행 하나를 원한다고 항상 해당 바이트만 독립적으로 가져오는 것은 아니다. 버퍼 풀은 최근·자주 사용하는 DB 페이지를 메모리에 보관해 저장장치 접근을 줄인다. 운영체제 페이지 캐시와 DB 자체 버퍼가 각각 관여할 수 있다. 캐시가 따뜻한 상태와 처음 읽는 상태의 시간이 다른 이유다.

인덱스는 조건에 맞는 행을 찾는 별도 검색 구조다. B+tree는 여러 키와 자식 포인터를 한 노드에 두어 높이를 낮추고, 정렬된 leaf를 이용해 범위 검색을 지원한다. 디스크·SSD의 페이지 단위를 활용한다는 점에서 단순한 이진 트리와 설계 목적이 다르다. 해시 인덱스는 동등 조건에 적합할 수 있지만 순서·범위 검색에 같은 이점을 제공하는 것은 아니다.

```sql
CREATE INDEX idx_runs_user_ts ON runs(user_id, ts);
EXPLAIN QUERY PLAN
SELECT id, ts FROM runs
WHERE user_id = 7 ORDER BY ts;
```

복합 인덱스 `(user_id,ts)`는 user\_id별로 모이고 그 안에서 ts순으로 정렬된 구조라고 생각할 수 있다. 특정 사용자의 시간순 기록을 읽는 데 유리할 수 있다. 하지만 ts만으로 모든 사용자를 찾는 조건에서 같은 효과가 자동 보장되는 것은 아니다. DB의 skip-scan 등 특수 전략이 있을 수 있어도 인덱스의 앞쪽 키와 쿼리 조건의 관계를 먼저 이해한다.

인덱스는 공짜가 아니다. 저장 공간을 쓰고 INSERT·UPDATE·DELETE 때 인덱스도 바뀐다. 낮은 선택도로 대부분의 행을 반환하거나 정렬·다른 열 접근 비용이 크면 전체 scan이 더 유리할 수 있다. “인덱스가 있는데 왜 안 쓰는가”는 힌트를 강제하기 전에 반환량·통계·쿼리 형태를 보아야 한다. EXPLAIN은 DB가 고른 전략을 보여 주며 실제 실행을 포함하는 도구인지 단순 추정인지 명령별로 구분한다.

### 복합 인덱스는 정렬된 키 순서로 이해하기

인덱스가 (document_id,seq) 순서라면 먼저 document_id, 같은 문서 안에서 seq로 정렬된 키를 생각할 수 있다.

| 조건 | 활용을 이해하는 방식 |
|---|---|
| document_id=1 AND seq>=10 | 앞 키를 고정하고 뒤 키 범위를 탐색 |
| document_id=1 | 해당 문서의 연속된 키 구간 탐색 |
| seq=10만 지정 | 앞 키가 고정되지 않아 다른 탐색·scan 전략이 필요할 수 있음 |

뒤쪽 열만 조건에 있다고 **인덱스를 절대 못 쓴다**고 단정하지 않는다. PostgreSQL은 자료 분포 등에 따라 skip scan 같은 전략을 사용할 수 있다. [공식 복합 인덱스 문서](https://www.postgresql.org/docs/current/indexes-multicolumn.html)의 사용 조건과 비용을 구분한다.

이상적인 B+tree에서 분기 수 B, 키 수 N이면 탐색 높이는 O(log_B N)이다. 정렬된 leaf에서 K개 결과를 순서대로 읽는 비용과 실제 테이블 행을 가져오는 비용은 별도다. 인덱스를 추가하면 저장 공간과 INSERT·UPDATE의 유지 비용도 늘어난다.

## 실행 계획은 연산의 조합이다

### 개념과 작동 원리

전체 행을 훑는 scan, 인덱스로 범위를 찾는 search, 정렬, 집계, JOIN은 서로 다른 실행 연산이다. Nested-loop join은 한쪽 행마다 다른 쪽에서 맞는 행을 찾는다.

반대쪽 인덱스가 있으면 유리할 수 있지만 두 큰 집합을 무작정 곱하면 비용이 커질 수 있다. Hash join은 한쪽 키로 해시 구조를 만든 뒤 다른 쪽에서 조회하고, sort-merge join은 정렬된 키를 함께 이동한다.

어느 방법이 좋은지는 행 수·정렬 상태·메모리·인덱스에 달려 있다.


옵티마이저는 통계로 결과 행 수와 비용을 추정한다. 특정 값에 데이터가 몰렸거나 열 사이의 상관을 놓치면 추정이 빗나갈 수 있다. 실제 행 수·시간과 계획을 비교하면 병목을 좁힐 수 있다. 다만 측정 자체도 캐시와 부하를 바꾸므로 동일 조건을 기록한다. 쿼리를 바꾼 뒤 빨라졌다는 한 번의 관찰만으로 인덱스 효과를 확정하지 않는다.

문서·청크·태그처럼 일대다 관계를 여러 번 JOIN하면 결과 행이 예상보다 늘어 중복 집계가 생기기 쉽다. 먼저 각 결합이 행 수를 어떻게 바꾸는지 작은 예제로 확인한다. 성능 분석보다 정답 의미를 검증하는 것이 우선이며 빠르게 틀린 쿼리는 개선이 아니다.

### JOIN의 입력 크기와 출력 크기를 함께 계산하기

| 대표 구현 | 단순 비용 모형 | 추가 조건 |
|---|---|---|
| 두 입력 전부 비교 | O(nm) | 비교 1회가 상수 비용 |
| 인덱스 nested loop | 대략 n번의 인덱스 탐색+결과 읽기 | 안쪽 키의 인덱스·선택도 |
| hash join | 기대 O(n+m+K) | 해시 분포·메모리·출력 K |

두 테이블이 각각 100행이어도 모든 행이 같은 JOIN 키를 가지면 결과가 10,000행일 수 있다. 입력을 읽는 비용만 계산하고 출력 비용을 생략하면 실제 병목을 놓친다. 메모리 부족으로 spill이 발생하면 단순 메모리 모형보다 비싸진다.

계획에서 추정 10행인데 실제 100,000행이면 이후 JOIN·정렬 계획도 영향을 받을 수 있다. PostgreSQL의 EXPLAIN 비용 단위는 경과시간 ms와 같지 않다.

**EXPLAIN ANALYZE는 실제 문장을 실행**하므로 쓰기 문장에도 효과가 생긴다. [공식 EXPLAIN 문서](https://www.postgresql.org/docs/current/sql-explain.html)를 기준으로 추정·측정을 읽는다.


## 트랜잭션과 동시 변경

### 개념과 작동 원리

계좌 A에서 10을 빼고 B에 10을 더하는 작업은 둘 중 하나만 저장되면 안 된다. 트랜잭션은 여러 변경을 하나의 논리적 단위로 묶어 commit하거나 실패 시 rollback하게 한다. 원자성은 일부만 반영된 상태를 남기지 않는 성질이고 내구성은 commit한 변경이 약속한 장애 범위에서 남는 성질이다. 일관성은 정의한 제약과 규칙을 만족하게 하는 데 관계하며 DB 선언만으로 모든 업무 규칙이 자동 발명되는 것은 아니다.

격리는 동시에 실행하는 트랜잭션이 서로의 중간 상태와 변경을 어떻게 보는지 정한다. 잔고 100을 두 작업이 모두 읽고 각각 10·20을 빼서 90·80을 저장하면 마지막 쓰기에 따라 결과가 80이나 90이 될 수 있다. 원하는 70이 아닌 lost update다. DB가 제공하는 원자적 갱신이나 적절한 잠금·충돌 검사가 필요하다.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 10
WHERE id = 1 AND balance >= 10;
-- 변경 행 수를 확인하고 후속 업무 조건을 처리한다.
COMMIT;
```

단순히 앱에서 읽은 오래된 숫자를 계산해 덮는 대신 현재 행을 기준으로 갱신하도록 표현할 수 있다. 그러나 실제 요구가 두 계좌 이동·부족 잔고 처리·중복 요청 방지라면 그 전체를 만족하는 트랜잭션 설계가 더 필요하다. 예제 한 줄이 모든 DB·격리 수준의 모든 충돌을 자동 해결한다는 뜻은 아니다.

잠금은 충돌하는 접근을 기다리게 할 수 있고 MVCC는 여러 버전으로 읽기가 볼 snapshot을 관리한다. Snapshot을 읽는다고 모든 실행이 직렬 실행과 같은 것은 아니다.

서로 다른 행을 읽고 각자 다른 행을 갱신해 전체 제약이 깨지는 write skew 같은 이상이 가능하다. 격리 수준 이름과 보장은 DB마다 세부 차이가 있으므로 문서를 확인한다.

Serializable은 결과가 어떤 직렬 실행과 같도록 하는 의미이며, 실제 요청의 시간 순서까지 다루는 분산 시스템의 linearizability와는 다른 개념이다.


### lost update가 생기는 순서와 보호할 불변식

잔고 100에서 두 작업이 각각 10·20을 차감한다고 하자.

| 순서 | T1 | T2 |
|---|---|---|
| 1 | 100 읽기 | |
| 2 | | 100 읽기 |
| 3 | 계산한 90 저장 | |
| 4 | | 계산한 80 저장 |

각 작업이 읽은 값을 기반으로 절대 잔고를 다시 저장하면 결과 80이 되어 한 차감이 사라질 수 있다. DB의 원자적 상대 갱신, 적절한 잠금·버전 비교·격리 수준 등으로 해결하되 실제 DB 동작과 재시도 규칙을 확인한다.

| 목표 | 따로 확인할 것 |
|---|---|
| 두 변경을 전부 또는 전혀 반영 | 트랜잭션 원자성 |
| 잔고가 음수가 되지 않음 | 조건부 갱신·제약·동시 접근 규약 |
| 여러 행의 업무 규칙 유지 | 격리 수준·잠금 범위·실패 처리 |

Serializable도 여러 트랜잭션을 항상 오류 없이 성공시킨다는 뜻은 아니다. 충돌 때문에 한 트랜잭션을 중단하고 전체를 재시도해야 할 수 있다. 같은 수준 이름의 구현 차이도 있으므로 [PostgreSQL 격리 문서](https://www.postgresql.org/docs/current/transaction-iso.html)를 기준으로 읽는다.

## 로그, 복구, 검색의 확장

### 개념과 작동 원리

DB는 메모리 페이지의 변경을 곧바로 안전하게 저장장치에 모두 반영할 수 없으므로 복구 로그를 사용한다. WAL은 데이터 페이지보다 필요한 로그 기록이 먼저 지속되도록 하는 규칙으로, 장애 뒤 redo·undo 등 복구를 가능하게 한다.

Checkpoint는 복구를 시작할 범위를 줄이는 데 도움을 준다. 복제·백업·로그는 관련되지만 서로 대체하지 않는다.

실수로 삭제한 데이터가 복제본에도 전파될 수 있으므로 “사본이 있다”가 원하는 시점 복구와 같지 않다.


전문 검색은 단어·토큰과 문서의 관계를 인덱싱하고 벡터 검색은 임베딩 공간의 근접도를 사용한다. 벡터 인덱스는 정확 검색을 하거나 속도·공간을 위해 근사 최근접 탐색을 할 수 있다.

근사는 정답 이웃을 놓칠 수 있어 recall과 지연의 교환관계를 평가한다. 거리가 작다는 사실은 답변이 사실이라는 보장이 아니다.

권한·날짜 필터를 언제 적용하는지에 따라 검색 대상도 달라지므로 검색 품질과 데이터 접근 의미를 함께 관리해야 한다.


### commit·체크포인트·백업의 역할 구분

| 장치 | 주된 역할 | 대신하지 못하는 것 |
|---|---|---|
| WAL | 데이터 페이지보다 먼저 복구 기록을 지속 | 독립된 전체 백업 |
| 체크포인트 | 복구에 필요한 작업량을 정리 | 모든 과거 시점 복원 자동 보장 |
| 복제 | 다른 노드에 변경 전달 | 잘못된 삭제까지 막는 보장 |
| 백업·복구 절차 | 정한 시점·범위로 복원 | 실제 복원 검증 없이 성공 확정 |

WAL 덕분에 commit 때 수정한 모든 데이터 페이지를 각각 즉시 저장할 필요는 없을 수 있다. 대신 어떤 로그를 언제 지속해야 하는지, 동기화 설정과 장애 범위를 이해해야 한다. [PostgreSQL WAL 설명](https://www.postgresql.org/docs/current/wal-intro.html)의 로그 선행 규칙을 참고한다.

**복습 문제:** 복제 노드가 3개라면 실수로 지운 행도 항상 복구할 수 있는가?

<details><summary>풀이</summary>

아니다. 삭제가 정상 변경으로 모두 복제되면 세 사본에서도 사라질 수 있다. 복제는 가용성과 장애 대응에 도움을 주지만, 복구 가능한 백업·로그 보존·시점 복원 계약을 대신하지 않는다.

## 핵심 정리

스키마와 제약은 허용할 데이터 상태를 표현한다. SQL은 원하는 결과를 선언하므로 JOIN·NULL·중복·정렬의 의미를 먼저 확인해야 한다.

정규화와 중복 저장은 일관성 관리와 조회 비용 사이의 선택이다. 인덱스와 버퍼는 읽기를 돕지만 공간·쓰기 비용을 추가한다.

실행 계획은 scan·join·sort 등으로 나누어 읽고 추정과 실제를 비교한다. 트랜잭션의 원자성·격리·내구성은 서로 다른 보장이며 업무 규칙까지 설계해야 한다.

복구·백업·검색 인덱스는 각각의 실패와 정확성 범위를 가진다.


### 심화 비교: 해시·B+트리·역색인의 검색 조건

| 구조 | 잘 맞는 질의 | 핵심 이유·주의점 |
| --- | --- | --- |
| 해시 인덱스 | 정확히 같은 키 | 해시 후보 위치를 빠르게 찾음, 일반적인 정렬·범위 탐색과 다름 |
| B+트리 계열 | 동등·범위·정렬 | 한 노드에 여러 키를 담아 높이를 낮추고 잎의 순서를 활용 |
| 역색인 | 단어가 포함된 문서 | 단어 → 해당 문서 목록을 연결, 토큰화·랭킹 필요 |
| 벡터 검색 인덱스 | 벡터 거리가 가까운 항목 | 근사 탐색이면 품질·지연·메모리의 교환관계 |

**B+트리가 페이지에 맞는 이유:** 분기 수가 커지면 키가 많아도 트리 높이를 낮게 유지할 수 있다. 교육용으로 분기 수를 100이라고 보면 100의 세제곱은 100만이다. 실제 높이는 노드 점유율·키 크기·구현에 따라 달라지고, 캐시된 상위 페이지가 있으면 논리적 방문 수와 물리 I/O 횟수도 다르다.

B+트리에서 내부 노드는 탐색 경계를, 잎은 키와 레코드 또는 위치 정보를 둔다. **범위 시작점을 찾은 뒤 잎을 순서대로 읽는 것**이 범위 질의의 핵심이다. DB 문서의 B-tree라는 이름과 교재의 B+트리 분류는 표기 방식이 다를 수 있어 실제 엔진을 확인한다.

### SQL 예제: 복합 인덱스는 조회 패턴에서 정한다

```sql
CREATE TABLE requests (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    status TEXT NOT NULL
);

CREATE INDEX idx_requests_user_time
ON requests(user_id, created_at);

SELECT id, created_at, status
FROM requests
WHERE user_id = 7 AND created_at >= 1000
ORDER BY created_at
LIMIT 20;
```

`(user_id, created_at)`는 먼저 사용자별로 모이고 그 안에서 시간순으로 정렬되는 구조로 이해한다. 사용자 동등 조건으로 범위를 좁힌 후 시간 조건·정렬을 활용할 수 있다. 반대로 전체 사용자의 `created_at`만으로 찾는 질의에는 같은 이점을 기대하기 어렵다.

**주의:** 선두 열이 없으면 인덱스를 절대 못 쓴다고 단정하지 않는다. 엔진·버전·통계에 따라 skip scan 같은 계획을 선택할 수도 있다. 인덱스 선택은 **실행 계획과 실제 행 수·정렬·I/O**를 확인해 검증한다. 인덱스가 많으면 저장 공간과 쓰기·갱신 비용도 증가한다.

### 동시성 예제: 같은 재고를 두 번 팔지 않기

초기 재고가 1일 때 두 트랜잭션이 각각 1을 읽고 0을 쓰면 둘 다 성공했다고 판단할 수 있다. **읽은 값을 앱에서 계산해 덮어쓰는 것과 DB 안에서 조건부 갱신하는 것**은 다르다.

```sql
UPDATE inventory
SET stock = stock - 1
WHERE product_id = 10 AND stock > 0;
```

이 형태의 단일 조건부 UPDATE를 지원하는 일반적인 트랜잭션 DB에서는 같은 행의 갱신을 DB 동시성 제어에 맡기고 **변경 행 수가 1인지** 확인한다. 0이면 재고 부족 또는 대상 부재다. 주문 생성까지 함께 성공해야 하면 그 변경도 같은 트랜잭션에 묶는다. 잠금 충돌·직렬화 실패는 엔진 계약에 맞게 처리한다.

| 방법 | 핵심 | 실패 시 처리 |
| --- | --- | --- |
| 비관적 잠금 | 먼저 잠그고 읽기·변경 | 잠금 대기·교착·timeout 처리 |
| 낙관적 동시성 제어 | version을 조건에 넣고 갱신 | 0행이면 충돌 확인 후 다시 읽고 판단 |
| 원자적 조건부 갱신 | 조건 검사와 변경을 DB 문장으로 결합 | 변경 행 수 검사 |

### 면접 질문 01: 인덱스가 있는데 왜 전체 스캔을 하는가

**답변:** 많은 행을 읽는 질의에서는 인덱스와 테이블을 오가는 비용보다 순차 스캔이 저렴할 수 있습니다. 테이블 크기·선택도·통계·정렬·인덱스 적용 가능한 조건인지 확인하고 실행 계획을 봅니다. 인덱스 존재만으로 사용을 강제하지는 않습니다.

**꼬리질문:** EXPLAIN ANALYZE는 읽기 전용인가? **실제로 질의를 실행**하므로 변경 쿼리와 큰 쿼리에서는 주의한다. cost는 그 자체로 밀리초가 아니다.

### 면접 질문 02: 복합 인덱스의 열 순서는 왜 중요한가

**답변:** 여러 열의 사전식 순서가 탐색 범위를 결정하기 때문입니다. 사용자 동등 조건 후 시간 범위를 조회한다면 `(user_id, created_at)`를 우선 검토합니다. 필터뿐 아니라 ORDER BY·LIMIT·데이터 분포와 다른 조회 패턴도 함께 봅니다.

**꼬리질문:** 선택도가 높은 열을 무조건 앞에 두는가? **동등·범위 조건과 정렬 활용**을 포함해 결정해야 하며 단일 규칙으로 정하지 않는다.

### 면접 질문 03: ACID는 각각 무엇을 보장하는가

**답변:** 원자성은 트랜잭션 변경의 전부 또는 전무, 일관성은 제약과 올바른 트랜잭션을 통해 유효 상태 유지, 격리성은 동시 실행의 관찰 의미, 지속성은 약속한 장애 범위에서 커밋 결과 유지입니다. 실제 강도는 격리 수준·동기화·복제 설정에 따라 확인합니다.

**꼬리질문:** ACID의 C가 복제 일관성과 같은가? **제약을 만족하는 상태와 여러 사본의 관찰 순서**는 구분한다.

### 면접 질문 04: 격리 수준이 높으면 모든 문제가 사라지는가

**답변:** 높은 격리는 동시성 이상을 줄이지만 충돌·중단·재시도 비용이 생길 수 있습니다. Read Committed는 다른 문장에서 새 커밋을 볼 수 있고, Repeatable Read의 세부 의미는 DB마다 다릅니다. PostgreSQL의 Repeatable Read도 직렬 실행과 같지는 않습니다.

**꼬리질문:** Serializable이면 트랜잭션이 하나씩 실행되는가? **결과를 직렬 실행과 동등하게 보장**하는 것이며 내부 구현은 동시 실행과 충돌 검출·중단을 사용할 수 있다.

### 면접 질문 05: MVCC면 잠금이 필요 없는가

**답변:** MVCC는 여러 행 버전과 스냅샷으로 읽기·쓰기 간 간섭을 줄입니다. 쓰기 충돌이나 일부 잠금·스키마 변경까지 사라지는 것은 아닙니다. 오래된 버전 정리와 장기 트랜잭션의 영향도 확인해야 합니다.

**꼬리질문:** snapshot이 같으면 모든 불변식이 지켜지는가? 서로 다른 행을 바꾸는 **write skew 같은 이상**이 가능해 격리 수준과 업무 불변식을 함께 설계한다.

### 면접 질문 06: 정규화와 비정규화는 언제 선택하는가

**답변:** 정규화는 중복과 갱신 이상을 줄이도록 함수 종속성에 맞춰 구조를 나누는 접근입니다. 비정규화는 읽기 비용을 줄이기 위해 중복을 허용할 수 있지만 원본·갱신·불일치 복구를 정해야 합니다. 주문 시점 가격은 현재 상품 가격과 의미가 달라 별도 이력 값으로 저장하는 것이 타당할 수 있습니다.

**꼬리질문:** JOIN이 많으면 무조건 비정규화하는가? **실행 계획·조회 빈도·쓰기 빈도·정합성 요구**를 먼저 측정한다.

### 면접 질문 07: LEFT JOIN의 COUNT는 무엇을 세는가

**답변:** COUNT(*)는 조인 결과 행을 세고 COUNT(오른쪽의 NOT NULL 키)는 매칭된 오른쪽 행을 셉니다. 오른쪽이 없는 왼쪽 행도 LEFT JOIN 결과에는 한 행 남으므로 두 값이 다를 수 있습니다. 오른쪽 조건을 WHERE에 놓으면 보존하려던 행이 제거될 수도 있습니다.

**꼬리질문:** 중복 조인으로 개수가 늘어나면? **관계의 일대다·다대다와 집계 단위**를 확인하고 필요하면 먼저 집계한다.

### 면접 질문 08: N+1 문제는 어떻게 찾는가

**답변:** 목록 조회 한 번 뒤 각 항목의 관련 데이터를 N번 추가 조회하는 패턴입니다. 요청당 쿼리 수와 DB 왕복 시간을 측정하고 JOIN·일괄 조회·적절한 eager loading으로 줄입니다. 거대한 JOIN이 행을 과도하게 늘릴 수 있으므로 결과 크기도 확인합니다.

**꼬리질문:** 연결 풀을 늘리면 해결되는가? **조회 횟수 자체와 DB 부하**가 남으므로 근본 해결이 아니다.

### 면접 질문 09: WAL이 있으면 커밋은 언제나 안전한가

**답변:** WAL은 변경된 데이터 페이지보다 복구용 로그를 먼저 기록하는 원칙입니다. 커밋 응답 전에 어디까지 durable하게 저장하는지, 복제본 승인 조건과 장애 범위를 확인해야 합니다. 로그 파일이 있다는 사실만으로 모든 장애에 대한 무손실을 보장하지 않습니다.

**꼬리질문:** 백업도 필요 없는가? **잘못된 삭제·논리 오류·전체 저장장치 손실**과 복구 시점 요구는 별도다.

### 면접 질문 10: RAG의 벡터 DB가 일반 DB를 대체하는가

**답변:** 벡터 인덱스는 유사도 후보를 찾는 역할입니다. 사용자·권한·문서 버전·처리 상태의 정합성은 일반적인 저장·트랜잭션 설계가 필요합니다. 한 제품에 여러 기능이 있어도 각 보장을 따로 확인합니다.

**꼬리질문:** 문서를 지웠는데 검색에 남으면? **원본 저장소와 검색 인덱스의 갱신 지연**, 캐시, 삭제 표시·재색인 경로를 확인하고 권한 필터를 검색 경로에도 적용한다.

## 복습문제와 풀이

**문제 1.** 청크가 없는 문서까지 세려고 LEFT JOIN 뒤 COUNT(\*)를 쓰면 어떤 점을 주의해야 하는가?

<details>
<summary>풀이 보기</summary>

LEFT JOIN은 오른쪽 값이 NULL인 행을 남길 수 있고 COUNT(\*)는 그 행도 센다. 실제 청크 개수를 원하면 NULL이 될 수 있는 청크 열을 COUNT하는 등 결과 의미에 맞게 집계해야 한다.

</details>

**문제 2.** 인덱스를 모든 열에 만들면 항상 빨라지는가?

<details>
<summary>풀이 보기</summary>

아니다. 각 인덱스가 공간과 쓰기 갱신 비용을 쓰며, 선택도·정렬·반환량에 따라 조회에서도 유리하지 않을 수 있다. 주요 쿼리와 실행 계획을 기준으로 설계한다.

</details>

**문제 3.** 트랜잭션으로 감쌌는데도 업무 제약이 깨질 수 있는 이유는?

<details>
<summary>풀이 보기</summary>

선택한 격리 수준이 해당 읽기·쓰기 충돌을 막지 못하거나 업무 조건을 잘못 표현했을 수 있다. 관련 행·검사·갱신을 정의하고 DB의 격리 보장과 충돌 처리 방식을 확인해야 한다.

</details>
