# 프로그램은 값과 이름, 실행 상태로 이루어진다

문서 파일을 읽어 단어 수를 세는 Python 코드를 생각해보자. 코드에는 파일 경로를 담는 변수, 문자열을 나누는 함수, 결과를 저장하는 리스트가 있다. 화면에서는 모두 글자와 숫자로 보이지만 실행 중에는 서로 다른 종류의 객체와 호출 상태가 생긴다. 파일이 닫히지 않거나, 같은 리스트를 여러 함수가 바꾸거나, 설치된 라이브러리가 달라지면 짧은 코드도 예상과 다르게 동작한다. 프로그래밍의 기초는 문법을 외우는 데서 끝나지 않는다. **값이 어디에 있고, 무엇이 그 값을 가리키며, 어느 실행 단계에서 바뀌는지**를 설명할 수 있어야 한다.

## 값, 타입, 이름을 분리해서 생각하기

Python에서 `x = 3`은 이름 x를 정수 객체에 연결하는 대입이다. 객체에는 정체성, 타입, 값이 있다. 타입은 허용되는 연산을 정한다. `3 + 2`는 숫자 덧셈이고 `'3' + '2'`는 문자열 연결이다. 같은 기호라도 어떤 객체에 적용하는지에 따라 의미가 달라진다. 정체성은 같은 객체인가를 판단하는 기준이고 값은 그 객체가 표현하는 내용이다. `==`는 일반적으로 값의 동등성을, `is`는 동일 객체인지를 비교하므로 둘을 바꾸어 쓰면 안 된다. 작은 정수나 문자열을 구현이 재사용하는지에 프로그램의 정확성을 의존시키지 않는다.

정수와 문자열처럼 불변인 객체는 생성한 객체의 값을 바꿀 수 없다. `x += 1`은 정수 객체 안의 3을 4로 고치는 것으로 이해하기보다, 결과 정수 객체에 x가 연결된다고 보는 편이 정확하다. 리스트·딕셔너리는 가변 객체여서 내용을 바꿀 수 있다. 다만 “tuple은 불변”이라는 말도 tuple이 참조하는 모든 객체까지 불변이라는 뜻은 아니다. tuple 안에 리스트가 있으면 tuple이 가진 참조는 그대로인 채 리스트 내용은 바뀔 수 있다.

```py
a = [1, 2]
b = a
b.append(3)
b = [9]
print(a)  # [1, 2, 3]
print(b)  # [9]
```

첫 줄에서 리스트 하나가 만들어지고 a가 이를 가리킨다. 둘째 줄은 같은 리스트를 가리키는 이름 b를 추가한다. 셋째 줄은 b가 가리키는 리스트 자체를 바꾸므로 a로 보아도 3이 추가되어 있다. 넷째 줄은 새 리스트를 만들고 b의 연결만 바꾼다. 기존 리스트와 a의 관계는 남아 있으므로 마지막 두 출력이 다르다. **객체 변경과 이름 재연결을 구분하는 것**이 이 예제의 핵심이다.

## 복사는 어느 깊이까지 하는가

이름을 추가하는 대입과 새 객체를 만드는 복사는 다르다. 복사에도 깊이가 있다. `a.copy()`는 새 바깥 리스트를 만들지만 각 원소의 참조를 복사한다. 원소가 또 리스트라면 안쪽 객체는 공유한다. “리스트를 복사했는데 원본도 바뀌었다”는 문제는 보통 이 지점에서 생긴다.

```py
a = [[1], [2]]
b = a.copy()
b[0].append(7)
b.append([3])
print(a)  # [[1, 7], [2]]
print(b)  # [[1, 7], [2], [3]]
```

둘째 줄 뒤에 바깥 리스트는 두 개지만 안쪽 리스트 `[1]`, `[2]`는 공유한다. 셋째 줄은 공유한 안쪽 리스트를 바꾼다. 넷째 줄은 b의 바깥 리스트에 새 원소를 추가하므로 a의 길이는 바뀌지 않는다. 깊은 복사는 중첩 객체를 재귀적으로 복사하지만 언제나 정답은 아니다. 큰 데이터를 통째로 복사하면 시간과 메모리가 들고, 파일·연결·외부 자원 같은 객체는 복사 의미가 단순하지 않다. 수정할 범위를 정하고 그 경계에서 필요한 만큼 복사하는 편이 설계상 명확하다.

함수 인자도 이름 바인딩으로 이해할 수 있다. 함수를 호출하면 인자 이름이 전달된 객체를 가리킨다. 함수 내부에서 `items.append(x)`를 하면 호출자도 보는 객체가 바뀔 수 있다. 반면 `items = []`는 지역 이름의 연결을 바꾸므로 호출자의 이름을 재연결하지 않는다. 반환값을 사용해 새 결과를 전달할지, 입력을 직접 변경할지 계약을 정해야 함수끼리 예상치 못하게 간섭하지 않는다.

## 객체 수명과 CPython의 메모리 회수

객체가 언제 필요 없어지는지는 참조 관계와 연결된다. `del x`는 이름 x를 제거한다. 다른 리스트나 지역 이름이 같은 객체를 가리키고 있으면 그 객체는 여전히 사용 가능하다. CPython은 일반적으로 참조계수와 순환 참조를 다루는 가비지 컬렉션을 사용한다. 서로를 가리키는 두 객체는 외부에서 도달할 수 없어도 참조계수만 보면 서로의 참조가 남을 수 있어 별도 처리가 필요하다. 이것은 CPython 구현의 설명이며 모든 Python 구현이 같은 방식과 시점에 객체를 회수한다는 언어 차원의 보장은 아니다.

객체 회수와 운영체제에 RAM을 돌려주는 시점도 다르다. 런타임 할당기는 다음 객체 생성에 재사용하려고 빈 메모리를 보유할 수 있다. 따라서 큰 리스트를 지운 뒤 프로세스 메모리 수치가 그대로라고 해서 즉시 누수라고 결론 내릴 수 없다. 살아 있는 참조가 남은 경우, 런타임이 빈 공간을 보유한 경우, Python 바깥의 라이브러리가 할당한 경우를 구분해야 한다. `tracemalloc`은 Python이 추적하는 할당을 비교하는 도구이고, 운영체제의 RSS는 프로세스에 상주한 메모리의 관측치다. 두 수치는 질문과 범위가 다르다.

파일과 네트워크 연결은 메모리만이 아니라 외부 자원이다. 참조가 사라지면 언젠가 닫힐 것이라 기대하기보다 `with open(...)`처럼 자원 해제 경계를 명시한다. 예외가 발생해도 context manager의 종료 처리가 실행되므로 오류 경로에서 파일이 남는 일을 줄인다. `try/except`로 모든 예외를 삼켜 버리면 실제 실패가 정상 결과처럼 보일 수 있다. 처리할 수 있는 예외만 잡고, 나머지는 문맥을 붙여 전달하는 것이 원인 추적에 도움이 된다.

## C의 포인터와 저장 기간

C의 포인터는 특정 타입의 데이터에 접근할 주소를 담는 값이다. `int x = 3; int *p = &x;`에서 `&x`는 x의 주소, `*p`는 그 주소를 통해 접근한 정수다. 포인터 값을 복사하면 같은 저장 영역을 가리킬 수 있지만 Python 참조처럼 접근 안전성이 자동 보장되지는 않는다. 가리키는 대상이 사라졌거나 범위를 벗어나면 정의되지 않은 동작이 생길 수 있다.

```c
int *p = malloc(2 * sizeof *p);
if (p == NULL) { return 1; }
p[0] = 10;
p[1] = 20;
free(p);
p = NULL;
```

첫 줄은 정수 두 개를 담을 동적 영역을 요청한다. 둘째 줄은 실패 가능성을 처리한다. 셋째·넷째 줄은 할당 범위 안에 값을 저장한다. `free`는 그 영역을 더 이상 사용하지 않겠다는 뜻이다. 마지막 대입은 이 이름으로 실수로 다시 접근하는 일을 줄이지만, 다른 포인터가 같은 주소를 복사해 두었다면 그 포인터까지 고치지는 않는다. 이미 해제한 주소를 쓰는 use-after-free, 두 번 해제하는 double free, 유효한 마지막 포인터를 잃어 해제할 수 없는 누수를 구분한다.

자동 저장 기간을 갖는 지역 변수와 동적 할당의 수명도 다르다. 일반적인 블록 지역 변수는 그 블록을 벗어나면 수명이 끝나므로 함수 반환 뒤에도 사용할 수 없다. 다만 `static` 지역 변수처럼 이름은 지역 범위에 있어도 저장 기간이 프로그램 전체인 예외가 있다. 지역 변수의 주소를 반환하면 호출자가 수명이 끝난 대상을 가리키게 될 수 있다. 동적 할당한 대상은 함수가 끝나도 살아 있을 수 있지만 누가 해제할지 정해야 한다. 전형적인 구현에서 호출 상태는 스택에, 동적 영역은 힙에 배치되지만 최적화 때문에 어떤 값은 레지스터에 있거나 저장 자체가 사라질 수 있다. 언어의 수명 규칙과 특정 컴파일 결과의 물리 배치를 동일시하지 않는다.

함수의 지역 이름과 객체 수명을 구별하면 반환값도 이해하기 쉽다. Python 함수에서 리스트를 만들어 반환하면 함수의 지역 이름은 사라져도 호출자가 반환 객체를 참조하므로 리스트는 살아 있다. 이는 C에서 수명이 끝난 자동 지역 배열의 주소를 반환하는 것과 다르다. 같은 “함수 안에서 만들었다”는 표현만으로 대상의 수명을 판단할 수 없는 이유다.

또한 범위는 이름을 어디서 찾을 수 있는지의 규칙이고 수명은 대상이 언제까지 유효한지의 규칙이다. 중첩 함수가 바깥 변수를 참조하는 closure, 클래스가 보관한 객체, 전역 캐시처럼 이름이 처음 생긴 실행 단계 뒤에도 참조가 유지될 수 있다. 호출 스택에서 함수가 빠졌다는 사실만으로 그 함수에서 접근한 모든 데이터가 사라졌다고 판단하지 않는다.

## 셸, 프로세스, 빌드가 코드를 실행하는 과정

터미널은 텍스트 입출력 창이고 셸은 명령을 해석하는 프로그램이다. `python3 count.py data.txt`를 입력하면 셸은 실행할 프로그램을 찾고 인자를 전달해 새 프로세스를 시작한다. 현재 작업 디렉터리는 상대 경로의 기준이고 환경변수는 자식 프로세스에 전달할 설정이다. 파일이 존재하는데도 못 찾는다면 코드가 잘못된 것인지, 다른 디렉터리에서 실행한 것인지 먼저 분리한다.

프로세스는 표준 입력·표준 출력·표준 오류라는 통로를 사용할 수 있다. `>`는 출력을 파일로 보내고 파이프는 한 명령의 출력을 다음 명령의 입력에 연결한다. 정상 데이터와 오류 메시지를 다른 통로에 쓰면 파이프를 연결해도 데이터 형식이 깨지는 일을 줄일 수 있다. 종료 코드는 호출자가 성공·실패를 판별하는 수단이다. 오류 문장을 출력했지만 종료 코드가 0이면 자동화 도구가 성공으로 오해할 수 있다.

C는 소스에서 기계어로 변환하는 컴파일과 여러 기계어·라이브러리 부분을 연결하는 링크를 구분한다. 헤더를 못 찾는 오류, 심볼을 못 찾는 링크 오류, 실행 중 접근 오류는 서로 다른 단계의 문제다. Python도 실행 전에 구문을 분석하고 내부 표현을 준비하며 모듈을 로드한다. “인터프리터 언어라 준비 과정이 없다”는 식으로 이해하면 import 경로와 패키지 충돌을 놓친다. 가상환경은 의존성 집합을 분리하고 버전 고정은 다시 설치할 대상을 명시한다. 운영체제와 CPU 아키텍처, 외부 서비스까지 완전히 고정하는 것은 아니다.

## 변경 기록과 디버깅은 원인을 좁히는 도구다

Git의 commit은 파일을 저장했다는 사실보다 **어떤 변경 묶음을 다시 식별할 수 있는가**가 중요하다. 작은 논리 단위로 commit하고 diff로 의도하지 않은 변경을 확인하면 오류가 어느 변경에서 들어왔는지 찾기 쉽다. branch는 변경 흐름을 분리하지만 복사한 폴더처럼 이해하기보다 commit을 가리키는 이동 가능한 이름으로 보는 것이 merge를 이해하는 데 유리하다. 데이터·비밀·대용량 결과를 무작정 Git에 넣지 않고 코드와 데이터 버전의 역할을 구분한다.

오류를 만나면 먼저 가장 작은 재현 입력을 만든다. stack trace는 어디서 호출되어 실패했는지 보여 주고 breakpoint는 그 시점의 지역 값과 제어 흐름을 멈춰 확인하게 한다. 출력문을 많이 넣는 것보다 예상과 처음 달라지는 상태를 찾는 것이 효율적이다. 함수가 잘못된 값을 받았는지, 올바른 입력을 잘못 바꿨는지, 외부 자원에서 실패했는지 경계를 따라 좁힌다. 실행 명령·입력·의존성·기대값을 함께 남기면 다른 사람도 같은 문제를 재현할 수 있다.

## 핵심 정리

Python의 이름과 객체는 다르며 대입은 참조 관계를 바꾼다. 객체 변경과 이름 재연결을 구분하면 함수 인자와 복사의 동작을 예측할 수 있다. CPython의 회수 방식은 객체 수명을 설명하지만 OS 메모리 수치의 즉시 감소를 보장하지 않는다. C에서는 포인터의 대상과 수명, 해제 책임을 직접 관리해야 한다. 셸·작업 디렉터리·환경변수·의존성은 프로그램의 실제 입력 조건이다. Git과 디버거는 변경과 실행 상태를 추적해 원인을 좁히는 도구다.
