# 소프트웨어 공학은 코드를 계속 바꿀 수 있게 만드는 방법이다

내 컴퓨터에서 한 번 올바른 결과가 나온 스크립트를 생각해보자. 내일은 입력 파일 형식이 바뀌고, 다음 주에는 외부 API가 실패하며, 동료는 다른 패키지 버전으로 실행할 수 있다. 새로운 기능을 넣다가 기존 결과가 바뀔 수도 있다. 소프트웨어 공학은 이런 변화 속에서도 코드를 이해·검증·배포·수정할 수 있게 만드는 원리다. 처음부터 복잡한 구조를 만드는 것이 아니라 책임과 실패 경계를 분명히 하는 데서 시작한다.

## 모듈은 함께 바뀌는 것과 따로 바뀌는 것을 나눈다

### 개념과 작동 원리

문서 검색 스크립트가 파일 읽기, 청크 분할, 검색, 모델 호출, 저장, HTTP 응답을 한 함수에서 모두 한다고 하자. 검색 방법 하나를 바꾸려 해도 파일과 DB·네트워크 설정을 함께 이해해야 한다. 테스트하려면 실제 모델까지 호출해야 하고 작은 오류가 어디서 시작했는지 찾기 어렵다. 각 부분이 바뀌는 이유를 기준으로 경계를 나누면 독립적으로 이해하고 검증할 수 있다.

모듈은 폴더 이름보다 책임과 입출력 계약으로 정의된다. 청크 분할기는 텍스트와 분할 규칙을 받아 청크 목록을 돌려주고, 저장소는 청크를 저장·조회하는 책임을 가진다. HTTP 계층은 요청을 검증하고 응용 기능을 호출해 응답으로 바꾼다. 핵심 계산이 특정 웹 프레임워크나 DB 연결을 직접 만들지 않도록 하면 같은 기능을 CLI·서버·테스트에서 재사용하기 쉽다.

외부 의존성을 함수 인자로 전달하는 방식은 이를 돕는다. 검색 함수가 어떤 DB를 사용할지 내부에서 고정하기보다 검색 가능한 인터페이스를 받으면 테스트에서 작은 가짜 구현을 넣을 수 있다. 이것이 의존성 주입의 기본 생각이다. 모든 함수에 추상 클래스와 복잡한 패턴을 붙일 필요는 없다. 실제로 바꿀 가능성이 있는 경계와 격리할 실패를 기준으로 최소한의 분리를 한다.

모듈을 잘게 나누어도 공유 전역 상태가 많으면 서로 얽힌다. 한 함수가 숨겨진 설정을 바꾸어 다른 함수의 결과에 영향을 주면 호출 순서를 알아야만 동작을 이해할 수 있다. 가능한 한 입력을 명시하고 변경하는 상태를 제한하면 원인과 결과가 드러난다. 함수형 스타일과 객체 지향 스타일은 이를 달성하는 여러 수단이지 어느 하나의 이름만으로 좋은 설계가 보장되지는 않는다.

### 책임을 나눌 때 바뀌는 이유를 기준으로 보기

| 책임 | 입력→출력 계약 | 바뀔 수 있는 이유 |
|---|---|---|
| 청크 분할 | 텍스트·규칙→청크 목록 | 분할 전략 변경 |
| 검색 | 질의·인덱스→후보 목록 | 검색 알고리즘 변경 |
| 저장 | 레코드→저장 결과 | DB·스키마 변경 |
| HTTP 변환 | 요청→응답 | 외부 API 계약 변경 |

서로 다른 변경 이유를 하나의 거대한 함수에 모으면 테스트에 필요한 의존성도 함께 늘어난다. 반대로 한 줄마다 클래스를 만들면 흐름을 따라가기 어려워질 수 있다. **모듈 수보다 경계의 응집도와 의존 방향**을 확인한다.

순수 계산과 외부 I/O를 나누면 작은 입력으로 계산을 검증하고, 경계에서는 DB·파일·네트워크 계약을 별도로 확인할 수 있다. 모듈 분리는 외부 서비스 장애가 사라진다는 보장이 아니라 원인과 책임을 추적할 단위를 제공한다.

## 계약, 타입, 오류가 외부 경계를 만든다

### 개념과 작동 원리

함수 계약은 허용 입력, 반환 의미, 실패 조건을 정한다. “문자열을 정규화한다”는 말에는 앞뒤 공백만 지우는지, 내부 공백도 합치는지, 빈 문자열을 허용하는지 같은 선택이 있다. 선택이 정해져야 테스트도 정해진다.

```py
def normalize_text(text: str) -> str:
    if not isinstance(text, str):
        raise TypeError('text must be str')
    return ' '.join(text.split())
```

이 함수는 공백으로 나눈 조각을 한 칸의 공백으로 연결한다. `'  a\n b  '`는 `'a b'`가 되고 공백만 있으면 빈 문자열이 된다. 타입 주석은 의도를 도구와 독자에게 알리지만 Python에서 주석만으로 런타임 입력이 자동 차단되는 것은 아니다. 예제의 명시적 검사가 그 역할을 한다. 모든 내부 함수에 중복 검사를 넣기보다 외부 입력 경계에서 검사하고 내부에서는 보장된 계약을 사용할 수 있다.

예외는 실패를 정상 반환값과 구분하는 방법이다. 파일 없음, 잘못된 형식, 외부 timeout은 원인과 대응이 다르다. 모두 빈 리스트로 바꾸면 “검색 결과가 실제로 없음”과 “검색 서비스가 실패함”을 구별할 수 없다. 호출자가 처리할 수 있는 예외를 정의하고, 더 높은 계층에서 사용자에게 보여 줄 상태로 변환한다. 원래 예외와 문맥을 잃지 않아야 운영 로그로 원인을 추적할 수 있다.

API 계약은 함수보다 오래 외부에 노출될 수 있다. 응답 필드의 삭제·타입 변경은 기존 클라이언트를 깨뜨린다. 선택 필드 추가와 필수 의미 변경은 영향이 다르므로 버전과 호환 정책을 정한다. 설정과 비밀값도 코드에 섞어 넣는 대신 실행 환경에서 주입할 수 있게 한다. 단, 환경변수만 썼다고 비밀이 자동 보호되는 것은 아니며 로그·오류 메시지·이미지에 들어가는 경로를 구분한다.

### 반환할 값과 실패를 같은 계약에 적기

문자열 앞뒤 공백을 제거하고 빈 결과를 허용하지 않는 함수라면 타입과 값의 조건을 함께 검사해야 한다.

```py
def require_text(value: str) -> str:
    if not isinstance(value, str):
        raise TypeError('text must be str')
    result = value.strip()
    if not result:
        raise ValueError('text must not be blank')
    return result

assert require_text('  alpha  ') == 'alpha'
assert require_text(require_text(' alpha ')) == 'alpha'
```

| 실패 종류 | 호출자가 판단할 일 |
|---|---|
| 허용하지 않은 타입 | 호출 코드·데이터 계약 수정 |
| 빈 내용 등 값 오류 | 사용자 입력·업무 규칙 확인 |
| 외부 의존성 장애 | 재시도 가능성·남은 예산 확인 |
| 내부 불변식 위반 | 구현 오류·상태 조사 |

모든 예외를 None으로 바꾸면 '값이 없음'과 '처리에 실패함'을 구분할 수 없다. 타입 annotation을 적는 것만으로 Python 런타임이 위 값 검사를 자동 수행하지도 않는다.

## 테스트는 무엇이 바뀌면 안 되는지 기록한다

### 개념과 작동 원리

단위 테스트는 작은 계산 단위의 동작을 확인한다. 통합 테스트는 코드와 DB·파일·프로토콜 같은 연결이 맞는지 확인한다. End-to-end 테스트는 사용자가 실제로 거치는 흐름을 확인한다. 이들은 더 우월한 순서가 아니라 서로 다른 실패를 찾는다. 모든 것을 end-to-end로만 시험하면 느리고 오류 위치가 모호해지며, 단위 테스트만 있으면 연결 설정 문제를 놓친다.

```py
import pytest

@pytest.mark.parametrize('raw, expected', [
    ('  a\n b  ', 'a b'),
    ('   ', ''),
    ('문서', '문서'),
])
def test_normalize(raw, expected):
    assert normalize_text(raw) == expected

def test_non_text_rejected():
    with pytest.raises(TypeError):
        normalize_text(3)
```

첫 테스트는 정상 입력 하나만이 아니라 여러 공백·빈 결과·한글의 의미를 확인한다. 둘째는 계약 밖 입력을 조용히 바꾸지 않고 거부하는지 확인한다. 구현의 split·join 호출 자체를 다시 확인하는 것이 아니라 외부에서 관찰할 결과를 검증한다. 내부 구현을 바꾸어도 계약이 같으면 테스트는 유지되는 것이 이상적이다.

Fixture는 반복되는 준비·정리를 묶는다. 임시 DB를 준비하고 종료 시 지우거나 작은 입력 데이터를 제공할 수 있다. Mock은 외부 의존성을 통제해 timeout·오류 같은 경로를 재현한다. 하지만 모델 API를 항상 정답 문자열을 주는 mock으로 바꾸어 통과했다고 실제 모델 품질이 좋아진 것은 아니다. 소프트웨어의 제어 흐름 검증과 모델의 답변 품질 평가는 분리해서 함께 수행해야 한다.

테스트가 가끔 실패하는 flaky 현상은 시간·실행 순서·공유 상태·네트워크 같은 숨은 의존성이 있다는 신호일 수 있다. 무조건 재실행해 초록색으로 만들면 원인이 남는다. 입력·시드·시간·외부 서비스를 통제할 수 있는 범위를 명시하고, 통제가 불가능한 실제 연결 테스트는 별도의 목적과 허용 조건으로 둔다. 테스트 개수보다 어떤 요구와 실패를 실제로 확인하는지가 중요하다.

### 예제·속성·연결 검증의 역할 나누기

| 검사 | 이 예의 질문 | 놓칠 수 있는 것 |
|---|---|---|
| 단위 예제 | `' alpha '`가 `'alpha'`인가 | 입력 전체 범위 |
| 경계 예제 | 빈 문자열·잘못된 타입은? | 실제 외부 연결 |
| 속성 | 두 번 정규화해도 결과가 같은가 | 잘못 구현한 상수 함수도 일부 속성 통과 가능 |
| 통합 검사 | DB 문자·NULL·트랜잭션 계약은? | 전체 사용자 경로 |
| end-to-end | 실제 요청부터 저장·응답까지 연결되는가 | 드문 오류의 모든 조합 |

테스트가 구현의 내부 호출 순서를 그대로 복사하면 리팩터링 때 외부 동작이 같아도 깨질 수 있다. **보존해야 하는 계약과 실패 모드**를 고른다. mock이 실제 외부 서비스와 다른 응답을 주면 통합 오류를 가릴 수 있으므로 경계의 실제 계약도 확인해야 한다.

통과 개수만으로 품질을 비교하지 않는다. 필요한 경우 기존 구현을 실패시키는 입력에서 새 구현이 기대 결과를 내는지 확인해 검사가 문제를 포착하는지 본다.

## 타입 검사, 코드 리뷰, 작은 변경

### 개념과 작동 원리

정적 타입 검사는 실행 전에 일부 잘못된 호출과 값의 연결을 찾을 수 있다. 하지만 모든 입력·상태·업무 규칙을 증명하지는 않는다. Lint는 자주 하는 실수나 일관성을 검사하고 formatter는 표현 차이를 자동 정리한다. 이런 도구가 반복적인 문법·스타일 논쟁을 줄여 리뷰에서 설계·정확성·예외 처리를 보게 한다.

코드 리뷰는 변경을 처음 보는 사람이 이유와 결과를 이해할 수 있는지 점검하는 과정이다. 어떤 입력에서 기존 동작이 잘못됐고 새 동작이 어떻게 달라지는지 설명하면 검토가 구체적이다. 서로 무관한 정리와 기능 변경을 한 번에 섞으면 무엇이 위험하고 어떤 테스트가 필요한지 판단하기 어렵다. 작은 변경 단위는 문제 발생 시 원인 추적과 되돌리기도 돕는다.

추상화에는 비용이 있다. 아직 존재하지 않는 수십 구현을 예상해 계층을 늘리면 실제 동작을 찾는 데 더 오래 걸릴 수 있다. 반대로 같은 외부 연결을 여러 곳에 복사하면 인증·재시도 정책을 일관되게 바꾸기 어렵다. 변경 빈도, 중복된 지식, 테스트 경계가 추상화의 근거가 되어야 한다.

### 타입·스타일·업무 규칙은 다른 검사다

| 검사 도구·과정 | 잘 찾는 문제 | 자동으로 증명하지 않는 것 |
|---|---|---|
| 정적 타입 검사 | 명시한 타입 사이의 잘못된 연결 | 이메일 문자열의 실제 유효성 |
| lint | 흔한 오류 패턴·정한 규칙 | 전체 업무 정답 |
| formatter | 표현·공백·줄바꿈 일관성 | 계산 의미 보존의 모든 경우 |
| 코드 리뷰 | 의도·설계·누락·검증 범위 | 실행 가능한 모든 상태 |

int 타입의 금액이라고 음수가 불가능한 것은 아니다. list 타입이라고 비어 있지 않은 것도 아니다. 타입으로 표현한 조건과 런타임 값의 조건을 구분한다.

작은 논리 단위의 변경은 원인과 검증을 연결하기 쉽다. 리뷰 설명에는 '개선했다' 대신 **어떤 입력의 결과가 어떻게 달라지는지**를 적고, 같은 변경에 필요하지 않은 정리를 섞지 않는다.

## 로그, 지표, 트레이스는 다른 질문에 답한다

### 개념과 작동 원리

로그는 개별 사건을 시간과 문맥으로 남긴다. 요청 ID·작업 ID·오류 종류를 구조화된 필드로 기록하면 여러 줄을 연결하고 검색하기 쉽다. 단순히 “실패”라고 적는 것보다 어느 단계에서 어떤 입력 범주의 작업이 실패했는지 남기는 것이 유용하다. 사용자 원문이나 비밀을 모두 남기는 것이 정보량의 정답은 아니며 진단에 필요한 문맥과 보관 범위를 정한다.

Metric은 요청 수·오류율·진행 중 작업·지연 분포 같은 집계다. Trace는 한 요청이 HTTP·검색·DB·외부 모델을 지나는 경로와 각 구간을 연결한다. 로그는 “이 요청에 무슨 일이 있었나”, 지표는 “전체에서 문제가 커지고 있나”, trace는 “어디서 시간이 들었나”라는 서로 다른 질문에 답한다. 하나를 많이 모으면 나머지가 자동 대체되는 것은 아니다.

```py
import json
from time import perf_counter

start = perf_counter()
result = normalize_text(' a   b ')
print(json.dumps({
    'event': 'normalize_finished',
    'request_id': 'example-1',
    'elapsed_ms': (perf_counter() - start) * 1000,
    'output_chars': len(result),
}, ensure_ascii=False))
```

이 코드는 단조 증가 시계를 이용해 구간의 경과시간을 재고 필드 형태로 기록한다. 결과 문자 수는 입력 본문을 그대로 기록하지 않고 처리 상황을 관측하는 예다. 이처럼 단순한 함수의 한 번 측정값은 신뢰할 벤치마크가 아니다. 반복 측정, 충분한 작업량, 측정 구간과 준비 비용 분리, 장비·부하 조건이 필요하다. 로그 직렬화·전송 자체도 비용이므로 과도한 계측이 프로그램의 행동을 바꿀 수 있다.

### 관찰 지표의 분모와 목표를 계산하기

10,000개의 평가 대상 요청 중 9,970개가 성공하면 성공률 SLI는 99.7%다. 목표 SLO가 99.9%라면 허용 실패 수는 이 평가창에서 10개이고 실제 실패는 30개다.

| 항목 | 이 예의 값 | 의미 |
|---|---|---|
| SLI | 99.7% | 관측한 지표 |
| SLO | 99.9% | 목표 수준 |
| 오류 예산 | 10/10,000 | 목표에 따른 허용 실패 |
| 실제 실패 | 30/10,000 | 예산의 3배 |

**평가 대상 요청의 정의가 분모**다. timeout·잘못된 입력·내부 재시도를 어떻게 집계하는지 정하지 않으면 팀마다 성공률이 달라진다. 성공 응답이어도 사용자가 원하는 작업을 못 끝냈다면 지표 정의를 다시 보아야 할 수 있다.

로그의 요청 ID는 한 사건을 추적하는 데 유용하지만, 요청마다 다른 ID를 지표 label로 만들면 시계열 수가 폭증할 수 있다. [Prometheus 공식 label 지침](https://prometheus.io/docs/practices/naming/)에서 cardinality와 label 설계를 확인한다. [Google SRE의 SLO](https://sre.google/sre-book/service-level-objectives/)와 [모니터링 설명](https://sre.google/sre-book/monitoring-distributed-systems/)을 함께 참고한다.

## 프로파일링은 병목의 위치를 나눈다

### 개념과 작동 원리

경과시간은 사용자가 기다린 실제 시간이고 CPU 시간은 계산에 CPU를 사용한 시간이다. 네트워크 대기가 길면 경과시간은 큰데 CPU 시간은 작을 수 있다. CPU profiler는 어떤 함수가 계산 시간을 쓰는지, 메모리 profiler는 어느 경로에서 할당이 늘어나는지 추적한다. Python에서 보이는 할당만으로 C 확장·GPU·OS 매핑까지 모두 설명할 수는 없으므로 관측 도구의 범위를 알아야 한다.

평균 지연이 100ms라고 해도 대부분 20ms이고 일부가 수초일 수 있다. p95는 관측 요청의 약 95%가 그 이하인 지연 경계를 나타내며, 최댓값·평균과 다른 양이다. 표본 수와 측정 창이 작으면 꼬리 지연도 불안정하다. 요청 혼합·동시성·캐시 상태가 바뀐 전후 결과를 같은 성능 비교로 취급하지 않는다.

최적화는 먼저 전체 비용의 큰 부분을 찾고, 동작을 보존한 작은 변경을 한 뒤 같은 조건에서 재측정한다. 작은 함수가 눈에 띄게 비효율적이어도 전체 시간의 1%라면 큰 개선이 어렵다. 정확성 확인 없이 빠르게 만든 구현은 다른 문제를 푼 것일 수 있다. CPU·메모리·처리량·지연 중 어떤 지표를 개선하려는지도 명시해야 한다.

### 평균과 꼬리 지연을 작은 표본에서 계산하기

20개 관측 중 19개가 10ms, 하나가 1000ms라고 하자. 평균은 $(19\times10+1000)/20=59.5$ms다. nearest-rank 규칙으로 p95는 정렬 후 19번째 값 10ms, p99는 20번째 값 1000ms다.

```py
import math
latencies = sorted([10]*19 + [1000])
nearest_rank = lambda p: latencies[math.ceil(p*len(latencies))-1]
assert sum(latencies)/len(latencies) == 59.5
assert nearest_rank(.95) == 10 and nearest_rank(.99) == 1000
```

분위수 계산 규약·표본 수·집계 창을 명시해야 한다. 표본이 적으면 p99가 극단 관측 하나에 좌우되며, 서로 다른 구간의 p95를 평균해 전체 p95를 얻을 수는 없다.

순차 단계가 파싱 5ms·검색 20ms·생성 70ms·저장 5ms인 모형에서 생성만 2배 빨라지면 전체는 65ms다. 겹쳐 실행되는 단계의 시간이나 parent span에 포함된 시간을 단순 합산하면 중복 계산할 수 있다.

## 패키징과 컨테이너는 실행 조건을 전달한다

### 개념과 작동 원리

소스코드와 실행 환경은 다르다. Python 버전·패키지·네이티브 라이브러리·설정·입력 파일이 맞아야 실행된다. 가상환경은 패키지 집합을 분리하고 lockfile은 선택한 의존성 버전을 다시 설치할 수 있게 돕는다. 하지만 같은 패키지 버전이라도 운영체제·CPU 아키텍처에 따라 다른 바이너리를 받거나 빌드가 필요할 수 있다. 재현 가능한 결과를 위해 코드와 데이터·설정의 식별도 함께 관리한다.

컨테이너 image는 파일 시스템과 실행 구성을 묶는 읽기 중심의 템플릿이고 container는 그 image로 시작한 실행 인스턴스다. 일반적인 Linux 컨테이너는 호스트 커널을 공유하며 namespace와 자원 제어 등으로 격리한다. 별도 커널을 가진 가상머신과 같지 않다. Mac의 Docker Desktop에서는 Linux 컨테이너를 위한 VM 계층이 있을 수 있어 사용자 OS와 실행 커널을 구분한다.

ARM64와 AMD64 image는 실행 대상에 맞아야 한다. 에뮬레이션으로 실행될 수 있어도 실제 속도·도구 호환성이 달라질 수 있다. 컨테이너를 삭제하면 사라질 쓰기 영역과 지속 저장할 volume도 구분한다. “image를 만들었다”는 사실만으로 DB 파일·비밀·외부 연결·권한까지 배포가 끝난 것은 아니다.

### 소스·빌드·실행 상태의 식별자를 연결하기

| 대상 | 기록할 예 | 같은 것으로 볼 수 없는 것 |
|---|---|---|
| 소스 | commit ID | 작업 중인 파일 전체 |
| 의존성 | 잠긴 버전·플랫폼 | 모든 OS의 동일 실행 결과 |
| 이미지 | 내용으로 식별하는 digest | 나중에 다른 내용을 가리킬 수 있는 tag |
| 실행 인스턴스 | 설정·환경·외부 자원 상태 | 이미지 파일만의 상태 |

이미지에 앱을 묶어도 실행 시 주입되는 설정, 마운트한 데이터와 외부 DB가 달라지면 결과가 달라질 수 있다. 빌드한 산출물과 실제 배포한 산출물이 같은지 확인해야 한다.

[Docker 공식 이미지 설명](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/)은 이미지의 계층과 불변성을 설명한다. 컨테이너 인스턴스의 쓰기 상태를 이미지 자체의 수정과 혼동하지 않는다. tag·digest로 특정 이미지를 지정하는 차이는 [공식 image pull 문서](https://docs.docker.com/reference/cli/docker/image/pull/)를 참고한다.

## CI/CD와 운영 중의 보장

### 개념과 작동 원리

CI는 변경을 통합할 때 빌드·정적 검사·의미 있는 테스트를 반복 실행해 문제를 빨리 발견하는 흐름이다. CD는 검증한 변경을 배포 가능한 상태로 만들거나 실제 환경에 전달하는 자동화와 연결된다. 자동화는 사람이 이해한 검증 규칙을 반복하는 수단이지 부족한 테스트를 스스로 완성하는 장치가 아니다. 실제 변경의 위험과 필요한 확인이 파이프라인에 반영되어야 한다.

프로세스가 켜졌다는 사실과 요청을 처리할 준비가 됐다는 사실도 다르다. Liveness는 살아 있는지, readiness는 필요한 의존성을 갖추고 트래픽을 받을 수 있는지에 해당하는 점검으로 나누어 설계할 수 있다. 새 버전이 준비되기 전에 요청을 보내면 배포 중 실패가 생긴다. 재시작이 안전한지, 진행 중 작업을 어떻게 마무리할지, DB 변경이 이전 버전과 호환되는지도 중요하다.

롤백은 단순히 이전 코드를 실행하는 것만으로 충분하지 않을 수 있다. 새 버전이 데이터 형식을 바꾸거나 외부 효과를 만들었다면 되돌리기 전략이 필요하다.

단계적 배포와 작은 트래픽 검증은 영향 범위를 줄일 수 있지만 실제 지표와 실패 기준이 있어야 한다. 가용성 목표나 지연 목표 같은 SLO는 “좋은 서비스”를 관측 가능한 약속으로 바꾸는 데 쓰인다.

목표를 정할 때는 사용자가 체감하는 성공과 내부 지표가 일치하는지 확인한다.


### 검증한 산출물의 배포와 준비 상태 확인

| 단계 | 확인할 질문 |
|---|---|
| 빌드 | 소스·의존성으로 실행 산출물을 만들었는가 |
| 검증 | 계약·연결·회귀 검사가 그 산출물에 맞는가 |
| 배포 | 검증한 동일 산출물이 실제 대상에 반영됐는가 |
| 준비 확인 | 요청을 받을 조건이 충족됐는가 |
| 관찰 | 오류율·지연·업무 결과가 목표를 유지하는가 |

Kubernetes에서 readiness 실패는 보통 그 컨테이너를 향한 트래픽 전달 준비 상태에 영향을 주며, liveness 실패에 따른 재시작과 다른 역할이다. startup probe가 설정된 경우 시작 확인이 성공할 때까지 다른 probe가 기다리는 동작도 구분한다. [공식 probe 문서](https://kubernetes.io/docs/concepts/workloads/pods/probes/)에서 각 역할을 확인한다.

**복습 문제:** 빌드·테스트가 성공했고 배포 명령도 반환되었다. 사용자 화면이 최신 버전이라고 확정할 수 있는가?

<details><summary>풀이</summary>

아직 확정할 수 없다. 대상 환경의 산출물 ID, 준비 상태, 실제 응답·캐시·업무 경로를 확인해야 한다. 소스 검증 성공과 배포 반영 성공은 서로 다른 단계다.

</details>

## 핵심 정리

모듈 경계는 책임·입출력·변경 이유를 분리하는 데서 나온다. 타입과 오류 계약은 정상 결과와 실패 의미를 명확히 한다.

단위·통합·end-to-end 테스트는 서로 다른 종류의 오류를 찾는다. 로그·지표·트레이스는 개별 사건, 전체 경향, 호출 경로를 각기 보여 준다.

프로파일링은 관측 범위와 측정 조건을 이해한 뒤 해석해야 한다. 패키징·컨테이너는 환경 전달을 돕지만 모든 외부 조건을 제거하지 않는다.

배포는 실행 시작뿐 아니라 준비 상태·호환·복구까지 포함한다.
